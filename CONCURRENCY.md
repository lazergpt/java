1. Чтобы избежать deadlock  при использовании вложенных synchronized блоков, необходимо всегда захватывать блокировки в фиксированном порядке, например если obj1 во внешнем блоке, то он должен быть во внешнем и во всех других местах.
2. Если внутренний и внешний блок синхронизации используют один и тот же объект блокировки, то взаимоблокировки быть не может, т.к. Java поддерживает reentrant (повторный вход) для мониторов, т.е. технически это будет один блок.
3. wait и notify могут вызываться только внутри synchronized, Иначе будет IllegalMonitorStateException
4. Вызываются на том же объекте. Если синхронизируетесь на obj, то и wait()/notify() должны быть вызваны на obj
5. wait() освобождает монитор. Когда поток делает obj.wait(), он отпускает монитор и переходит в состояние ожидания. Когда его разбудят, он снова попытается захватить монитор, прежде чем продолжить выполнение.
6. wait() обязан проходить в цикле, а не в условии, так как если будет обычный if, то при ложном пробуждении(без notify) управление может вернуться в точку после if, а условие в этот момент ещё не выполнилось.
7. Semaphore является по сути свой блоком синхронизации под который могут пройти указанное количество потоков. Используется для ограничения параллелизма, пулов ресурсов, контроля нагрузки. Есть tryAcquire, если лимит исчерпан — можно сразу сделать «fallback» вместо ожидания. 
8. Если сделать семафору release без acquire, то счётчик уйдёт в минуса. Можно использовать для каких-нибудь хаков.
9. Частая ошибка с Semaphore, забыть сделать ему release() после acquire, в этом случае счётчик в семафоре никогда не восстановится и новые потоки перестанут проходить в критическую секцию(или к-во параллельных доступов в секцию будет меньше чем ожидалось).
10. CountDownLatch может быть полезен, если необходимо запустить все задачи одновременно.
11. Если забыли(сделали недостаточно) countDown() в каком-то потоке → await() никогда не завершится.
12. CountDownLatch одноразовый: когда счётчик стал 0, он всегда остаётся 0. Для повторного барьера нужен CyclicBarrier
13. CyclicBarrier преодолевается, когда соберутся N потоков. Под соберутся имею ввиду - когда они готовы ждать, они вызывают barrier.await()
14. Когда await() вызывает последний из N потоков:
     - выполняется опциональное barrierAction (если задано в конструкторе), пока оно не завершится, потоки на новый круг не заходят;
     - все ожидающие потоки одновременно освобождаются;
     - барьер автоматически переходит в исходное состояние (становится снова «готов к приёму N потоков»).
15. Можно вручную сбросить CyclicBarrier с помощью вызова reset. Все ожидающие потоки при этом получат BrokenBarrierException и могут попробовать повторить операцию.
16. ReentrantReadWriteLock - Предоставляет по сути два замка, на чтение и на запись. 
- Под замки на чтение могут проходить все кто хочет, если в этот момент нет записи. 
- Под замок на запись может попасть только один поток, при этом все чтения блокируются.
- Нельзя повысить уровень блокировки автоматически.
- При повышении уровня блокировки, между освобождением read и захватом write может вклиниться другой поток и захватить замок первым.
- Пример паттерна проверь-и-обнови (Check-Then-Act): 
  writeLock.lock();
  // ... write smth
  readLock.lock();
  // ...
  writeLock.unlock();
  // ... // read something
  readLock.unlock();
Используется для того, чтобы прочитать только что записанные данные. Например, при валидации консистентности записанного тяжёлого объекта, чтобы не блочить других читателей, или при чтении сложного состояния и его отправки по сети.
- Если Десять потоков взяли блокировку на чтение и одинадцатый поток хочет взять блокировку на запись в другом месте, но на этом же объекте ReentrantReadWriteLock, Он будет ждать пока не закончат чтение 11 потоков. Для решения проблемы голодания писателей есть параметр в конструкторе `fair`, чтобы всем потокам доставалось времени поровну.
17. StampedLock - гибкий и производительный подход к блокировке. 
Можно использвать как обычный ReentrantReadWriteLock, но основной смысл в оптимистичной блокировке, берём штамп, читаем значение и проверяем бралась ли за это время блокировка. Если нет, то возвращаем прочитанное значчение, если да то берём настоящий readLock и читаем под ним.
Хорош при частом чтении и небольшом количестве записей.
18. Exchanger позволяет двум потокам обменяться данными при вызове метода exchange. Обмен работает только между парой вызовов метода exchage на одном объекте. 
Если обмен попробовать провести на нечётном к-ве потоков, например 3, то обмен между первыми двумя произойдёт, а третий повиснет на методе exchange в ожидании парного вызова. 
19. volatile гарантирует, что при каждом чтении переменная вычитывается из памяти и потоки видят одно и тоже значение переменной, но он не гарантирует защиты от гонок и атомарности изменения переменной, например инкремента.
Момент в том, что количество чтений в сложном выражении не обязательно равно количеству появлений переменной в выражении, зависит от реализации компилятора `int x = vol + vol * 2 - vol`
20. Для гарантии атомарности операции над переменной используются Atomic* классы. Внутри они используют аппаратный volatile и CAS(compare-and-swap) который собственно и гарантирует атомарность инкремент.
21. CAS работает следующим образом: 
- Прочитать текущее значение переменной.
- Вычислить новое значение (текущее + 1).
- Попробовать атомарно записать новое значение, если в памяти всё ещё лежит старое значение.
- Если запись не удалась (потому что другой поток успел поменять значение), повторить с шага 1.
Отсюда вытекают плюсы: не блочит другие потоки на операции с переменной. Нет дорогого переключения контекста при неудаче. Область действия только одна переменная.
И минусы: возможен livelock, соответственно повышеный расход CPU на повторны попытки при большой конкуренции, в этом случае лучше использовать `LongAdder`;
### Основные коллекции для работы в многопоточной среде:
22. CopyOnWriteArrayList и CopyOnWriteArraySet: при каждом чтении доступ к элементам осуществляется без синхронизации, напрямую, но при модификации изменения происходят в копии структуры, доступ к которой могут получить(через новый гет или итератор) все читатели после окончания модификации. Пока идёт создание копии и её модификация, читатели читают из старой версии коллекции.
- нет риска `ConcurrentModificationException`
- каждый итератор видит консистентное состояние на момент его создания.
- Высокая стоимость модификаций, копирование массива O(N). Плохо при частых записях.
- Читатели не видят свежих данных мгновенно.
23. ConcurrentLinkedQueue - смысл реализации в том, что при вставке в конец, если у потока не получается выполнить CAS, он проверяет не поменялся ли хвост `tail.next != null`, 
и если поменялся то он сам меняет указатель хвоста на актуальную ссылку с помощью CAS, а потом с помощью CAS пробует повторить уже свою операцию. 
Сделано так потому, что поток который поменял tail.next, неизвестно когда обновит ссылку на сам хвост, поэтому типа помогаем ему.
Нельзя хранить null.
24. ConcurrentHashMap - внутри как обычная HashMap, но с важными отличиями:
- массив бакетов и ссылка на следующий элемент являются `volatle` полями, что позволяет отображать мгновенно изменения для всех потоков.
- При вставке используется синхронизация для вставки в непустой бакет, причём замком будет первый элемент бакета. Если бакет пустой, то используется CAS для записи в пустую ячейку.
25. ConcurrentLinkedDeque - в целом реализация похожа на ConcurrentLinkedQueue, с поправкой на то, что можем вставлять/удалять с обоих концов.
26. ConcurrentSkipListMap - потокобезопасная реализация SortedMap. Даёт O(logN) сложность поиска. Основан на SkipList который представляет собой многоуровневый список. 
Для списков и ссылок на ноды используется volatile и CAS, соответственно является lock-free. Нельзя хранить null ни в ключе, ни в значении.
27. ConcurrentSkipListSet - по сути обёртка над ConcurrentSkipListMap, соответственно является lock-free и не разрешает null значения.
