# Память и JVM

### **Как устроена память в JVM?** Heap vs Stack — что где хранится: примитивы, ссылки, объекты. Где лежат локальные переменные метода, где — поля объекта?
Память делится на несколько областей\
**Heap** - общий для всех потоков, хранит все объекты(ссылки в экземпляре, а сами объекты в хиппе, в другом месте), интернированные строки и массивы, живёт от старта JVM до её завершения. Не обязательно одна физическая область. Статические поля тоже лежат в Heap в специальном объекте `Class`, а метаданные класса в Metaspace.\
**Stack** - у каждого потока свой, хранит фрейм вызовов(состоит из Local Variable Array (LVA) который состоит из (this, параметры метода и локальные переменные), стек вычислений(операндов) для байт-кода, ссылка на пул констант класса, Служебная информация).\
размер задаётся `-Xss`\
**PC register** - указатель на адрес текущей инструкции. У каждого потока свой.\
**Native method stack** - хранит вызов нативного кода. У каждого потока свой.
**Metaspace** - общий для всех потоков. Хранит метаданные класов( пулы констант, байткод методов, структура класса, инфа о методах и полях).


### **Metaspace — что это, чем заменил PermGen и как регулируется его размер.**
**Metaspace** - область в native‑памяти для метаданных классов(пул констант, байткод методов, структура класса, инфа о методах и полях). \
Отличия от **PermGen**: 
- **Metaspace** лежит не в heap, а в отдельной области памяти.
- **PermGen** собирался только при Full GC, что вызывало длительные STW-паузы.
- **PermGen** имел фиксированный размер, задаваемый через `-XX:PermSize` и `-XX:MaxPermSize`. Проблема, ибо сложно оценить Количество загружаемых классов в рантайме (динамические прокси, CGLIB, скриптовые движки, hot-redeploy).

**Metaspace** по умолчанию имеет безлимитный размер, но регулируется:
`-XX:MetaspaceSize` - дефолт платформозависимый. значение на котором тригерится GC для освобождения памяти, после чего это значение корректируется автоматом, чтобы небло частого срабатывания GC или отжора памяти большого.
`-XX:MaxMetaspaceSize` - максимальный размер.
`-XX:MinMetaspaceFreeRatio`- 40% по умолчанию, если после GC свободно меньше — Metaspace расширяется.
`-XX:MaxMetaspaceFreeRatio` - 70% по умолчанию, если свободно больше — Metaspace сжимается.

Метаданные класса освобождаются только при выгрузке класса (class unloading), которая происходит только при GC соответствующего classloader'а, соответственно `OutOfMemoryError: Metaspace` почти всегда означает утечку classloader'а, а не нехватку памяти.
**OutOfMemoryError: Metaspace** - Причина — утечка classloader'ов или лавинообразная генерация классов, например:
- с помощью CGLIB
- Hot-redeploy в серверах приложений - каждый редеплой создаёт новый classloader, старый не собирается
- Фреймворки, генерирующие классы под каждый запрос

Диагностика: 
- Трассировка загрузки классов `-XX:+TraceClassLoading`
- jcmd <pid> VM.metaspace # Мониторинг Metaspace

### **GC Roots — что это и почему JVM использует tracing вместо подсчёта ссылок** (reference counting не справляется с циклическими зависимостями).
**GC Roots** - ссылка, с которой GC начинает обход графа объектов. Вчё что достижимо от GC Roots живое, иначе мусор - это основная идея tracing GC.

Что считается **GC Roots**:
- локальные переменные и параметры методов в стеке;
- объекты Thread запущенных потоков;
- статические поля классов;
- ссылки из JNI(нативные методы).
- захваченные мониторные объекты;
- Промежуточные ссылки во время вычислений;
- Объекты, удерживаемые JVM - System ClassLoader, примитивные классы, preallocated exceptions (например, NullPointerException)

**Reference Counting** - каждый объект хранит счётчик ссылок на себя. Если счётчик становится 0, то объект удаляется.
Плюсы:
- Мгновенное освобождение (детерминизм).
- Нет STW-пауз. 
- Прост в реализации
Минусы:
- Не подходит для циклических ссылок.
- Счётчик это общий ресурс, нужно соблюдать Атомарность в многопоточности
- Фрагментация - объекты освобождаются по одному, соответственно heap фрагментируется.

### **Типы ссылок:** Strong, Soft, Weak, Phantom — для чего нужен `ReferenceQueue`, как GC по-разному обходится с каждым типом.
1. `Strong Reference` - ссылки к которым мы привыкли и создаём по умолчанию через оператор `new`.
   Пока есть такая ссылка на объект, сборщик мусора его не удалит, Кроме случаев ссылки в "островах памяти",
   т.е. кто-то на объект ссылается, но связи с корнем у них уже нет, в таком случае ссылка удалится.
2. `Soft Reference` - Объект удаляется при нехватке памяти. Перед выбросом `OutOfMemory` JVM гарантированно почистит такие ссылки,
   чтобы выкроить память и отсрочить `OutOfMemory`. Само собой пока есть связь с корнем объект живёт.
   Если есть несколько ссылок на объект, то побеждает более сильная, т.е. имеет смысл только если Soft единственная ссылка на объект.
   Соответственно, после инициализации Soft Reference, нужно занулить исходную Hard Reference. Обычно используется для кэшей и подобного не важного.
3. `Weak Reference` - объект удаляется при следующем проходе GC, если на объект нет более сильной ссылки.
   Используется в качестве ключа в WeakHashMap. Используется при кешировании без каких либо гарантий, где кэши не должны блокировать удаление, сборку мусора.
   Так же используется для предотвращения утечек при регистрации Listener/Callback - лямбда Listener-а может содержать ссылку на
   объект внутри которого она создавалась(какой-нибудь фрейм), при создании мы передали лямбду Listener-а в кнопку, а кнопки часто лежат в глобальном статическом списке, или поле.
   Соответственно кнопка через лисенер держит от удаления фрейм, соответственно образуется утечка памяти.
   Если используем Weak ссылку и передаём её в лямбду в которой не используются методы и поля this класса, то лямбда не захватывает this неявно,
   соответственно она не будет держать this от сборки GC, у лямбды есть только Weak ссылка.
   Есть и альтернативное предпочтительное решение с использованием WeakHashMap - окно(фрейм) кладём в мапу в качестве ключа, а значением будет слушатель,
   когда твёрдые ссылки на окно удаляться, его и соответствующий лисенер снесут при GC.
   Ещё одна утечка может быть, если окно создаёт поток с бесконечным циклом и новый поток использует this, окно никогда не закроется, т.к. новый поток ссылается на окно. Решается через WeakReference.
4. `PhantomReference` - не даёт доступ к объекту, всегда возвращает null, но позволяет узнать, что объект уже помечен на удаление.
   Почти всегда используется с `ReferenceQueue` - который может быть передан в конструктор ссылки и в который JVM помещает Soft/Weak/Phantom ссылку после уборки.
   `java.lang.ref.Cleaner` (Java 9+) реализован на phantom-ссылках и заменяет finalize()

`ReferenceQueue` - Единственный способ узнать от GC, что объект собран. GC помещает в него ссылку после сборки мусора. Нужно не забывать чистить.
### **Типы утечек памяти** в Java: статические коллекции, ThreadLocal в пуле потоков, незанятые слушатели, кэши без вытеснения — и как их искать через `jstack`, `jmap`, `jstat`, JFR.
- Статические коллекции;
- ThreadLocal в пуле потоков
- Проблема с Лисенерами, описанная в `Weak Reference`
- кэши без вытеснения

**Диагностика**
- `jstat` — растёт ли вообще. мониторинг GC в реальном времени `jstat -gcutil <pid> 1000`. 
Ключевые колонки: `O` (Old generation utilization %), `FGC` (Full GC count), `FGCT` (Full GC time);
`O` растёт монотонно и не падает после Full GC. `FGC` растёт быстро (Full GC каждые минуты вместо часов). `FGCT` увеличивается — GC тратит всё больше времени.
- `jmap` — что растёт. снимок heap и гистограмма. `jmap -histo:live <pid> | head -30`. Показывает, какие классы занимают больше всего памяти. Если ThreadLocalMap$Entry, ваш domain-класс - то проблемка.
- `jstack` — для утечек через потоки. thread dump для `ThreadLocal` и listener'ов. `jstack <pid> > threads.txt`. Искать имена потоков: `http-nio-8080-exec-*`, `ForkJoinPool.commonPool-worker-*`, `pool-*-thread-*` — долгоживущие потоки пула.\
  jstack показывает стек вызовов и locks, но не показывает ссылки на объекты в heap. Для этого нужен heap dump.
- `JFR` - включается в production, overhead < 1%, собирает live set — heap usage после Old Collection

### **JIT-компиляция:** интерпретатор, C1/C2, tiered compilation — как JVM решает, какой код компилировать.
JIT-компиляция это многоуровневая система, где JVM динамически выбирает уровень компиляции для каждого метода на основе собранного профиля выполнения. Код, выполняющийся часто, компилируется агрессивнее и оптимизируется сильнее.
Tiered Compilation состоит из 5-и уровней. Классический путь `0 → 3 → 4`

| Уровень | Исполнитель   | Характеристика                                  |
|---------|---------------|-------------------------------------------------|
| 0       | Интерпретатор | Запускает байт-код, собирает базовую статистику 
| 1       | C1 (Client)   | Быстрая компиляция, малая оптимизация           |
| 2       | C1 (Client)   | Быстрая компиляция, легкая оптимизация          |
| 3       | C1 (Client)   | Быстрая компиляция, полное профилирование       |
| 4       | C2 (Server)   | Медленная компиляция, агрессивная оптимизация   |
`C1 (Client Compiler)`: Быстрый, но генерирует менее оптимальный код. Используется как промежуточный этап для сбора точного профиля
`C2 (Server Compiler)`: Медленный, но генерирует высокооптимизированный код. Использует профиль, собранный на уровне 3, для спекулятивных оптимизаций (инлайнинг, девиртуализация и т.д.)
JVM принимает решение о компиляции базируясь на счетчиках (вызовы метода, итерации циклов) и загруженности компилятора
Классический путь `0 → 3 → 4` - Интерпретатор исполняет и собирает счётчики; при прогреве метод уходит на C1 (tier 3) — там дорабатывается профиль (частоты ветвлений, типы в полиморфных вызовах); данные насытились → C2 (tier 4).\
Выбор между Level 2 и Level 3, а также скорость перехода зависят от загруженности очередей компиляторов.\
Быстрые/тривиальные методы могут прыгать `0 → 1` сразу, без C2, т.к там нечего заоптимизировать.\
Если C1 загружен, JVM может начать собирать профиль прямо в интерпретаторе (Level 0), и е сли профиль будет готов раньше, чем C1 скомпилирует Level 3, метод может сразу уйти в C2 (переход 0 → 4).

- `OSR` — ключевой механизм для горячих циклов. Если метод долго выполняется в интерпретаторе (например, бесконечный while), JVM не ждет окончания метода.\
Она компилирует цикл и заменяет стек на лету, переключая выполнение на скомпилированный код прямо внутри цикла.\
- C2 компилирует код на основе предположений (например, «этот метод всегда вызывается только с одним типом»). Если предположение нарушается, скомпилированный код инвалидируется и JVM откатывается к интерпретатору. После сбора нового профиля метод может быть перекомпилирован. Ошибки в логике предположений могут приводить к циклам перекомпиляции, когда JVM бесконечно компилирует и откатывает один и тот же метод
- Скомпилированный код хранится в Code Cache — области памяти вне heap. Для управления памятью используется Segmented Code Cache (JDK 9+), разделяющий кэш на сегменты для профилированного (C1) и непрофилированного (C2) кода.


### Escape Analysis — какие оптимизации JVM применяет (скалярное замещение, удаление синхронизации, allocation elimination).
Escape Analysis - оптимизация JIT-компилятора (C2), суть которой: на этапе компиляции определить — может ли объект быть доступен из кода вне метода (или вне потока). Если не может, он применяется ряд оптимизаций.

| Состояние        | Значение                                                                                                              |
|------------------|-----------------------------------------------------------------------------------------------------------------------|
| **NoEscape**     | Объект не выходит за пределы метода, не публикуется наружу                                                            |
| **ArgEscape**    | Передаётся как аргумент в другой метод, но не сохраняется в heap/статику                                              |
| **GlobalEscape** | Публикуется глобально: записывается в поле другого объекта, в static, возвращается из метода, попадает в другой поток |
Оптимизации возможны только для `NoEscape`.\
Три ключевые оптимизации:
- **Scalar Replacement** - компилятор раскладывает поля объекта на независимые локальные переменные, полностью устраняя аллокацию объекта в heap. \
Поля объекта «размазываются» по регистрам/LVA, а сам объект исчезает. Это устраняет и аллокацию, и заголовок объекта, и последующую работу GC.
- **Allocation Elimination** - Когда объект скалярно замещён, инструкция new полностью устраняется из скомпилированного кода. Эффект особенно заметен для объектов в циклах которые создаются много раз, промежуточных объектов в Stream API, лямбдах, autoboxing, временных объектов-обёрток;
- **Lock Elision** - Если объект доступен только одному потоку и не убегает в другие потоки, то все synchronized-операции над ним бессмысленны — их можно полностью убрать.

Почему может не работать:
- Зависимость от инлайнинга. Если метод, принимающий ссылку, не заинлайнен, объект считается «убежавшим»
- Слияние потоков управления. Если после if/else невозможно определить, на какой объект указывает ссылка, скалярное замещение не выполняется.
- Временные объекты, живущие между итерациями, обычно скалярно не замещаются.
- Слишком большие методы пропускаются, объекты считаются убежавшими. ~150 байт байт-кода

Флаги:

```
  -XX:+DoEscapeAnalysis        # включён по умолчанию
  -XX:+EliminateAllocations    # скалярное замещение
  -XX:+EliminateLocks          # устранение блокировок
  -XX:+PrintEscapeAnalysis     # диагностический вывод (debug build)
  -XX:+PrintEliminateAllocations
```

### **Off-heap память и DirectByteBuffer** — зачем нужна, где применяется на практике.
**Off-heap память** — это область памяти, выделяемая JVM через нативные вызовы (обычно `Unsafe.allocateMemory` или `ByteBuffer.allocateDirect`), которая находится вне `Java Heap` и не управляется `Garbage Collector`.
- Необходим, чтобы не раздувать heap большими объёмами кэшируемых данных. При росте heap до десятков гигабайт GC-паузы становятся неприемлемыми для latency-sensitive приложений.
- `Off-heap` позволяет использовать всю доступную RAM системы (десятки/сотни ГБ), не ограничиваясь `-Xmx`. Apache Geode/Ignite/Data Grid используют это для кэшей до терабайт на ноду.
- `DirectByteBuffer` позволяет данным напрямую взаимодействовать с сетевыми сокетами и файлами без копирования между heap и native-буферами ОС. `DirectByteBuffer` — стандартный механизм доступа к такой памяти из Java-кода через NIO.
- Off-heap кэши используют меньше памяти на запись, чем on-heap аналоги, за счёт отсутствия заголовков объектов и выравнивания
- Размер ограничен `-XX:MaxDirectMemorySize` и по умолчанию равен `Xmx`. При превышении `OutOfMemoryError: Direct buffer memory`

Применяется в Kafka, Apache Geode, gRPC, HBase

Проблемы:
- off-heap память не собирается GC. Забыли освободить руками - утечка нативной памяти.
- Не виден в heap dump.
- Дорогая аллокация/освобождение, поэтому память не освобождают в прямом смысле, а оставляют зарезервированной т.е. пуллят
- При частых create/update с разными размерами возможна сильная фрагментация (решается slab-аллокацией - аллокация одинаковыми блоками, как в HBase/Geode).
- Дополнительный overhead на доступ: сериализация/десериализация, отсутствие прямого доступа к полям объекта
- для многопоточного доступа ответственность на вас, т.к. нет барьеров памяти.
## Сборщики мусора

### **Serial, Parallel, G1, ZGC, Shenandoah** — отличия, когда какой выбирать.
- Serial GC: Использует один поток, останавливает все приложение ("Stop The World"). Подходит для маленьких приложений (до 100 МБ).
- Parallel GC: Сборщик по умолчанию Java 8. Использует несколько потоков для всех фаз. Нацелен на максимальную пропускную способность (например, для пакетной обработки данных).
- G1 (Garbage First) GC: Java 9 default. Разделяет кучу на множество равных регионов. Определяет, где больше всего мусора, и очищает эти регионы в первую очередь.
  Подходит для больших куч (от 4 ГБ) с требованиями к малому времени задержки. Чуть выше накладные расходы CPU.
- ZGC / Shenandoah: Современные ультранизкозадержечные сборщики, которые выполняют почти всю работу (включая перемещение объектов) параллельно с работой потоков приложения, снижая паузы до минимума (менее 10 мс).
  Выше потребление CPU, чуть ниже throughput по сравнению с Parallel/G1.
- Epsilon GC - вообще не собирает мусор — только выделяет память. Когда память заканчивается, выбрасывает OutOfMemoryError. Использование - тесты производительности, бенчмарки, сценарии с очень коротким жизненным циклом JVM.

### **Кейс из Т-Банка:** «Heap 64 GB, паузы Stop-the-World > 10 мс — что делать?» — переход на ZGC/Shenandoah, тюнинг параметров.
Перед кручением параметров и переключением GC - Проверка — точно ли виноват GC? Может это была деоптимизация, class redefinition или thread dump.\
STW время складывается из `STW = TTS (все Java-потоки должны дойти до safepoint-полла) + собстvenно GC-фаза (root scanning → evacuate/copy → card/RSet-обслуживание) + выход из safepoint.` Может проблема быть и в TTS - проверяется через `-Xlog:safepoint+time`.
Вопросы: какой GC включен? Если 11мс и 11 минут, всё оно > 10мс. На 64Г хипа немного больше 10мс это отличный результат для G1, но скорее всего 10мс это не Full GC, или уже на ZGC.

Что делаем по итогу: 
- смотрим логи GC - `-Xlog:gc*,gc+phases=debug,safepoint,time,uptime:file=...` и  JMC - «GC Pause Times», «Time to Safepoint», «Evacuation Failure», «Object Allocation in New/Outside TLAB», «Object Count After GC».
- Смотрим: доля времени в STW, частота, длительность, причина(G1 Evacuation Pause (young), G1 Evacuation Pause (mixed), Remark, Cleanup, Full GC?)
- Full GC в логе? Тогда ищем причину: утечка или Humongous allocations( объекты > 50% размера региона) часто тригерят GC.
- в k8s может быть лимит по CPU, 8 потоков сборки мусора могут тупить на 1-2 CPU.
- И отдельно ставлю вопрос: не нужно ли заменить одну JVM на 64 ГБ на две по 32 — для latency-сервиса это обычно выгоднее любого тюнинга.
- Пробуем ZGC, даёт sub-ms паузы независимо от размера кучи, но стоит памяти/CPU

Антипаттерны: 
- Тупо ставить `MaxGCPauseMillis=5` как решение - сборки будут чаще, пропускная способность меньше для G1 с таким к-вом памяти.
- `jmap -dump` - дамп это многосекундная пауза + риск добить остатки памяти.
- увеличить heap, чтобы сборка была реже. В реальности сборка будет реже, но ещё дольше.
- Миграция на ZGC без замера footprint и без метрик allocation stalls.
- Считать, что все STW-паузы это GC. Не-GC safepoint (JVMTI-агент, redefinition, класс-лоадинг, длинный цикл) выглядит в мониторе один-в-один.

# **Параметры GC:** `MaxGCPauseMillis`, `G1HeapRegionSize`, `ConcGCThreads` — как влияют на поведение?
1. `MaxGCPauseMillis` - рекомендация и ориентир для GC на максимальное время STW. У GC есть оценки стоимости на каждый регион, из чего он может высчитать сколько регионов он может убрать за отведённое время.\
young-сборка собирает все young-регионы, частично их обработать нельзя.
При уменьшении значения, уменьшается размер young регионов и время сборки, но увеличивается частота сборки, общая пропускная способность падает.\
Флаг не влияет на Full GC. В `ZGC` отсутствует, сборщик спроектирован на минимальные задержки и регулируют число воркеров.
2. `G1HeapRegionSize` - размер региона от 1 до 32 степенями двойки. Дефолт высчитывается из размера Heap, чтобы в итоге получилось около 2048 регионов.
Чем больше регион, тем дольше сборка в регионе. Чем меньше, теб больше объектов считается Humongous, Humongous объекты релоцируются сразу в old поколение и если регионы маленькие, а объекты большие получаем сильную фрагментацию и риск Full GC даже на свободной памяти.
`Практический кейс: в одном из обсуждений G1 увеличение региона с 4 МБ до 8 МБ убрало многомиллисекундные паузы, вызванные humongous-объектами`
3. `ConcGCThreads` - максимум параллельных потоков GC конкурентных фаз (marking, evacuation-подготовка). В STW-фазе эти потоки не участвуют: там работает `ParallelGCThreads`.\
Дефолт(и для ZGC): `ParallelGCThreads / 4`, т.е. при 4-х потоках `ConcGCThreads = 1` и это Проблема встречающаяся на `PROD` на больших кучах - одному потоку сложно перебрать 64 гига, особенно когда приложение продолжает выделять память под новые объекты соответственно растёт вероятность Full GC.\
С другой если `ConcGCThreads` равен всем ядрам, то потоки GC воруют процессорное время у потоков приложения.
**Практика:** поднимаем, если в логах видим warnings вида `Timing ratio` / concurrent-фазы «не поспевают» (Failure To Keep Up). На контейнерах проверяем, что JVM видит реальные лимиты CPU (`-XX:ActiveProcessorCount`)

## Java Memory Model (JMM)

### **Что такое happens-before?** Полный список источников: действия в одном потоке, выход из монитора → вход в него, запись volatile → чтение, `Thread.start()` → действия в потоке, `join()`.
`happens-before` - частичный порядок между действий, определяющий гарантии видимости переменных в памяти. Частичный имеется ввиду, который выполняется не всегда, а только когда это необходимо.
Если между действиями нет happens-before и они обращаются к одной переменной хотя бы одно из действий — запись, возникает data race, и результат не определён (можно увидеть любое значение, включая «невозможные»)
Источники `happens-before`:
1. **Программный порядок** -  Любое действие раньше по тексту happens-before любому позже в том же потоке.
2. **Мониторы** - _unlock_ монитора happens-before каждого последующего _lock_.
3. **Volatile** - Запись _volatile_-поля happens-before каждого последующего чтения того же поля.
4. **Thread.start()** - Каждое действие до вызова `start()` happens-before все действия запущенного потока.
5. **Завершение потока** - Тело потока happens-before _join()_ потока, либо получения false от _isAlive()_.
6. **Прерывание** - Вызов `interrupt()` в потоке A happens-before первому действию B, в котором B заметил прерывание (`isInterrupted()`, проброс `InterruptedException`).
7. **Final-поля и freeze** - Запись каждого final-поля happens-before действия freeze в конце конструктора. Утечка this из конструктора нарушает гарантию.
8. **finalize()** - Конструктор happens-before началу финалайзера. Финализация с JDK 18 помечена deprecated for removal.
9. **Инициализация по умолчанию** - Запись дефолтного значения в поле `happens-before` записи любого другого значения в это же поле. Гарантирует, что «нулевая инициализация» всегда видима — с ней нельзя увидеть «мусор» вместо нуля.
10. **Transitivity Rule** — транзитивность. Если `A hb B` и `B hb C`, то `A hb C`.

Практические использование:
1. Двойная проверка блокировки - поле ссылки обязано быть _volatile_, иначе читатель может получить ссылку на объект, где конструктор ещё не завершился.

Антипаттерны:
1. Называть happens-before «временем». Это отношение видимости и порядка, оно не обязано совпадать с порядком на часах.
2. Утверждать, что «гарантировано переупорядочивание, если нет happens-before». Спецификация снимает гарантию, а не добавляет запрет.
3. Утверждать, что при hb нет переупорядочивания. JMM разрешает любые переупорядочивания, не приводящие к наблюдаемому нарушению hb.
4. Считать, что final сам по себе безопасен при утечке this из конструктора.
5. Путать **volatile** с атомарностью составных операций и с защитой состояния объекта.
6. synchronized на разных объектах — правило «unlock → lock» не срабатывает, видимости нет.
7. Double-checked locking без volatile

### **volatile vs synchronized:** volatile даёт видимость, но НЕ атомарность. Почему `i++` с `volatile` — гонка данных (read-increment-write = три такта).
- **volatile** даёт видимость и запрет переупорядочиваний вокруг одного поля, но не даёт атомарности составных операций.\
- **synchronized** даёт видимость через acquire/release-семантику монитора, и атомарность блока кода целиком — «никто другой не находится внутри того же блока одновременно.\
- `volatile int i; i++;` — это классическая гонка. Операция `i++` состоит из трёх шагов: прочитать, прибавить, записать и между ними нет гарантии непрерывности.\
- если в volatile-поле кладётся ссылка на мутабельный объект, `volatile` гарантирует только видимость самой ссылки.
- `volatile` не означает игнорирование кэша и всегда чтение из ОЗУ, всё сложнее и реализовано через протокол когерентности (MESI).
- volatile-запись «дороже» обычной
- всё, что было записано до volatile-записи, тоже становится видимым - паттерн называется «публикация через volatile».

### **ordering, visibility, atomicity** — три кита JMM, что гарантирует каждая из гарантий.

1. **Atomicity** - Действие атомарно, если оно наблюдается как неделимое — либо выполнено целиком, либо не выполнено
   вовсе. Другие потоки не видят промежуточных состояний.
   Одиночные чтения и записи примитивов гарантированно атомарны на аппаратном уровне.\
   Запись ссылки атомарна по определению.
2. **Visibility** - Запись, сделанная одним потоком, становится видимой другому потоку при наличии отношения
   happens-before между ними.
3. **Ordering** - Порядок выполнения действий, наблюдаемый другими потоками, соответствует happens-before. Если A hb B,
   то никакой поток не увидит B раньше A.

Можно получить одну гарантию без других:
- **Atomicity без visibility**: `AtomicInteger.lazySet()` — запись атомарна, но без немедленной видимости.
- **Visibility без atomicity**: `volatile-флаг` — видим, но i++ на нём не атомарен.
- **Ordering без atomicity**: ``VarHandle.acquireFence()`` — упорядочивает, но не защищает RMW.

Типы барьеров:
- LoadLoad - Переупорядочивание двух чтений
- StoreStore - Переупорядочивание двух записей
- LoadStore	- Чтение перед записью
- StoreLoad	- Запись перед последующим чтением (самый дорогой)

## Locks и синхронизация

### **ReentrantLock vs synchronized:** когда выбирать `ReentrantLock` — `lockInterruptibly()`, `tryLock` с таймаутом, fairness policy.
**ReentrantLock** тоже что и **synchronized** с некоторыми дополнительными плюшками.

Когда **ReentrantLock**:
- Если нужно отпустить лок по таймауту.
- Нужна неблокирующая попытка захвата (tryLock())
- Если поток ожидающий блокировку должен быть прерван, то `lockInterruptibly()` вместо `lock()`.
- нужна гарантия, что самый долго ждущий поток получит блокировку следующим. `new ReentrantLock(true)`
- Метрики и диагностика блокировок (isLocked(), getQueueLength(), getHoldCount()).
- Блокировку нужно захватить в одном методе, а освободить в другом

Антипаттерны **ReentrantLock**
- заменять **synchronized** на **ReentrantLock** «ради скорости(спорно)»
- Считать **lock()** прерываемым. Он не прерываемый
- **unlock()** внутри **try**, а не перед try
- всегда ставить fair=true
- Смешивать **synchronized** и **ReentrantLock** для защиты одного состояния — два разных механизма, ни один не даёт гарантий относительно другого.

Проблемы **ReentrantLock**:
- блокировку нужно снимать руками через вызов `unlock()`.


### **ReadWriteLock / StampedLock** — когда чтений много больше записей, оптимистичные чтения в `StampedLock`.
1. ReentrantReadWriteLock - Предоставляет по сути два замка, на чтение и на запись.
- Под замки на чтение могут проходить все кто хочет, если в этот момент нет записи.
- Под замок на запись может попасть только один поток, при этом все чтения блокируются.
- Нельзя повысить уровень автоматически, не освободив чтение перед этим.
- При повышении уровня блокировки, между освобождением read и захватом write может вклиниться другой поток и захватить замок первым.
- Пример паттерна проверь-и-обнови (Check-Then-Act):
  writeLock.lock();
  // ... write smth
  readLock.lock();
  // ...
  writeLock.unlock();
  // ... // read something
  readLock.unlock();
  Используется для того, чтобы прочитать только что записанные данные. Например, при валидации консистентности записанного тяжёлого объекта, чтобы не блочить других читателей, или при чтении сложного состояния и его отправки по сети.
- Если Десять потоков взяли блокировку на чтение и одинадцатый поток хочет взять блокировку на запись в другом месте, но на этом же объекте ReentrantReadWriteLock, Он будет ждать пока не закончат чтение 11 потоков. Для решения проблемы голодания писателей есть параметр в конструкторе `fair`, чтобы всем потокам доставалось времени поровну.
2. StampedLock - гибкий и производительный подход к блокировке.
- Можно использовать как обычный ReentrantReadWriteLock(но без реэнтерабельности).
- Основной смысл в оптимистичной блокировке, берём штамп(состояние блокировки на момент захвата), читаем значение и проверяем бралась ли за это время блокировка. Если нет, то возвращаем прочитанное значение, если да то берём настоящий readLock и читаем под ним.
- Хорош при частом чтении и небольшом количестве записей.
- Также позволяет перейти от readLock к writeLock, в отличие от ReentrantReadWriteLock.
- В отличие от ReentrantReadWriteLock, не поддерживает wait/notify‑подобную семантику(Condition). Методы readLock(), writeLock() и tryOptimisticRead() класса StampedLock не проверяют флаг прерывания во время ожидания,
  Т.е. если внешний поток попытается прервать выполнение текущего в момент ожидания блокировки, то ничего не произойдёт, метод продолжит выполнение.
- StampedLock не поддерживает реентерабельность между режимами чтения и записи в одном потоке. Если вы уже удерживаете readLock, вы не можете просто вызвать writeLock().
  Вы должны сначала освободить readLock (unlockRead), а затем захватить writeLock, иначе можно словить Deadlock т.к. нет реинтерабельности, а тот самый поток который захватил чтение, внутри защищённого блока пытается захватить запись, что не удасться из-за уже существующей блокировки на чтение.
- StampedLock не поддерживает политику справедливости как ReentrantReadWriteLock, но есть внутренние механизмы отдающие приоритет читателям, а если появляются долго ожидающие писатели то акцент(приоритет) смещается в их сторону, но без всяких гарантий.

Пример оптимистичного чтения:
```
    public double distanceFromOrigin() {
    long stamp = lock.tryOptimisticRead(); // берём штамп перед попыткой оптимистичного чтения 
    double currentX = x, currentY = y;       // непосредственно чтение

        // Проверяем, не было ли изменений с момента получения штампа
        if (!lock.validate(stamp)) {
            stamp = lock.readLock(); // Если были изменения, берем блокировку
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.sqrt(currentX * currentX + currentY * currentY);
    }

```
Также предоставляет возможность перехода от readLock к writeLock




### **deadlock, livelock, starvation** — чем отличаются, как избежать (упорядочение блокировок, `tryLock` с таймаутом).
1. **Deadlock** - Два или более потока навсегда заблокированы, ожидая ресурсы, которые заняты друг другом.\
**Deadlock возникает только если одновременно:**
- Mutual exclusion — ресурс держит только один поток.
- Hold and wait — поток держит один ресурс и ждёт другой.
- No preemption — ресурс нельзя отобрать силой.
- Circular wait — цикл в графе ожиданий.

Пример:

```
class Account {
private final Object lock = new Object();

    void transfer(Account to, int amount) {
        synchronized (this.lock) {         // A
            synchronized (to.lock) {       // B
                // ...
            }
        }
    }
}

// Поток 1: a.transfer(b) → держит a, ждёт b
// Поток 2: b.transfer(a) → держит b, ждёт a
// DEADLOCK
```
Способы избежать: 
- захват блокировок всегда в одном порядке.(Устраняет circular wait — четвёртое условие Коффмана.)
- **tryLock** с таймаутом чтобы не ждать вечно (hold and wait — поток отпускает первый лок, если не получил второй)
- Один глобальный лок, что грубо, но надёжно: вместо N локов — один. Устраняет circular wait и hold-and-wait сразу. Минус один — падает параллелизм.
- **Lock-free** структуры. **AtomicInteger**, **ConcurrentHashMap**, **VarHandle.compareAndSet** — вообще без блокировок. Устраняет mutual exclusion.
- `lockInterruptibly` — поток можно прервать и разобрать зависание снаружи.

Обнаружение:
- `jstack <pid>` — покажет `Found one Java-level deadlock`
- Програмная детекция `ThreadMXBean.findDeadlockedThreads()`
2. **Livelock** - Потоки не заблокированы, они активно работают, меняют состояние, но не продвигаются к результату.
Пример: 
- A и B одновременно столкнулись на tryLock, оба вежливо уступили, оба снова попробовали — снова столкнулись. И так по кругу.
- один откатывает транзакцию, второй тут же перезапускает её

Способы избежать:
- Рандомизация/экспоненциальный backoff при ретраях
- общий счётчик попыток — после N ретраев один поток «уступает дорогу» детерминированно.

Отличие от deadlock: в livelock CPU оспользуется - потоки активны, в deadlock — спят. Но в обоих прогресса ноль.
3. **Starvation** - поток работоспособен, но планировщик/GC/другие потоки не дают ему исполниться или получить ресурс — неопределённо долго.
Причины:
- non-fair lock может «переходить» одному и тому же потоку, пока новый стоит в очереди. 
- ???писатели не отпускают лок — читатель в **ReentrantReadWriteLock** без fair-режима может ждать вечно.
- очередь задач неограниченна, долгие задачи не пускают короткие.
- Затянутые GC-паузы — все потоки ждут GC.

Способы избежать:
- Fair-лок
- мелкие критические секции, не держать лок во время I/O.

Способы избежать:
- использовать политику справедливости


### **ABA-проблема:** значение сменилось A → B → A, CAS не замечает. Решение — `AtomicStampedReference`.
`AtomicStampedReference`- Добавляет к значению целочисленную версию, которая увеличивается при каждом изменении. CAS проверяет и значение, и версию. Версия это int, он может переполниться после 2^31 изменений.\
К тому же в нём Двойной CAS (значение + stamp). Так же можно попробовать Не использовать lock-free структуры для избегания АВА.

Когда ABA реально опасна:
- Lock-free стеки/очереди — классика. 
- Счётчики с инкрементом/декрементом — если важен факт изменения, а не только значение. 
- Финансовые транзакции — баланс 100 → 200 → 100, но операции были.
- State machines — переход состояния A → B → A логически означает другое состояние.

Когда ABA безопасна:
- Чистые счётчики: если интересует только текущее значение. 
- Кэши: важно текущее содержимое, не история.

Как поймать ABA:
- Стресс-тесты с высокой конкуренцией (JCStress).
- Инварианты: проверка, что структура не повреждена (например, top.next != null для непустого стека)


### **Потокобезопасный счётчик** — выбрать `AtomicInteger` vs `synchronized` vs `LongAdder` и обосновать выбор через уровень конкуренции.

## CAS и атомарные классы

### **AtomicInteger, AtomicLong, LongAdder** — как работает CAS (compare-and-swap) без блокировок, чем `LongAdder` лучше при высокой конкуренции (контурные ячейки вместо одного значения).
`LongAdder` быстрее, т.к. каждый поток инкрементит свой счётчик, которые суммируются при вызове `sum()`.
Нюансы:
- `Cell[]` в `LongAdder` выровнен по cache line (обычно 64 байта), чтобы соседние ячейки не попадали в одну линию, иначе два потока, инкрементящие разные cells в одной cache line, будут «драться» за линию.
- Если `sum()` вызывается часто (например, каждую секунду для метрик), а add — миллионы раз в секунду, `sum()` даёт несогласованный snapshot. Для метрик это обычно приемлемо, но для финансов — нет.
- Contention — главный враг CAS: одна кэш-линия мигает между ядрами, ретраи растут с числом потоков.

`LongAccumulator` принимает произвольную функцию для свёртки, например которая получает максимальное значение, или произведение.

### **AtomicReference, AtomicStampedReference** — для чего применяются(Lock-free структуры данных).
`AtomicReference<T>` - обёртка над volatile-ссылкой на объект, дающая атомарные операции над ней: через CAS. Позволяет строить lock-free структуры без блокировок.\
Ключевой метод **updateAndGet**. Имеется проблема ABA, т.к. нет версии. Функция в **updateAndGet** может вызваться несколько раз при retry. Она должна быть чистой — без side effects.
`AtomicStampedReference` имеет версию, в отличие от `AtomicReference<T>`. Не решает «глубокий» ABA. Если объект mutable и его поля изменились без замены ссылки, stamp не поможет — нужно делать объект immutable или использовать другие техники.
`AtomicReference` безопасен, если объект immutable. Если mutable — CAS на ссылку не защитит от изменения полей.

## ExecutorService и пулы потоков
### **Виды пулов** в `Executors`: `newFixedThreadPool`, `newCachedThreadPool`, `newSingleThreadExecutor`, `newScheduledThreadPool` — внутреннее устройство, отличия.
Все четыре фабрики из `Executors` — это просто предустановленные конфигурации одного и того же базового класса `ThreadPoolExecutor`. Отличия сводятся к трём параметрам: corePoolSize, maximumPoolSize и типу workQueue

| **Фабрика**                  | 	**corePoolSize**	         | **maximumPoolSize**         | 	**workQueue**                         | 	**keepAliveTime** | 
|------------------------------|----------------------------|-----------------------------|----------------------------------------|--------------------|
| **newFixedThreadPool**       | 	nThreads(параметр метода) | 	nThreads (параметр метода) | 	LinkedBlockingQueue (неограниченная)  | 	0                 |
| **newCachedThreadPool**      | 	0	                        | Integer.MAX_VALUE           | 	SynchronousQueue	                     | 60 сек             |
| **newSingleThreadExecutor**	 | 1                          | 	1                          | 	LinkedBlockingQueue (неограниченная)	 | 0                  |
| **newScheduledThreadPool**   | 	corePoolSize	             | Integer.MAX_VALUE           | 	DelayedWorkQueue	                     | 0                  |

1. `newFixedThreadPool` - Предсказуемое потребление ресурсов и задачи не теряются. Но можно потратить всю память бесконечной очередью.
2. `newCachedThreadPool` - Хорош для коротких быстрых задач. Но при большом количестве медленных задач создаётся очень много потоков с риском `OutOfMemoryError: unable to create native thread`
3. `newSingleThreadExecutor` - Гарантия последовательности, задачи не выполняются параллельно друг другу. Низкая пропускная способность и неограниченный рост очереди. 
4. `newScheduledThreadPool` - задачи после завершения помещаются обратно в очередь с новым временем.
`setContinueExistingPeriodicTasksAfterShutdownPolicy` - продолжать задачи после `shutdown()`.
   `setExecuteExistingDelayedTasksAfterShutdownPolicy` - выполнять ли отложенные задачи после `shutdown()`;
`scheduleWithFixedDelay` - фиксированная пауза между завершениями задач.
`scheduleAtFixedRate` запуск через каждый период, если задача выполнялась дольше периода, то она сразу повторяется после завершения.

Нюансы:
- осторожно с готовыми фабриками, т.к. можно получить ООМ из-за бесконечной очереди у `newFixedThreadPool` и `newSingleThreadExecutor`, или ООМ из-за бесконтрольного роста потоков у `newCachedThreadPool`.\
Лучше создавать кстомный `ThreadPoolExecutor` с `ArrayBlockingQueue`, осмысленным `RejectedExecutionHandler` и нормальным названием потока через `threadFactory`.
- Порядок выполнения в `ThreadPoolExecutor`: сначала заполняются core-потоки **→** потом очередь **→** потом создаются потоки до **maximumPoolSize** **→** потом **rejection**.
- Из предыдущего пункта следует, что при бесконечной очереди `maximumPoolSize` не имеет смысла.
- Лучше использовать виртуальные потоки в IO задачах, т.к. они не ограничены размером пула и не блочат платформенный поток.
- у `newCachedThreadPool` необработанное исключение в повторяющейся задаче в тихую игнорит дальнейшие запуски — задачи обязательно оборачивать в try/catch.
- `shutdownNow()` возвращает невыполненные задачи списком из `awaitTermination/shutdownNow()`
- `LinkedBlockingQueue` имеет два lock'а (`put` и `take`) — в отличие от `ArrayBlockingQueue` с одним. Это даёт лучший **throughput** при высокой конкуренции, но не решает проблему переполнения.

Политики `RejectedExecutionHandler` при достижении максимума потоков и заполнености очереди:
- `AbortPolicy` - бросается `RejectedExecutionException` исключение. стоит по умолчанию.
- `CallerRunsPolicy` - задача выполняется в потоке отправителя, что даёт естественный backpressure: продюсер сам начинает тормозить.
- `DiscardPolicy` - молча выбросит новую задачу.
- `DiscardOldestPolicy` выбросит старейшую задачу, а новую поставит на её место.
- Кастомные политики, например `AbortPolicy` с ретраем.

### **Что будет, если очередь переполнится** в `ThreadPoolExecutor`? — политики: `AbortPolicy`, `CallerRunsPolicy`, `DiscardPolicy`, `DiscardOldestPolicy`.
Политики `RejectedExecutionHandler` при достижении максимума потоков и заполнености очереди:
- `AbortPolicy` - бросается `RejectedExecutionException` исключение. стоит по умолчанию.
- `CallerRunsPolicy` - задача выполняется в потоке отправителя, что даёт естественный backpressure: продюсер сам начинает тормозить.
- `DiscardPolicy` - молча выбросит новую задачу.
- `DiscardOldestPolicy` выбросит старейшую задачу, а новую поставит на её место.
- Кастомные политики, например `AbortPolicy` с ретраем.

### **Почему `Executors.newFixedThreadPool` с unbounded queue — плохая идея** в проде?
1. Очередь никогда не переполнится, соответственно политика `RejectedExecutionHandler` никогда не выполнится.
2. Если пул обрабатывает задачи медленнее чем принимает, задержка между получением задачи и её обработкой становится всё больше и больше. Если задача пролежит в очереди слишком долго, она может больше не пригодится.
3. Если очередь растёт, то рано или поздно получим `OutOfMemoryError`.
4. ????Если через пул идут `submit(Callable)` (а не `execute(Runnable)`), Каждая задача обёрнута в `FutureTask` которая держит ссылку не только на результат, но и на вызы

Как правильно:
- Ограниченная очередь `ArrayBlockingQueue`
- Мониторинг `getQueue().size()`, `getActiveCount()`
- Разделение пулов по типам задач: CPU-bound - **corePoolSize = CPU count**, очередь небольшая. **I/O-bound** - больше потоков, отдельный пул, свои таймауты.
- Даже с ограниченной очередью задача может «зависнуть». `Future.get(timeout)` или `CompletableFuture.orTimeout()` — обязательны для внешних вызовов.
- Для I/O-bound задач `Executors.newVirtualThreadPerTaskExecutor()`

## Синхронизаторы

### CountDownLatch vs CyclicBarrier — в чём принципиальная разница (одноразовый vs многоразовый, срабатывание по счётчику vs по числу потоков).
1. `CountDownLatch` - инициализируется числом **N**. Потоки, вызывающие `await()`, блокируются, пока счётчик не достигнет нуля. Любой поток (не обязательно участник) может вызвать `countDown()`, уменьшая счётчик.
**Ключевые свойства**:
- `countDown()` можно вызвать из любого потока — не обязательно из «участника». Это «счётчик завершений».
- `await()` можно вызвать из нескольких потоков — все они проснутся при достижении нуля.
- Нет действия на барьере — после срабатывания ничего дополнительно не выполняется.

**Применение**:
- одновременный запуск всех задач и их ожидание
2. `CyclicBarrier` - инициализируется к-вом участников. Поток, вызывающий `await()`, блокируется, пока все участники не вызовут `await()`. Когда все пришли — барьер открывается, и все потоки одновременно продолжают выполнение.
**Ключевые свойства**:
- Только участники вызывают `await()`(т.к. вызывающий поток блокируется).
- Многоразовый. После срабатывания барьер автоматически сбрасывается и готов к следующему циклу
- Барьерное действие (Runnable) — выполняется один раз при пересечении барьера последним пришедшим потоком, но до того, как остальные проснутся.
- Поломка барьера. Если один поток упал с исключением, был прерван или вышел по таймауту — барьер ломается для всех. Остальные получают BrokenBarrierException.
- `reset()` — можно сбросить вручную. Если кто-то ждёт — получит `BrokenBarrierException`.

**Применение**:
- Многофазные вычисления: все потоки завершают фазу → синхронизация → следующая фаза.
- Итеративные алгоритмы (например, симуляции, game loop, численные методы): каждый шаг — барьер.
- Параллельные тесты, где нужно, чтобы все потоки стартовали строго одновременно (часто в паре с **CountDownLatch** для старта).

### **Semaphore, Exchanger, Phaser** — для каких сценариев.
1. `Semaphore` является по сути свой блоком синхронизации под который могут пройти указанное количество потоков.

Использование:
- для ограничения параллелизма.
- Rate limiting / throttling

Нюансы:
- Есть `tryAcquire`, если лимит исчерпан — можно сразу сделать «fallback» вместо ожидания.
- `release()` без `acquire()` легален и увеличивает permits сверх начального — можно «перелить» семафор. Не баг, но источник ошибок.
- Не заменяет `Lock` — нет reentrancy, нет `ownership`. `release()` из другого потока — норма.
- забытый `release()` в `finally` → вечная блокировка. Всегда `try/finally`.
- **Fair/non-fair** — как у `ReentrantLock`; fair гарантирует FIFO выдачу.
- `acquire(n)/release(n)` — блокировки можно брать пачками.

2. `Exchanger` позволяет двум потокам обменяться данными при вызове метода exchange.
   
Ключевые свойства:
- потоки должны вызывать `exchange()` парами. Если один вызвал, а второй — нет, первый ждёт.
- можно использовать `exchange(value, timeout, unit)`  с таймаутом.
- `exchange()` реагирует на `interrupt()`
- Атомарный swap
- Можно использовать повторно

Применение:
-  двойная буферизация - **producer** заполняет буфер, **consumer** читает. Вместо копирования — обмен буферами. Пока **consumer** читает один, **producer** заполняет другой.
```java
// Producer
Buffer current = new Buffer();
while (running) {
    fill(current);
    current = exchanger.exchange(current);  // мгновенный обмен
}

// Consumer
Buffer current = null;
while (running) {
    current = exchanger.exchange(current);  // получает заполненный
    process(current);
}
```
- **Pipeline-обработка** с двумя стадиями - Stage A обрабатывает, Stage B — следующую. Exchanger передаёт батч между ними без промежуточной очереди.
- Генетические алгоритмы: Два потока обмениваются «популяциями» для скрещивания — классический пример из javadoc Exchanger.
- Тестирование - Синхронизация двух потоков в тесте: оба дошли до точки — обменялись маркерами.

3. `Phaser` - обобщение возможностей `CountDownLatch` и `CyclicBarrier`

Свойства:
- Как CyclicBarrier — многоразовый, с фазами.
- Каждая стадия — фаза. Потоки могут присоединяться/выходить между стадиями.
- Динамическое число участников — `register()` / `deregister()`.
- можно строить дерево фазеров для масштабирования.
- Фазы нумеруются (0, 1, 2, ...). `arriveAndAwaitAdvance()` возвращает номер следующей фазы.

Применение:
- Многофазные вычисления с переменным числом потоков
- Итеративные алгоритмы с изменяющимся числом участников, Симуляции, где одни агенты «умирают», другие «рождаются».
- Тесты и бенчмарки с переменным числом потоков

Нюансы:
- Есть и нестрогий режим: `arrive()` без ожидания — «я пришёл, но ждать не буду».
- Терминация через `onAdvance` — удобно для «выполнять, пока есть работа».
- `awaitAdvance(phase)` — можно ждать фазу, не будучи участником. Полезно для координатора.
- Не блокирует, если фаза уже прошла — возвращается немедленно. Это защита от гонок.
- Заменяет `CountDownLatch` + `CyclicBarrier` — в новом коде, где нужна гибкость, `Phaser` предпочтительнее.

### **CompletableFuture** — построение цепочек асинхронных задач, обработка ошибок, комбинирование результатов.
`CompletableFuture` это реализация **Future** и **CompletionStage** из Java 8, предназначенная для построения асинхронных конвейеров. Позволяет навешивать колбэки — код исполняется по завершении, без ручного ожидания.
Нюансы:
- методы с суффиксом **Async** (например, `thenApplyAsync`) выполняются в отдельном потоке (по умолчанию в `ForkJoinPool.commonPool()`), в то время как их аналоги без суффикса могут выполниться в потоке, который завершил предыдущую задачу.
- Если в цепочке возникает исключение, оно распространяется дальше, и все последующие `thenApply` игнорируются, пока не встретится обработчик.
- Никогда не используйте методы ***Async** без явного `Executor`. По умолчанию они используют ForkJoinPool.commonPool(), который имеет фиксированный размер (обычно количество ядер CPU - 1) и неограниченную очередь.
- Если стартовали как `runAsync`(без возврата результата) без `whenComplete` ошибка будет молча потеряна. Всегда завершайте цепочку обработчиком.
- Non-daemon потоки по умолчанию — приложения не завершатся, пока не закончатся CF
- Правила гигиены: свой executor для I/O, не блокироваться внутри CF, всегда закрывать цепочку обработчиком ошибок.

Методы(аналогично с суффиксом `async`):
- `thenApply` преобразует результат от предыдущего шага.
- `thenAccept` если нужно сделать что-то без возврата значения.
- `thenRun` если действие не зависит от результата предыдущего шага.
- `exceptionally` вызывается если предыдущая задача завершилась исключением, позволяет вернуть запасное/дефолтное значение.
- `handle` Вызывается всегда (и при успехе, и при ошибке) и получает на вход либо результат, либо исключение. Позволяет трансформировать результат или восстановиться после ошибки.
- `whenComplete` выполняет действие при любом исходе, но не меняет результат и не обрабатывает исключение, просто пробрасывает дальше.
- `thenCombine`  Объединяет результаты двух независимых `CompletableFuture`, когда оба завершатся, с помощью `BiFunction`.
- `allOf` Возвращает `CompletableFuture<Void>`, который завершается, когда завершатся все переданные `future`. Результаты нужно извлекать вручную, например, через `join()` внутри `thenRun`.
- `anyOf`: Возвращает `CompletableFuture<Object>`, который завершается, когда завершится самый быстрый из переданных `future`.

## ThreadLocal и виртуальные потоки

### **ThreadLocal** — для чего нужен, какие подводные камни (утечки при использовании с пулами потоков — потоки не умирают, значения не очищаются).
`ThreadLocal<T>` — механизм, дающий каждому потоку свою независимую копию значения. Один и тот же `ThreadLocal`-объект в разных потоках возвращает разные значения.

Использование:
- для Не-потокобезопасных объектов без синхронизации: прост создаём по экземпляру на поток. `static final ThreadLocal<SimpleDateFormat> SDF = ThreadLocal.withInitial(() -> new SimpleDateFormat("..."));`\ В современном мире мало актуально, т.к появились потокобезопастные аналоги.
- В веб-приложениях — передача **SecurityContext**, **TransactionContext**, **MDC**, **RequestContext** без протаскивания через все методы.
- Кэши, буферы для парсинга, временные структуры — чтобы не аллоцировать каждый раз. `private static final ThreadLocal<byte[]> BUFFER = ThreadLocal.withInitial(() -> new byte[8192]);`
- **Spring** хранит **Connection/EntityManager** в `ThreadLocal` — отсюда `@Transactional` работает без явной передачи контекста.

Опастности:
- Утечка памяти: если не подчищать за собой при завершении работы в потоке, значение остаётся привязанным к нему на всё время жизни потока.
- Утечка данных: опять же, если не подчищать за собой, поток может перейти в пользование другой задаче и всё что мы насохраняли будет видно ей с неопределёнными последствиями.
- **Фантомные Entry** с `key = null`: `ThreadLocalMap` ключ это **weak reference** на `ThreadLocal`, а значение — **strong reference**. Если на `ThreadLocal` нет сильных ссылок GC очищает weak-ключ → `key = null`, но значение при этом остаётся в `ThreadLocalMap`.
- значения `InheritableThreadLocal` наследуются в дочерних потоках, соответственно могут жрать кучу памяти при хранении тяжёлых объектов. Актуально и для обычного `ThreadLocal` созданного через `withInitial`;
- Невидимая связь между компонентами, `ThreadLocal` по сути глобальная переменная в рамках потока.
- `CompletableFuture`, `ExecutorService`, реактивные потоки (Reactor, RxJava): задача выполняется в другом потоке, а там `ThreadLocal` пуст. Можно разрулить через `ScopedValue` в качестве замены.
- Виртуальных потоков могут быть миллионы. Каждый имеет свой `ThreadLocalMap` → миллионы map'ов → огромный расход памяти.

Правила использования:
- Всегда подчищать в `finally`. Без исключений.
- ThreadLocal должен быть статическим полем, не экземплярным. Иначе каждый экземпляр — свой ThreadLocal, что бессмысленно и ведёт к утечкам.
- Не хранить большие объекты надолго — только на время операции.
- Не использовать для бизнес-логики — только для cross-cutting (security, transaction, logging).
- Документировать — если ThreadLocal часть API, явно описать lifecycle.
- В асинхронном коде — явно передавать контекст или использовать `TransmittableThreadLocal`/`ScopedValue`.
- Мониторинг — если подозреваете утечку, ищите в heap dump ThreadLocalMap$Entry с **key = null, value != null**

### **Daemon-потоки** — что это, чем отличаются от обычных, примеры (GC работает как daemon).
**Daemon-поток** — это поток, который не удерживает **JVM** от завершения. Когда все не-daemon потоки завершились, JVM немедленно убивает все оставшиеся daemon-потоки и завершается.

Нюансы:
- `finally` не гарантирован, соответственно Нельзя писать в файл/БД из daemon'а без риска потери данных, нельзя использовать для задач требующих гарантированного завершения, **try-with-resources** в daemon'е — не гарантирует **close()**.
- Распространённый миф: «daemon-потоки низкоприоритетные». Нет. Daemon-поток может иметь **MAX_PRIORITY**, а user-поток — **MIN_PRIORITY**. Это независимые характеристики.
- Поток, созданный из daemon-потока, по умолчанию тоже daemon. Аналогично user-поток создаёт user-поток. Можно переопределить через **setDaemon()** до **start()**
- Если пул в daemon-потоке — его worker'ы тоже daemon. При завершении main они умрут вместе с задачами.
- Виртуальные потоки — всегда daemon по своей природе. Они не удерживают JVM. Thread.setDaemon() на виртуальном потоке — no-op (не бросает исключение, но и не меняет ничего).
- `jstack <pid>` показывает daemon-статус
- Shutdown hooks выполняются после остановки обычных потоков, но до daemon потоков, То есть daemon-потоки живут дольше, чем user-потоки, но умирают без очистки.
- `System.exit()` запускает shutdown sequence: hooks → daemon killed. `Runtime.halt()` — немедленно убивает `JVM`, без hooks и без очистки.
- `ForkJoinPool.commonPool()` — daemon-потоки. Поэтому незавершённые `CompletableFuture` на `commonPool` не удерживают JVM.

Использование:
- Внутри JVM — все служебные потоки daemon: GC-потоки, JIT-компиляторы (C1 CompilerThread, C2 CompilerThread ).
- Фоновые задачи в приложении, например метрики.
- Кэш-эвиктор
- `Executors.newScheduledThreadPool()` создаёт user-потоки (через `ThreadPoolExecutor` с `defaultThreadFactory`). JVM не завершится, пока пул не shutdown'ится. Если задачи не важны, то безопаснее их сделать демонами, чтобы не блочить остановку приложения
- Не используйте daemon для критичных задач
- Daemon + finally = потеря данных

### **Виртуальные потоки (Java 21+):** как устроены, чем отличаются от платформенных, почему `synchronized` внутри виртуального потока может пинить носительский поток (до JEP 491).
Виртуальные потоки — это лёгкие потоки, управляемые **JVM**, а не **ОС**. Они «монтируются» на небольшое число платформенных потоков-носителей (carrier threads). Когда виртуальный поток блокируется (I/O, sleep), он «размонтируется» и освобождает носитель, который переключается на другую задачу.

Основные моменты: 
- **Модель M:N**: Тысячи виртуальных потоков (M) работают на пуле из нескольких платформенных потоков (N, обычно = числу ядер CPU)
- **Continuation**: Это механизм, позволяющий «заморозить» стек виртуального потока в кучу (heap) при блокировке и «разморозить» его обратно на носителе позже.\
Стек виртуального потока — это объект в куче, а не отдельная область native-памяти, поэтому он лёгкий и управляется GC.
- **Планировщик**: По умолчанию используется `ForkJoinPool` с режимом **FIFO**. Его размер обычно равен числу доступных процессоров.
- Платформенный поток занимает около 1МБ, а виртуальный несколько сотен байт и размер меняется динамически.
- Работают поверх платформенных потоков;
- Легковесные;
- Самая крутая фича - как только натыкаемся на блокирующую операцию, сразу же передаём управление другому потоку;
- Планируются JVM, а не ОС;
- Оптимальны при блокирующих операциях.
- внутри используется реализация `ForkJoinPool` из-за workstealing(один платформенный поток может украсть виртуальный поток у другого платформенного) и наличия локальных очередей платформенных потоков.
- для виртуальных потоков запускается отдельный `ForkJoinPool` с количеством потоков равным к-ву процессоров.
- Бесшовная интеграция в существующую кодовую базу;
- Реализованы на базе `Continuation` - внутреннее АПИ позволяющее сохранить состояние потока выполнения.  Когда создаётся виртуальный поток, для него создаётся соответствующий объект `Continuation`.
- По умолчанию являются демон потоками, соответственно как только главный поток завершается, останавливаются и виртуальные потоки. Чтобы избежать остановки, в конце джойним виртуальный поток к основному `vThread.join()`;
- Вызов `setPriority` для виртуального потока не изменяет его приоритета, он у него будет всегда **NORM_PRIORITY**;
- статический метод `Thread::getAllStackTraces` возвращает стек-трейсы только платформенных потоков, но не виртуальных.
- В JVM есть глобальный механизм - read poller, он отслеживает синхронные сетевые операции когда они вызываются в виртуальном потоке, помещает файловый дескриптор и поток в **Map**, а получив уведомление о событии, ищется нужный поток и возобновляет его выполнение.
- Каждый поток имеет собственную копию переменной `ThreadLocal` - что может вести к взрывному росту потребления памяти, а наследование значения ThreadLocal от родительского потока может вести к неявным ошибкам.
  Для мониторинга использования `ThreadLocal` есть флаг `-Djdk.traceVirtualThreadLocals` который при каждом обращении к `ThreadLocal` из виртуального потока будет печатать StackTrace в логи;
#### Rate Limiting
Благодаря отличному масштабированию использование виртуальных потоков может перегрузить вызываемые сервисы, чтобы этого избежать используют Rate Limiting. Типичный пример - использование семафора см класс `by.java.concurrency.RateLimiting`.
#### Pinning
Пиннинг — ситуация, когда виртуальный поток временно прикрепляется к своему потоку-носителю и не может от него отсоединиться даже при блокирующих операциях.
Возникает при:
- входе в synchronized блок, Java 21-23. Чтобы избежать - используется `ReentrantLock` вместо `synchronized`.
  В `ReentrantLock` используется механизм park/unpark, что позволяет определить момент парковки виртуального потока и отсоединить его от потока носителя.
  В Java 24 починили `synchronized` и он больше не пиннится. З.Ы. Пиннинг на быстрых операциях не критичен, по сравнению с блокирующими операциями.
- вызов нативных методов, или внешних функций.
- загрузка/инициализация классов, т.к. используется нативный код, но это работает быстро и редко.
- сторонние библиотеки, которые напрямую обращаются к системным вызовам в обход стандартных Java API.
- Не совсем пиннинг, но виртуальный поток на файловых I/O в Линуксе и при DNS-запросах(До Java 21) будет блокировать платформенный поток т.к. JDK пока не поддерживает `io_uring`, асинхронный I/O.
  На низком уровне это обходится так: FJK видит что поток заблокировался на I/O и создаёт ещё один поток, для компенсации простаивающего. Когда ситуация разрулится, компенсационные потоки остановятся.
Проблемы вызываемые пиннингом:
- Снижение пропускной способности;
- Проблема масштабируемости;
Для Мониторинга пиннинга нужно указать флаг `-Djdk.tracePinnedThreads=full` при старте приложения, на каждый эпизод в логи будет печататься стектрейс;

Причина пиннинга платформенного потока виртуальным на `synchronized` блоках: `synchronized` в JVM реализован через мониторы, а каждый объект имеет собственный монитор, JVM должна отслеживать, кто его держит. \
Проблема в том, что монитор привязывается к платформенному потоку, а не к виртуальному. Когда виртуальный поток захватывает монитор, JVM записывает владельцем его носителя. Когда виртуальный поток фризится внутри блока синхронизации, а вместо него запускается другой виртуальный поток, этот другой может проходить через монитор, ведь монитор приписан к платформенному, который остался тем же.\
Поэтому решили оставить пиннинг виртуальных потоков в блоках синхронизации.

## Коллекции

### **HashMap: Внутреннее устройство:** бакеты, связные списки, красно-чёрные деревья (с Java 8), порог деревафикации (8 элементов, отмена при уменьшении до 6).
`HashMap` — это массив `Node<K,V>[] table`, где каждый элемент — бакет. Индекс бакета вычисляется как `(n - 1) & hash`, где n — длина массива (степень двойки), а **hash** — хеш ключа, дополнительно «размешанный» через `hashCode() ^ (hashCode() >>> 16)` для лучшего распределения.

Так как сложность поиска в списке равна O(n), а в дереве — O(log n), на больших размерах список заменяется на дерево. 
Условия замены списка деревом:
- Длинна бакета достигает 8;
- Общая ёмкость `HashMap` не менее 64.

Нюансы:
- Если при первом условии второе не выполнилось, вместо деревофикации вызывается `resize()`(удвоение массива), чтобы «разбросать» элементы по разным бакетам.
- Почему именно 8? Из соображений вероятности: при хорошей хеш-функции и load factor 0.75 частота попадания 8 элементов в один бакет подчиняется распределению Пуассона и составляет примерно 0.00000006.  То есть дерево строится только в экстремальных случаях, когда хеш-функция «плохая»
- Если из дерева удалять элементы и их число падает до 6, дерево превращается обратно в связный список.
- **TreeNode** примерно в два раза больше обычного **Node**
- Красно-чёрному дереву нужно упорядочивание. Если ключи реализуют `Comparable`, используется `compareTo()`. Если нет — применяется `tieBreakOrder()`: сначала сравнение по имени класса, затем по `System.identityHashCode()`
- `null`-ключ кладётся в бакет 0 (`hash(null)` = 0) — один `null`-ключ разрешён.
- `null`-значения разрешены — поэтому `map.get(key) == null` не означает «нет ключа»: проверять надо через `containsKey`
- Если заранее известно число элементов n, задайте `new HashMap<>((int)(n / 0.75) + 1)` — избежите resize'ов. Иначе при добавлении 1000 элементов произойдёт **~10 resize'ов (16 → 32 → ... → 1024)**
- `HashMap(int initialCapacity)` не создаёт массив сразу — он вычисляет threshold и создаёт `table` при первой `put()`. Ёмкость округляется вверх до степени двойки.
- Итерация — **O(capacity + size)**, не **O(size)**. `HashMap` итерирует весь массив бакетов, включая пустые. Поэтому `new HashMap<>(1_000_000)` при 10 элементах — итерация по миллиону бакетов. Это важно для `keySet()`, `values()`, `entrySet()`;

### **HashMap Асимптотика** операций put/get в лучшем и худшем случае — O(1) vs O(log n).

Основные случай

| Операция        | Лучший случай | Средний случай            | Худший случай                       |
|-----------------|---------------|---------------------------|-------------------------------------|
| get(key)        | O(1)          | O(1) амортизированно      | O(log n) (Java 8+) / O(n) (Java 7−) |
| put(key, value) | O(1)          | O(1) амортизированно      | O(log n) (Java 8+) / O(n) (Java 7−) |
| remove(key)     | O(1)          | O(1) амортизированно      | O(log n) (Java 8+) / O(n) (Java 7−) |
| resize()        | —             | O(n) амортизированно O(1) | O(n)                                |

Put/get в пустой бакет `O(1)` - Вычисление индекса `(n-1) & hash` — константное время, сравнение ключа — константное.
В худшем случае, когда всё в одном бакете `O(log n)` для дерева и O(n) для списка.
`resize()` — `O(n)` т.к. нужно переложить каждый элемент.


### **HashMap Рехеширование** — когда происходит, как считается новая позиция бакета.
- Запускается, если после вставки число элементов превышает **threshold**. `threshold = capacity × loadFactor`. По умолчанию `loadFactor = 0.75`
- Рехеширование происходит только при `put()`.
- При `remove()` размер может упасть, но уменьшения _capacity_ не происходит — **HashMap** не «сжимается» автоматически.

**Как считается новая позиция (Java 8 — трюк с одним битом)**
Пусть старая **capacity** — _n_, новая — _2n_. Индекс вычисляется маской `hash & (cap - 1)`. У старой маски _n-1_ и новой маски _2n-1_ различие — один добавленный старший бит:
значит, новый индекс либо совпадает со старым, либо отличается ровно на `+oldCap` — в зависимости от того самого бита хэша:
Пример: элемент с hash & 15 == 5 лежит в бакете 5. При удвоении до 32:

если бит №4 хэша равен 0 → остаётся в бакете 5;
если равен 1 → переезжает в бакет 5 + 16 = 21.

### Контракт equals/hashCode:** что будет, если hashCode у двух объектов одинаковый, а equals возвращает false? — оба останутся в коллекции.
Это легальная ситуация — коллизия хешей. `HashMap` обработает её корректно: оба объекта попадут в один бакет, но останутся разными ключами. Поиск по ним будет работать правильно, но чуть медленнее (нужен обход списка/дерева).
Проблема возникает в обратном случае: `equals = true`, но `hashCode` разный — тогда `HashMap` перетирает элементы.

**Контракт `hashCode()`**:
- Если `a.equals(b)`, то `a.hashCode() == b.hashCode()` — обязательно.
- Если `!a.equals(b)`, то `hashCode` может совпадать или различаться — не обязательно разный.
- **Consistency**: повторный вызов на том же объекте возвращает то же значение (если объект не изменён).

**Контракт `equals()`**:
- Рефлексивность: `a.equals(a) == true`.
- Симметричность: `a.equals(b) == b.equals(a)`.
- Транзитивность: `a.equals(b) && b.equals(c) → a.equals(c)`.
- **Consistency**: повторный вызов возвращает то же значение.
- `a.equals(null) == false`.

**Ключевое:** контракт односторонний — из `equals` следует равенство хешей, но не наоборот. Одинаковый `hashCode` при разных `equals` — нормально и ожидаемо.

**Что если equals не согласован с hashCode**
- `equals = true`, `hashCode` разный - попадут в разные бакеты, а `get()` не найдёт ключ по `equals(`) в неправильном бакете.
- ключи `HashMap` должны быть `immutable`. Иначе — потеря элементов.
  
При ~77 000 элементах вероятность коллизии `hashCode` (2^32) превышает 50%.

### **Ловушка с HashSet:** два объекта с одинаковым `hashCode`, но без переопределённого `equals` — какой размер множества? (используется `==` из `Object` — два разных объекта, размер = 2).
Размер множества будет 2, а не 1. `HashSet` внутри — это `HashMap`, где элементы — ключи, а значения — фиктивный PRESENT-объект.
Соответственно логика добавления будет как у `HashMap`, два объекта попадут в один бакет, но т.к. `equals` у них не переопределён и будет разный, то в `HashSet` будет лежать два объекта с одинаковым `hashCode`.  
Одинаковый `hashCode` кладёт объекты в один бакет, но дубликат распознаётся только через `equals`;

### **ArrayList vs LinkedList:** где быстрее вставка в середину, внутреннее устройство (поля LinkedList — `size`, `first`, `last`; ArrayList — массив с capacity и коэффициентом роста 1.5).
Вставка в середину `LinkedList` быстрее теоретически (`O(1)` на вставку после поиска позиции vs `O(n)` на сдвиг в `ArrayList`), но на практике `ArrayList` почти всегда быстрее — из-за cache locality и стоимости обхода `LinkedList` до позиции.

`ArrayList`:
- Непрерывный блок памяти (массив `Object[]`)
- Элементы лежат последовательно в `heap`.
- `size` — сколько занято; `elementData.length` — `capacity`.
- Доступ по индексу — `O(1)`
- При переполнении — `grow()`: новый массив в 1.5 ×, копирование `Arrays.copyOf()`
- `ArrayList.add(index)` использует `System.arraycopy()`, который JIT компилирует в нативную `memmove` — высокооптимизированную процессорную инструкцию. Сдвиг 10 000 элементов — микросекунды.


`LinkedList`:
- Узлы разбросаны по **heap** — каждый `Node` отдельный объект.
- Каждый узел хранит `item`, `next`, `prev`.
- Доступ по индексу — `O(n)`: обход от `first` или `last` (оптимизация: если **индекс < size/2** — идём с начала, иначе с конца). 
- Нет **capacity** — нет переполнения, нет копирования.
- `O(n)` из-за поиска. Вставка «сама по себе» — `O(1)`, но до неё нужно дойти.
- каждое обращение к `node.next` требует загрузки из памяти, т.к. ноды разбросаны по heap и скорее всего будут кэш промахи.
- Каждая вставка в `LinkedList` аллоцирует `Node` — новый объект в **heap** → давление на GC. `ArrayList` вставляет в существующий массив — нет аллокации (кроме `grow`)

### **ConcurrentHashMap** — как устроена конкурентность внутри ( CAS + synchronized на бакет с Java 8).
`ConcurrentHashMap` - внутри как обычная `HashMap`, но с важными отличиями:
- массив бакетов и ссылка на следующий элемент являются `volatle` полями, что позволяет отображать мгновенно изменения для всех потоков.
- При вставке используется синхронизация для вставки в непустой бакет, причём замком будет первый элемент бакета. Если бакет пустой, то используется CAS для записи в пустую ячейку.
- чтения без блокировок.
- `size()` — это оценка, а не точное значение. Для подсчета используется набор распределенных счетчиков (`CounterCell`), аналогично `LongAdder`. Поэтому при конкурентных изменениях `size()` дает приблизительное значение в моменте. Для больших объемов предпочтительнее `mappingCount()`
- Итераторы слабо консистентны (Weakly Consistent). Они не бросают `ConcurrentModificationException`, но отражают состояние карты на момент или после создания итератора, а не фиксированный снимок.
- Запрет на `null`. ConcurrentHashMap не допускает `null` ключей и значений. Это сделано для того, чтобы избежать неоднозначности при конкурентном доступе (нельзя отличить отсутствующее значение от `null` через `containsKey`)
- Cпец-хэши узлов. Отрицательные значения hash маркируют служебные состояния: **MOVED** — бакет в процессе переноса при `resize` (`ForwardingNode` — указатель на новую таблицу), **TREEBIN** — корень дерева. Читая отрицательный _hash_, поток понимает: «структура меняется» — и либо помогает, либо ждёт.
- Кооперативный **resize**. Начавший расширение поток делит таблицу на «полосы переноса» (`stride ≥ 16` бакетов); другие пишущие потоки, наткнувшись на `ForwardingNode`, подхватывают кусок переноса сами (`helpTransfer`) — `resize` выполняется параллельно всеми желающими.

### **CopyOnWriteArrayList / CopyOnWriteArraySet** — когда использовать (много чтений, мало записи), почему запись медленная.
`CopyOnWriteArrayList` и `CopyOnWriteArraySet`: при каждом чтении доступ к элементам осуществляется без синхронизации, напрямую, но при модификации изменения происходят в копии структуры, доступ к которой могут получить(через новый гет или итератор) все читатели после окончания модификации. Пока идёт создание копии и её модификация, читатели читают из старой версии коллекции.
- нет риска `ConcurrentModificationException`
- каждый итератор видит консистентное состояние на момент его создания.
- Высокая стоимость модификаций, копирование массива **O(N)**. Плохо при частых записях.
- Читатели не видят свежих данных мгновенно.
- Читатели никогда не блокируются и видят согласованный снимок
- **array** — `volatile`, чтобы читатели видели актуальную ссылку.
- COW копирует весь массив — даже если вставка в конец. Для `n = 1 000 000` — копирование 8 МБ ссылок на каждый вызов `add()`
- `iterator()` не поддерживает `remove()`
- `addIfAbsent()` атомарен, закрыт общим блоком синхронизации
- Пока читатели держат ссылку на старый массив, он не собирается. При частых мутациях и долгих итерациях — много «старых» массивов в heap одновременно.
- `addAll()` делает одну копию, не N
- а вот `removeAll()` может вызывать `remove()` многократно → O(n²)
- Если чтений мало, а записей много `Collections.synchronizedList` будет получше.
- `CopyOnWriteArrayList` растёт по одному элементу — серия добавлений n элементов = копирования `1+2+3+…+n = O(n²)` на заполнение. Классическая ошибка: собирать COW-список в цикле.

**Почему чтение быстрое:**
- Нет блокировки — `get()`, итерация, `contains()` работают со снимком.
- Нет `volatile-read` на каждый элемент (только на ссылку массива).
- `Cache locality` — массив непрерывен.

`CopyOnWriteArraySet` является `CopyOnWriteArrayList` внутри.
Не использовать(кроме очевидного) когда Нужна точная согласованность итератора и мутаций, а также не хочется дополнительно грузить сборщик мусора.

### **TreeMap / TreeSet** — красно-чёрное дерево, сортировка через `Comparator` или `Comparable`.
1. `TreeMap<K,V>` — реализация `NavigableMap` на основе красно-чёрного дерева.
**Ключевое свойство**: дерево всегда отсортировано по ключу. Благодаря этому получаем: Логарифмические операции: _get_, _put_, _remove_ — `O(log n)`.
**Сортировка:**
- Сортировка через наследование ключами `Comparable<T>` — «естественный порядок» объекта.
- Или `Comparator<T>` — внешний порядок, передаётся в конструктор.
- В приоритете сравнение через `Comparator<T>`
- Если не был передан `Comparator<T>` и ключи не наследуют `Comparable<T>`, тогда будет выброшено исключение `ClassCastException`
- **Важно!** Контракт `TreeMap` использует `compareTo` (или `Comparator`), а НЕ **equals**, но на самом деле они должны быть согласованными!
- `TreeMap` хранит только один `Comparator` — на момент создания. Если поменять логику объекта-компаратора после вставки, дерево уже не перебалансируется по новой логике — порядок «застынет» неправильным.

2. `TreeSet` обёртка над TreeMap, у которого в качестве значения используется объект заглушка.

Когда использовать:
- нужна сортировка по ключам
- Нужны навигационные операции (floor, ceiling, range), или min/max
- нужны субдиапазонные запросы(subMap).

Не использовать:
- нужны только вставки и вычитки, без сортировки
- нужна потоко-безопастность
- Ключи с несогласованным **compareTo**/**equals** не согласованы, есть риск потери элементов.
- Запрещены **null**-ключи если используется natural ordering — `NullPointerException` при `compareTo`. А с кастомным `Comparator` всё ок, при условии, что он обрабатывает случай с `null`.


### **LinkedHashMap** — двусвязный список поверх бакетов, как получить LRU-кэш через `accessOrder = true` и `removeEldestEntry`.
`LinkedHashMap` наследуется от `HashMap`, но добавляет двусвязный список, проходящий через все `entry`. Это даёт предсказуемый порядок итерации — в отличие от `HashMap`, где порядок зависит от хешей.\

`HashMap` предоставляет пустые(ничего не делающих) хуки, которые `LinkedHashMap` переопределяет:
- `void afterNodeAccess(Node<K,V> p) { }`
- `void afterNodeInsertion(boolean evict) { }`
- `void afterNodeRemoval(Node<K,V> p) { }`
- `boolean removeEldestEntry(Map.Entry<K,V> eldest) { return false; }`

Нюансы:
- Каждый узел — одновременно элемент бакета и элемент двусвязного списка.
- Есть флаг `accessOrder`: **false** - упорядочивание в порядке вставки и **true** - в порядке последнего доступа.
- Есть метод `removeEldestEntry`, по умолчанию всегда возвращает `false`(не удалять), но мы можем его переопределить со своим условием для LRU кэша. Защищён от `null`.
- `LinkedHashMap` чуть медленнее `HashMap`
- `LinkedHashMap` хавает больше памяти из-за ссылок на соседние узлы.

Нюансы LRU-реализации:
- при `accessOrder = true`, `get()` меняет порядок элементов, что может быть нежданчиком. Т.е. get мутирует структуру.
- при `accessOrder = true` итерация идёт от `head` (самый старый) к `tail` (самый свежий)
- при `accessOrder = true` получаем `overhead` на каждый `get` из-за перемешения узла в хвост списка. Кстати тут итератор может кинуть `ConcurrentModificationException` при следующем `next()`, если `get()` был между.
- `removeEldestEntry` вызывается при `putAll`, причём для каждого вставляемого элемента.

## Строки
### String Pool** — где находится (Heap до Java 7, вне PermGen с Java 7+), `intern()` — зачем нужен, дедупликация строк в G1.
**String Pool** — это специальная область памяти, где хранятся уникальные экземпляры строк. **Java 8+** Пул строк остался в **Java Heap**.
Строковый литерал кладёт строку в пул.\
`String.intern()` кладёт КОПИЮ строки в пул и возвращает ссылку на неё, если она там была, то вернёт ссылку на уже существующую. Использовать со:
- Строками, которые много раз сравниваются через `equals()`.
- Строками, которые часто повторяются и живут долго.

Не использовать Если строки уникальны и не повторяются(ввод пользователя), интернирование только создаст дополнительную нагрузку на пул и GC.
Начиная с **JDK 8u20**, **G1 GC** получил поддержку автоматической **дедупликации** строк. Работает только с **G1** (и **Shenandoah** в некоторых версиях).
Принцип работы дедупликации в том, что сборщик сканирует строки и находит те, у которых одинаковый массив символов и дубликаты перенаправляются на один общий массив, т.е. в итоге одинаковые строки содержат ссылку на один и тот же массив.\
Причём ссылки на сами строки не меняются, т.е. если они были не равны, то и останутся не равными.
По умолчанию дедупликация выключена, чтобы не грузить ЦПУ. Нужно профилировать, чтобы понять нужно оно чи не через JFR-событие **jdk.StringDeduplication**

Отличие дедупликации от `intern()`:
- `intern()` унифицирует объекты `String` (одна ссылка на строку).
- **Дедупликация** унифицирует только массивы символов внутри разных объектов `String`.
- **Дедупликация** автоматическая — не требует изменений в коде.
- `intern()` требует явного вызова и работает через пул строк.

### **StringBuilder vs StringBuffer** — в чём разница (синхронизация), почему `StringBuilder` почти всегда предпочтительнее.
- `StringBuffer` тот же `StringBuilder` но у которого все методы синхронизированные. В однопотоке **JIT** может выкинуть синхронизацию если объект не утекает за пределы метода.
- `StringBuffer` имеет поле `toStringCache` т.е. последний вызов `toString()` кэшируется. `toStringCache` сбрасывается после каждой мутации. У `StringBuilder` такого кэша нет.
- `StringBuilder` почти всегда предпочтительнее, т.к. используется как локальная переменная.
- `StringBuffer` синхронизирует отдельные методы, но не составленные из них операции. Для нормального блока нужна внешняя синхронизация, а с ней уже и `StringBuilder` норм будет работать.
- `StringBuffer` не даёт «настоящей» конкурентности. Для сценария «несколько потоков пишут в один буфер» нужны другие инструменты (например, `BlockingQueue<String>` + сборка в конце).
- `String s = "a" + b + "c" + d;` в **Java 9+** использует **invokedynamic** + `StringConcatFactory` для +, но если конкатенация идёт через цикл то не ок, т.к. создаётся в каждой итерации `StringConcatFactory`.
- Если известен изначальный размер(default 16), лучше его задавать сразу, чтобы не было ресайзов. 
- `StringBuilder` не потокобезопасен даже для чтения. Если один поток вызывает `append()`, а другой — `toString()` `ArrayIndexOutOfBoundsException`, «Рваные» строки.
- `Collectors.joining()` использует `StringBuilder` внутри — но для параллельных стримов использует `StringJoiner` и сливает части в конце. Это корректно и эффективно.

## Исключения

### **Иерархия:** `Throwable` → `Error` / `Exception` → `RuntimeException`. Checked vs unchecked.
- Прямое наследование от `Throwable` — антипаттерн
- `catch (Throwable)` или `catch (Error)` — антипаттерн
- `Error` — проблемы вне контроля приложения. Их не нужно ловить, обычно нельзя восстановиться.
- в редких случаях `OutOfMemoryError` можно поймать в изолированном коде (например, в пуле потоков для **graceful shutdown**), но это очень осторожно.
- `InterruptedException` — особый **checked**. Если поймали `InterruptedException` и не можете обработать — восстановите флаг прерывания через `Thread.currentThread().interrupt()`. Иначе информация о прерывании теряется.
- `try-with-resources` подавляет исключения из `close()`, добавляя их в `getSuppressed()`. Не теряйте их при логировании.
- При перепробрасывании исключения, всегда передавайте оригинальное исключение как `cause` — иначе теряется контекст.
- `Spring` по умолчанию откатывает транзакцию только на unchecked `(RuntimeException и Error)`. **Checked exceptions** не откатывают без `@Transactional(rollbackFor = ...)`.
- При выкидывании исключения из `finally` в `try/finally` конструкции, оно скроет исключение брошеное в блоке `try`.
- Создание исключения (`new`) — дорого, т.к. `fillInStackTrace()` обходит стек, но его можно переопределить.
- Бросание исключения - дорого: размотка стека.


**Checked exceptions**:
- Либо поймано в try/catch
- либо объявить `throws` в сигнатуре

**Unchecked exceptions (RuntimeException):**
- не требуют **throws** и не проверяются компилятором.
- **Смысл:** Это баг в программе — исправь код, а не лови исключение
- Бросается, если вызывающий код может и должен что-то сделать (**retry**, **fallback**, сообщить пользователю).
- Используется при нарушении контракта метода, баг в коде, который нужно исправить, а не обрабатывать.

### **try-with-resources vs try-catch-finally** — что делает под капотом (интерфейс `AutoCloseable`, порядок закрытия ресурсов).
`try-with-resources` — синтаксический сахар, который автоматически закрывает ресурсы, реализующие `AutoCloseable`. Компилятор генерирует вызовы `close()` в правильном порядке, с корректной обработкой исключений через **suppressed**.
`try-catch-finally` — ручное управление: вы сами пишете `close()` в `finally`, сами обрабатываете исключения из `close()`

Нюансы `try-with-resources`: 
- закрытие ресурсов происходит в обратном порядке открытию. Сделано так на случай, если ресурсы зависимы второй от первого.
- Если `try-with-resources` бросает исключение в `try/catch` блоке и при этом ещё и при закрытии ресурса, то исключение из `close()`  добавляется в `suppressedExceptions` основного.\
В обычном `try-catch-finally` исключение `finally` перетирает основное исключение.
- `try-with-resources` с несколькими ресурсами компилятором разворачивается во вложенную структуру `try`
- **Java 9+** позволяет использовать **effectively final** переменные объявленные вне(до) `try`, в `try-with-resources` без повторного объявления.
- Если `close()` бросает исключение при отсутствии основного исключения — оно пробрасывается как обычно.
- `Null` ресурс не приводит к ошибке. Компилятор генерирует _null-check_ перед `close()`. Это безопасно.
- `try-with-resources` Компилятор ловит `Throwable` (не только Exception, а и `Error`), чтобы гарантировать `close()`
- ????close() происходит до catch.
- ????Lock и ExecutorService не AutoCloseable
- `close()` вызывается до оператора `return` в `try` блоке. Если `close()` бросит — `return` отменяется, исключение пробрасывается.
- Переменные ресурсов — effectively final, их нельзя переприсвоить — иначе close был бы вызван для «сменённого» объекта.
- Ресурсы-обёртки главное поле для ошибок: закрытие `BufferedReader` закрывает и вложенный `FileReader`.
- если исключение бросил конструктор ресурса, оно тоже попадает в обычный `catch`

Когда `try-catch-finally` нужен:
- `finally` не для ресурсов, а для логики — восстановление состояния, разблокировка не-`AutoCloseable`-монитора. `ReentrantLock` — не `AutoCloseable`, тут `finally` по-прежнему нужен

### **Can a catch block handle multiple exceptions?** — `catch (A | B e)` с Java 7, ограничение: типы не должны быть в отношении наследования.
Да, но:
- Переменная **e** — **effectively final**
- типы в **multi-catch** должны быть несвязанными (ни один не наследник другого).
- Чтобы вызвать специфичный метод исключения — нужен отдельный `catch` или `instanceof`.
- Порядок типов не важен, В отличие от отдельных catch, где порядок критичен.
- `finally` выполняется после `catch`, независимо от того, был ли он `multi-catch`.
- `Multi-catch` не влияет на **suppressed exceptions** `try-with-resources`.
- Технически можно смешать `Exception` и `Error` в `multi-catch`. Практически — антипаттерн: Error не ловят.

### **Что будет, если в finally бросить исключение?** — перекроет исключение из try.
- Исключение из `finally` подавляет (затирает) исключение из `try` или `catch`. Оригинальное исключение теряется и не попадёт ни в стек, ни в лог, ни в `getCause()`.
- Если `return` в `try`, а исключение в `finally`, тогда `return` отменяется, бросается исключение. Метод не возвращает значение.
- `return`ы в `try/finally` - вернёт тот что в `finally`;

### **`finalize()` — почему устарел и deprecated?** Нет гарантии вызова, задержка GC, проблемы с производительностью. Альтернативы — `Cleaner` / `PhantomReference`.
Проблемы `finalize()`:
- Нет никаких гарантий, что` finalize()` вообще будет вызван, и тем более — когда это произойдет
- Код в `finalize()` может работать долго и тормозить сборщик мусора.
- Внутри `finalize()` можно сделать объект снова достижимым — например, присвоить его статическому полю или сохранить в другую ссылку. \
В результате объект не будет собран сборщиком мусора, хотя логически он больше не нужен. Это ведёт к неожиданным утечкам памяти.
- выполняется в системных потоках. Даже в однопоточном приложении появление финализатора делает его многопоточным, создавая риск дедлоков.

Что в место?
- `try-with-resources`
- `java.lang.ref.Cleaner` Для ресурсов, которые живут дольше, чем один блок кода, или когда нужно освободить нативную память. `Cleaner` не «воскрешает» объекты и безопаснее

## Stream API и функциональщина
### **Промежуточные vs терминальные операции** — ленивость, когда пайплайн реально выполняется.
**Промежуточные**: _filter(Predicate)_, _map(Function)_, _flatMap(Function)_, _peek(Consumer)_ и т.д
**Терминальные**: _collect(Collector)_, _forEach(Consumer)_, _reduce(...)_, _findFirst/findAny_, _anyMatch/allMatch/noneMatch_ и тд.

Нюансы:
- Если все операции **stateless**, то для каждого элемента выполняется вся цепочка _filter_ → _map_, а не «сначала все _filter_, потом все map». Элементы обрабатываются по одному через весь пайплайн.
- Если есть операция **stateful**, она накапливает промежуточный результат. Пример таких операций `sorted()`, `distinct()`, `limit()`.
- Некоторые операции могут остановить пайплайн раньше, чем обработаны все элементы: `anyMatch`, `findFirst`, `findAny`, `limit(n)`
- `peek` — для отладки. Не использовать его для side effects.
- `forEach` vs `forEachOrdered` - для последовательных стримов нет разницы. `forEachOrdered` гарантирует порядок при использовании с параллельными стримами.
- `Stream` нельзя переиспользовать, если попробуем с ним что-то делать после вызова любой операции, то получим `IllegalStateException`.
- дешёвые и фильтрующие операции вызываем в первую очередь. `Filter` до `map` уменьшает к-во элементов для map.
- `sorted()` дорогая операция т.к. `stateful`, накапливает все элементы, сортирует **(O(n log n))**
- `distinct()` является `stateful` хранит все уникальные элементы в `HashSet` → память **O(n)**. Для больших стримов дорого.
- `findAny` лучше в параллельных стримах чем `findFirst`, т.к. не нужно знать какой элемент первый.
- **Stateful**-операции (`sorted`, `distinct`, `limit`)


### **Что возвращает промежуточный метод стрима?** — новый `Stream`, операция отложенная.
- Промежуточные операции не мутируют исходный стрим. Они создают новый стрим
- Исходный стрим становится непригодным
- После вызова любой операции исходный `Stream` считается «потреблённым».

### **Consumer vs Supplier vs Function vs Predicate** — когда какой.
1. `Consumer<T>` - Принимает значение, ничего не возвращает. Метод `accept(T)`.
2. `Supplier<T>` - Ничего не принимает, но возвращает значение. Метод `get()`.
3. `Function<T,R>` - Принимает один параметр и возвращает один параметр. Метод `apply(T)`.
4. `Predicate<T>` - Принимает параметр и возвращает `boolean`. Метод `test(T)`.

- `Supplier<T>` Когда нужно отложенное создание значения, фабрика, lazy-инициализация, т.к. его отработка происходит именно в момент вызова `get()`, а не создания.
- `Predicate<T>` Когда нужно проверить условие.
- `Function<T,R>` Когда необходимо преобразовать типы.
- `Consumer<T>` Когда необходимы side эффекты.


### **`reduce` vs `collect`** — разница, когда использовать mutable reduction.
1. `reduce` это immutable reduction: каждый шаг создаёт новое значение из предыдущего и текущего. Подходит для примитивов, неизменяемых типов, свёрток (сумма, произведение, min/max, конкатенация строк)
2. `collect` — mutable reduction: накапливает результат в изменяемом контейнере (например, ArrayList, StringBuilder, HashMap), который переиспользуется между элементами. Подходит для коллекций и сложных агрегаций (группировка, партиционирование, toMap

**Нюансы:**
- Ключевое отличие: `reduce` создаёт **O(n)** промежуточных объектов (по одному на элемент), `collect` — **O(1)** (один контейнер, мутируется). Для коллекций `collect` всегда эффективнее.
- `reduce` вместе с `String` — **O(n²)**.

### **Параллельные стримы** — как работают (`ForkJoinPool.commonPool`), почему не всегда ускоряют, проблемы с общим пулом.
Под капотом используется модель `Split-Apply-Combine` и системный пул потоков `ForkJoinPool`
1. `Spliterator` рекурсивно делит источник данных на части (чанки). Это ключевой этап: если данные нельзя эффективно разделить (например, `LinkedList` или источник на основе `Iterator`), параллелизм будет неэффективен
2. `Apply`: Каждая часть обрабатывается в отдельном потоке из общего пула `ForkJoinPool.commonPool()`. Пул использует `work-stealing` для балансировки нагрузки: освободившиеся потоки «воруют» задачи у занятых.
3. `Combine`: Терминальная операция (`collect`, `reduce`) собирает частичные результаты в один. Для параллельных стримов существуют специальные конкурентные коллекторы (например, `groupingByConcurrent`), которые работают быстрее обычных, так как не требуют слияния промежуточных `Map`

Параллелизм добавляет накладные расходы на координацию и синхронизацию, которые могут «съесть» выгоду в следующих случаях:
- коллекций меньше ~1000 элементов, или очень быстрые операций. Накладные расходы превышают выгоду
- Плохо разделяемые источники данных сводят параллелизм на нет.
- Если задача ждёт I/O или блокировок, потоки ForkJoinPool простаивают, и параллелизм не помогает. Операции должны быть сложными **CPU-bound**.
- Сборка мусора: Интенсивное создание объектов в нескольких потоках может вызвать конкуренцию и резко увеличить нагрузку на **GC**, замедляя всю программу.
- **statefull** операции `sorted()`, `distinct()`, `limit()` требуют координации между потоками, что создаёт дополнительную нагрузку и снижает эффективность.
Если лямбда внутри потока использует или изменяет общее изменяемое состояние (например, модифицирует внешнюю переменную или коллекцию), это ведёт к race conditions и непредсказуемым результатам.

`ForkJoinPool.commonPool()` — это общий ресурс для всего JVM из чего следуют проблемы:
-  Пул имеет всего (число ядер - 1) потоков.
-  Если один стрим выполняет долгую блокирующую операцию (например, ждёт ответа по сети), он занимает поток, а остальные желающие поработать его ждут.

### **`flatMap`** — что делает, пример превращения списка списков в плоский поток.
- `flatMap` — промежуточная операция, которая преобразует каждый элемент в поток, а затем объединяет все эти потоки в один плоский поток. Вместо `Stream<Stream<T>>` получается `Stream<T>`.
- `flatMap` не любит `null` — если функция вернёт `null` вместо `Stream`, будет `NullPointerException`
- `flatMap` сохраняет порядок для последовательных стримов. Для параллельных стримов порядок не гарантирован.
- `mapMulti` — более эффективная альтернатива.
```java
// flatMap — создаёт Stream для каждого элемента
stream.flatMap(s -> s.isEmpty() 
    ? Stream.empty() 
    : Stream.of(s.toUpperCase()));

// mapMulti — без создания промежуточных Stream
stream.<String>mapMulti((s, consumer) -> {
    if (!s.isEmpty()) {
        consumer.accept(s.toUpperCase());
    }
});
```
- `flatMap` и `Collectors.flatMapping`: `flatMapping` — downstream-collector для `flatMap` внутри `groupingBy`
```java
Map<String, List<String>> itemsByOrder = orders.stream()
    .collect(Collectors.groupingBy(
        Order::id,
        Collectors.flatMapping(
            o -> o.items().stream().map(Item::name),
            Collectors.toList()
        )
    ));
```
- Уникальность и сортировка теряется после `flatMap`.

## Нюансы языка (Senior-level)
### **Ковариантный возвращаемый тип** при переопределении — можно вернуть подтип, но нельзя сузить тип аргумента.
**Ковариантный возвращаемый тип** — это возможность сузить (сделать более конкретным) тип возвращаемого значения в переопределённом методе подкласса. Примитивы — не ковариантны.
```java
class Animal {
    Animal reproduce() { return new Animal(); }
}

class Cat extends Animal {
    @Override
    Cat reproduce() { return new Cat(); }  // Cat — подтип Animal
}
```

Нюансы:
- Чтобы сохранить бинарную совместимость и полиморфизм, компилятор генерирует **bridge**-методы, т.е. В байт-коде существует два метода, реальный и _bridge_ метод, вызывающий реальный.
- Bridge-методы видны через рефлексию —`getDeclaredMethods()` вернёт оба
- Массивы в Java ковариантны — `String[] <: Object[]` и является источником `ArrayStoreException`.
```java
Object[] arr = new String[1];
arr[0] = 42;  // ArrayStoreException — Runtime!
```
- Ковариантность возвращаемого типа работает с _generics_:
```java
class Box<T> {
    Box<T> copy() { return new Box<>(); }
}

class StringBox extends Box<String> {
    @Override
    StringBox copy() { return new StringBox(); }  // StringBox <: Box<String>
}
```
- Ковариантность не работает для параметров **generics**:
- можно сузить _checked exceptions_ в _override_. А расширить нельзя.
- `static` методы не переопределяются — ковариантность не применима. `static` метод в подклассе — скрывает (`hides`) метод суперкласса, не `override`.
- `javap -c -p MyClass.class | grep -A5 bridge` для диагностики.


### **Затенение (shadowing)** переменных — поле и локальная переменная с одним именем.
`Shadowing` — ситуация, когда переменная с тем же именем объявлена во внутренней области видимости, и она скрывает переменную из внешней области.\
Обращение по имени внутри внутренней области относится к внутренней переменной.
Виды затенения:
- Параметр метода затеняет поле класса
- Локальная переменная в методе затеняет поле класса
- Переменная во вложенном блоке затеняет переменную во внешнем блоке. Не относится к телу цикла, тут затенения не происходит и будет ошибка компиляции.
- Параметр лямбды затеняет поле класса, но не может затенять локальную переменную того же метода, будет ошибка компиляции.

### **Статические и дефолтные методы в интерфейсах** — конфликт при множественном наследовании, правило разрешения.
#### **default методы в интерфейсах**
**Дефолтные методы:** Нужны для обратной совместимости. Java 8 добавила `forEach`, `stream()`, `removeIf` в `Collection`.\
Если бы это были абстрактные методы все существующие реализации (`ArrayList`, `LinkedList`, пользовательские) сломались бы.\
`Default`-методы позволили добавить поведение без breaking change:
- Помечены `default`
- Имеют тело.
- Не обязательны для реализации в классах.
- Реализация может переопределить default-метод.
- Неявно public. **Java 9+** можно `private`;
- Нужны для обратной совместимости.
- Взможно Множественное наследование поведения.

**Правила разрешения конфликтов**:
- метод из класса побеждает метод из интерфейса.
- более специализированный интерфейс побеждает более общий.
- Если наследуем два несвязанных интерфейса с одинаковым default методом, то требуется обязательное переопределение в наследнике.
#### **Static-методы в интерфейсах**
**Static-методы** нужны для реализации утилитарных методов, или фабричных методов, привязанных к интерфейсу.
- Помечены `static`
- Не наследуются подинтерфейсами и классами: нельзя вызвать `obj.staticMethod()`. Вызываются только как `Interface.staticMethod()`;
- Не переопределяются.
- Вызываются через имя интерфейса: `MathUtil.square(5)`.
- Неявно `public`

#### **Private-методы** в интерфейсах
**Java 9** добавила `private` и `private static` методы — для вспомогательной логики внутри интерфейса. Нужны для того, чтобы переиспользовать логику внутри дефолтных и статических методов, не выставляя её наружу.
- `private` метод не может быть `abstract`.
- `private` метод не может быть `default`.
- `private` метод не наследуется и не переопределяется.
- Может быть `static`.


### **Records (Java 16+)** — что это, неизменяемость, почему нет setter-ов, нельзя наследовать.
**Records** - специальный вид класса, созданный для хранения неизменяемых данных. Избавляет от рутинного кода по написанию сеттеров, геттеров, конструкторов и переопределения методов из `Object`.
```java
public record Point(int x, int y){}
```
превращается в `final` класс с:
- `private final` полями
- каноническим конструктором
- методами доступа с именами совпадающими с именами полей
- `equals`, `toString`, `hashCode` составленные из всех полей.
- Сеттеров нет, т.к. поля неизменяемые.

Дефолтные методы можно переопределять.
Важно понимать, что неизменяемой является сама ссылка, мы можем менять состояние объекта, например добавить элементы в массив являющийся полем.
Отлично подходят для VO, конфигураций, хранения ответов АПИ.

### **Sealed classes (Java 17+)** — зачем нужны, как работают с `permits`.
**Sealed classes** - механизм позволяющий ограничить круг наследников класса, или интерфейса заранее определённым списком.
**Для чего:**
- Исчерпывающий паттерн матчинг: компилятор точно знает все возможные подтипы и, например в новом `switch`, может проверить полноту покрытия и не требовать `default` блок.
- Безопастность, компилятор гарантирует целостность иерархии.
- Моделирование фиксированных вариантов - комманды, состояния, типы ошибок, выражения.
- Закрытые апи, где автор только контроллирует существующие реализации.

**Нюансы:**
- Ключевое слово `permits` перечисляет разрешённые подклассы.
- если наследники и сам sealed класс находятся в одном файле, то `permits` и перечисление наследников можно опустить.
- дочерний класс обязан явно указать один из трёх вариантов продолжения иерархии, он может быть: `final`, `sealed`, `non-sealed`. `non-sealed` - от него могут наследоваться как и кто угодно.
- интерфейсы работают по тому же принципу
- Подклассы обязаны быть в одном модуле.
- Sealed подход делает иерархию жёсткой, добавление нового подтипа требует больших изменений, вплоть до изменения `switch` операторов.
- Через рефлексию можно получить доступ список разрешённых подклассов.

Лучше не использовать:
- Для открытых библиотек, где пользователи должны создавать свои реализации.
- В быстро меняющихся прототипах.
- Когда нужна гибкость наследования без ограничений.


### **Pattern matching** — `instanceof` с паттерном, switch expressions по типам.
**Pattern matching** - механизм, позволяющий проверить значение на соответствие образцу и извлечь данные одним действием.\
Является эволюцией класической эволюцией `instanceof`. С вводом **Pattern matching** компилятор взял на себя проверку типа и создание переменной нужного типа.\
Во время `instanceof` можно провести деконструкцию `record` классов, и обращаться в блоке `instanceof` к полям `record` напрямую, без указания объекта.\
**Важности:**
- Переменная объявленная в паттерне, имеет строго-ограниченную область видимости блоком в котором тип уже подтверждён. Это исключает `ClassCastException`.
- Если в `switch` перебираем `sealed` иерархию, то `default` секция не нужна, компилятор сам увидит пропущенную обработку класса.\
Ошибка компиляции будет и в случае расширения `sealed` иерархии, компилятор попросит добавить новый класс во все `switch` операторы.
- В `switch` можно принять `null` без проблем, если `case` обработчик будет самым первым.
- Для небольшого количества ветвей, `switch` с **Pattern matching** компилируется в `if`/`else`, а при большом количестве могут строиться таблицы для поиска соответствия
- деконструкция работает только с `record`.
- Недостижимые `case` запрещены, т.е. `case` должны идти от узкого типа к более общему.
- `when` — дополнительное условие после.
- Компилятор проверяет generic-тип при **Pattern matching**

- **Compact Strings (Java 9+)** — `byte[]` вместо `char[]` в `String`, кодировка Latin-1 vs UTF-16, экономия памяти.
