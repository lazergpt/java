# Вопросы по PostgreSQL на собеседованиях Senior Java Developer

Подборка вопросов, которыми люди делятся после собеседований в Т-Банк (и Т1/Иннотех — там похожая школа), а также нестандартные вопросы из других компаний. В Т-Банке секция по БД живёт внутри общего технического интервью (SQL-задача + теория), а у сеньоров ещё и в code review / troubleshooting-сценариях.

## Что спрашивают в Т-Банке / Т1

### **Что такое транзакция? Может ли любая операция SQL быть в транзакции?** — про ACID, BEGIN/COMMIT/ROLLBACK. Любят копать в то, что DDL в PostgreSQL транзакционен, а `CREATE INDEX CONCURRENTLY` — нет.
**Транзакция** — логическая единица работы с БД, которая либо полностью выполняется (commit), либо полностью откатывается (rollback).\
**Гарантирует свойства ACID**:
- **Atomicity** — либо все операции применяются, либо ни одна (**ROLLBACK**).
- **Consistency** — переход из одного согласованного состояния в другое (_constraints_, _FK_, _triggers_ проверяются).
- **Isolation** — параллельные транзакции не видят промежуточных состояний друг друга (в **PostgreSQL** — уровни Read Committed по умолчанию, Repeatable Read, Serializable; Read Uncommitted фактически маппится в Read Committed).
- **Durability** — после **COMMIT** данные сохраняются (**WAL** + **fsync**).

В _PostgreSQL_ каждый SQL-запрос выполняется в транзакции.\
Особенность _PostgreSQL_ — транзакционный **DDL** (в отличие от _Oracle_/_MySQL_, где **DDL** делает _implicit_ _commit_):\
**`CREATE TABLE`**, **`ALTER TABLE`**, **`DROP`**, **`TRUNCATE`**, **`CREATE INDEX`** (не concurrent) откатываются через `ROLLBACK`.

**нельзя обернуть в явный транзакционный блок (BEGIN ... COMMIT):** будет ошибка cannot `run inside a transaction block`
- `VACUUM`
- `CREATE INDEX CONCURRENTLY` / `REINDEX CONCURRENTLY`
- `CREATE DATABASE` / `DROP DATABASE`
- `ALTER SYSTEM`

Последовательности (_nextval_) не откатываются при `ROLLBACK`, поэтому в последовательностях возможны «дыры». Это не транзакционно по своей природе.

### **Почему в PostgreSQL нет настоящего Read Uncommitted?** — фирменный вопрос про PG: минимальный уровень — Read Committed, MVCC физически не даёт прочитать «грязные» данные.
В _PostgreSQL_ уровень _Read Uncommitted_ существует формально, но фактически работает как _Read Committed_. Корень причины — архитектура **MVCC**,\
Которая не позвояет «увидеть» незакоммиченные данные.\ 
Когда транзакция изменяет строку, создаётся новая версия строки со своим _xmin_ (транзакция создавшая строку),\
а старая помечается через _xmax_(транзакция изменившая строку). Другая транзакция при чтении получает _snapshot_ и видит только те версии строк, чьи _xmin_ уже закоммичены,\
а _xmax_ — либо не установлен, либо соответствует транзакции, которая ещё не закоммичена. Незакоммиченные версии строк физически невидимы для снимка.\

Это фундаментальное свойство механизма хранения: грязные чтения просто невозможны, потому что читатель никогда не «смотрит» на версии, созданные незакоммиченными транзакциями.

### **Как работают уровни изоляции в Postgres через MVCC? От чего защищает Repeatable Read?** — snapshot isolation: фантомов нет, но при конфликтном UPDATE вы получите serialization failure и нужен retry.
В основе MVCC лежит snapshot: на момент его создания фиксируется список незакоммиченных транзакций. Любая строка, созданная транзакцией из этого списка или после него, невидима. Видны только версии, закоммиченные до снимка.
Разница между уровнями лишь в том, когда делается снимок:
1. **Read Committed (по умолчанию)** - Снимок создаётся заново для каждого отдельного оператора SQL внутри транзакции. Поэтому:
- `SELECT` видит только данные, закоммиченные до начала этого конкретного запроса.
- Два последовательных `SELECT` в одной транзакции могут вернуть разные данные, если между ними другая транзакция сделала `COMMIT`.
- `UPDATE`/`DELETE` находят строки по снимку на момент начала команды, но если строка уже изменена конкурентом — _PostgreSQL_ ждёт завершения конкурирующей транзакции, а затем перечитывает новую версию строки и применяет изменение к ней - так называемое «EvalPlanQual» перечитывание.
2. **Repeatable Read (и Serializable)** - Снимок создаётся один раз — в момент выполнения первого нетранзакционного _statement_ транзакции, и дальше не меняется до её конца. Поэтому:
- Все запросы внутри транзакции видят один и тот же срез данных, независимо от того, что коммитят другие транзакции.
- Если транзакция пытается изменить строку, которая была изменена другой транзакцией после создания снимка, она получает ошибку `could not serialize access due to concurrent update (SQLSTATE 40001)` и должна быть повторена целиком.
- Защищает от _Non-repeatable read_ - строка не «меняется» между чтениями.
- Защищает от _Phantom read_ — повторный `SELECT ... WHERE` не вернёт новых строк.
- Защищает от _lost updates_ на стороне БД — вторая попытка `UPDATE` той же строки упадёт с ошибкой `could not serialize access due to concurrent update` вместо того, чтобы молча перезаписать чужое изменение.
3. **Serializable** - Работает как Repeatable Read, но дополнительно использует Serializable Snapshot Isolation (SSI) с предикатными блокировками (predicate locks, SIReadLock),\
которые отслеживают read/write-зависимости между транзакциями и откатывают одну из них при обнаружении цикла, несовместимого с последовательным выполнением.

### **Как устроен MVCC? Что происходит со строкой при UPDATE?** — новая версия строки + пометка старой (xmin/xmax), отсюда dead tuples и разговор про VACUUM.
В основе MVCC лежит идея многоверсионности: физически в таблице могут одновременно существовать несколько версий одной и той же логической строки (кортежа).\
Каждая версия — это отдельный физический кортеж (_HeapTuple_) со служебными полями в заголовке (_HeapTupleHeader_).\
**Служебные поля версии строки**
- xmin ID транзакции, создавшей эту версию
- xmax ID транзакции, удалившей/заменившей эту версию
- ctid Указатель на следующую версию строки (страница, офсет) или на саму себя
- infomask Флаги: committed/aborted для xmin, xmax, и др.

**Что происходит при `UPDATE`**
1. На старой строке выставляется _xmax = ID_ текущей транзакции. Она становится невидимой для будущих снимков, но остаётся видимой для уже идущих транзакций со старым снимком. 
2. Рядом (или на другой странице) вставляется новый кортеж с _xmin = ID_ текущей транзакции, _xmax = 0_. 
3. ctid старой строки теперь указывает на новую. 
4. Индексы обновляются: в них появляется запись, ссылающаяся на новый кортеж.

Может отработать **HOT**-оптимизация (_Heap-Only Tuple_) -  Если при _UPDATE_ не затронут ни один индексированный столбец и на той же странице есть свободное место,\
то новая версия кладётся на ту же страницу, и записи в индексы не добавляются. Индекс по-прежнему указывает на первую версию в цепочке, а дальше идёт проход по _ctid_.\
Это экономит место в индексах и ускоряет `UPDATE`.

**Нюансы:**
- Пока транзакция «висит», _vacuum_ не может удалить мёртвые версии.

### **Зачем нужен VACUUM и autovacuum? Что будет, если его отключить?** — очистка dead tuples, карта видимости и главное: защита от переполнения счётчика транзакций (XID wraparound), когда база уходит в read-only.
`UPDATE`/`DELETE` не удаляют строки физически, а лишь помечают их удалёнными через _xmax_.\
**VACUUM** решает три задачи:
- **Освобождение места внутри страниц** — мёртвые кортежи помечаются как свободное пространство для переиспользования новыми вставками. Без этого таблица только растёт.
- **Обновление visibility map** - **VACUUM** помечает страницы как _all-visible_ (все версии на странице видимы всем) — это включает _index-only scan_ (важнейшая оптимизация для чтения) и ускоряет сам **VACUUM** в будущем.\
Также помечает _all-frozen_ страницы.
- **Заморозка (FREEZE) — защита от wraparound** - заменяет в tuple header'ах старые _xmin_ на специальное значение _FrozenTransactionId_ , чтобы они «не старели» — это защита от _wraparound_;
- **Обновляет статистику** **VACUUM** обновляет часть статистики; _ANALYZE_ (обычно вызывается вместе) — собирает статистику для планировщика (гистограммы, ndistinct, корреляции) и поддерживает _visibility_ map, которую используют _index-only scans_ и антиjoin-оптимизации.

**Autovacuum** - Фоновые воркеры, которые автоматически запускают **VACUUM** (и **ANALYZE**) по порогам. По умолчанию: `50 + 0.2 * n_live_tup`.\
Для таблицы на 10 млн строк — это 2 млн мёртвых кортежей, прежде чем придёт воркер. На больших таблицах это слишком поздно, поэтому **scale_factor** часто снижают до 0.01–0.05.\
Плюс _autovacuum_ делает _анти-wraparound vacuum_, когда **XID** приближается к критическому порогу — этот процесс нельзя отменить или прервать.

**Что будет, если отключить**
1. **Bloat** — таблицы и индексы растут от неактуальных версий, `seq scan` и `index scan` замедляются, дисковое пространство утекает.
Активные OLTP-таблицы с частым **UPDATE** могут раздуться в десятки раз.
2. **Деградация index-only scan** — visibility map не обновляется, планировщик перестаёт использовать index-only scan → рост I/O
3. **Wraparound** — самое опасное. Когда счётчик XID подходит к пределу, **PostgreSQL:**
- сначала пишет предупреждения в лог;
- затем блокирует запись (! на сервере, _ERROR: database is not accepting commands_);
- после — переводит кластер в read-only.

### **Что такое bloat и как с ним бороться?** — разрастание таблиц; отличить обычный VACUUM (возвращает место внутрь таблицы) от VACUUM FULL (эксклюзивная блокировка) и pg_repack.
**Bloat** — физическое раздувание таблиц и индексов устаревшими данными, которые уже не видны ни одной транзакции, но место занимают.\
**Причины:**
- _Autovacuum_ не успевает за потоком `UPDATE`/`DELETE`. Типично для горячих таблиц с частыми обновлениями.
- **Долгие транзакции**: любой живой снапшот (idle in transaction, долгий `SELECT`, реплика с `hot_standby_feedback`) запрещает `vacuum` чистить версии старше себя — это главный «производитель» `bloat` на практике;
- Горячие обновления без **HOT**: при обычном `UPDATE` без **HOT** во все индексы пишутся новые записи, старые помечаются мёртвыми.\
Пока не сработает _index vacuum_ / _cleanup_, они занимают место и продолжают попадать в сканы (кэш-эффективность падает).

**Как обнаружить**
Самый точный способ — расширение _pgstattuple_, которое читает все страницы и показывает реальный процент мёртвых кортежей и свободного места:
```openidepostgresql
CREATE EXTENSION pgstattuple;
SELECT * FROM pgstattuple('your_table');
```

**Как бороться - Профилактика**
1. Тюнинг _autovacuum_ на горячих таблицах - Дефолтный _autovacuum_vacuum_scale_factor = 0.2_ означает, что для таблицы в 10 млн строк autovacuum запустится только после ~2 млн мёртвых строк.\
Для «горячих» таблиц задают per-table параметры:
```openidepostgresql
ALTER TABLE hot_table SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold = 1000,
  autovacuum_vacuum_cost_limit = 2000
);
```
2. **Избавляться от долгих транзакций / курсоров**. Мониторить `pg_stat_activity` на `idle in transaction` и `age(backend_xid)`.
3. **fillfactor — снижение bloat от UPDATE.** Для таблиц с частым `UPDATE` уменьшение `fillfactor` (например, до 70–90) резервирует место на странице под обновлённые версии, позволяя `UPDATE` класть новую версию на ту же страницу (HOT-update) и не плодить лишние страницы\
Важно: `fillfactor` помогает только от `UPDATE`, но не от `DELETE` — мёртвые кортежи от удалений всё равно копятся до `vacuum`.
4. По возможности проектировать под HOT-обновления: не менять индексированные столбцы
5. **партиционирование** - Если таблица подвержена массовым `DELETE` - партиционирование позволяет вместо `DELETE` делать `DROP PARTITION` — это мгновенная операция, которая вообще не создаёт _bloat_ и не требует _vacuum_.

**Как бороться с уже существующим bloat**
1. **VACUUM** - блокировка только на запись, место не возвращается ОС, только помечает страницы свободными для переиспользования **СУБД**. Использовать всегда для профилактики.
2. **VACUUM FULL** - **ACCESS EXCLUSIVE** полная блокировка таблицы на всё время работы. Место возвращается ОС. Использовать с маленькими таблицами. В продакшене на большой таблице - почти всегда ошибка
3. **pg_repack** - Блокировка только на старте и в конце (секунды). Место возвращается ОС. переписывает таблицу и индексы онлайн, без длительного простоя. Используется в Проде на больших таблицах.


### **Почему индекс может не использоваться?** — низкая селективность, функции над колонкой (`UPPER(email)`, `DATE(created_at)`), маленькая таблица дешевле читать seq scan. Ждут, что скажете про EXPLAIN ANALYZE и расхождение estimated/actual rows.
1. **Низкая селективность.** Индекс эффективен, когда нужно достать небольшую долю строк таблицы. Если нужно прочитать >5–15% таблицы, последовательное чтение дешевле, \
но `PostgreSQL` склонен выбирать _Seq Scan_ даже при селективности ниже _5–10%_ — он довольно пессимистичен в оценке выгоды индексов.

**Диагностика:** **EXPLAIN ANALYZE** — сравниваем _rows_ в оценке планировщика и в _actual rows_. Если _actual_ сильно больше _estimated_, проблема может быть не только в селективности, но и в статистике. 
2. **Маленькая таблица** - Если таблица занимает несколько страниц, _seq scan_ дешевле любого индекса просто из-за отсутствия накладных расходов на обход _B-tree_.
3. **Устаревшая или неполная статистика**. Планировщик оценивает селективность по статистике (`pg_statistic`), которую собирает **ANALYZE**.\
Если данные массово вставили, удалили или обновили, а _ANALYZE_ не запускался, оценки количества строк становятся неверными — и планировщик может «не увидеть» выгоду индекса.
4. **Использование обычного индекса, вместо функционального.** Если у нас индекс по колонке _created_at_, а в условии мы используем `date_trunc('day', created_at)`, то обычный индекс бесполезен.
5. **Неявное приведение типов** Колонка _varchar_, а в запросе передали _integer_. Решается передачей правильного типа, или явным приведением константы(не колонки) к нужному типу `WHERE device_id = '12345678'::varchar`.
6. **LIKE с префиксным шаблоном** - `WHERE name LIKE '%abc'` тут обычный индекс не поможет. Для %abc нужен _pg_trgm + GIN_.
7. **`WHERE a = 1 OR b = 2`** — индекс по _a_ не поможет, если нет индекса по _b_ (тогда возможен _BitmapOr_)
8. **`WHERE status != 'deleted'`** — с большой долей вероятности будет низкая селективность, планировщик предпочтёт _seq scan_.
9. _random_page_cost_ по умолчанию завышен для **SSD**, т.к расчитан на **HDD** (по умолчанию 4, для **SSD** ставят 1.1–1.5), из-за этого планировщик «боится» случайных чтений и выбирает _seq_.
10. Раздутый индекс (_index bloat_) Индекс физически большой(много мёртвых записей после массовых _UPDATE_/_DELETE_)), обход дорогой.\
Планировщик может посчитать, что проще прочитать таблицу целиком. Если после _REINDEX_ индекс снова начинает использоваться — это верный признак того, что дело было в _bloat_.

**Решение:** настроить более агрессивный _autovacuum_ для таблицы/индекса или выполнить `REINDEX INDEX CONCURRENTLY index_name`.
11. Запрос на диапазон по нескольким колонкам, а индекс составной в неправильном порядке. _INDEX (a, b, c)_ не поможет для `WHERE b = 1 AND c = 2` без _a_

**Диагностика в целом:**
- _Seq Scan_ vs _Index Scan_ / _Index Only Scan_ / _Bitmap Index Scan._
- _rows_ (оценка) vs _rows_ (факт) — расхождение → статистика.
- _Buffers_: _shared hit_/_read_ — реальный _I/O_.
- _Filter_: ... и Rows Removed by _Filter_ — если много строк отфильтровано после чтения, индекс не сработал как предикат.
- pg_stat_user_indexes — проверить, использовался ли индекс хотя бы раз (`idx_scan`). Если `idx_scan = 0` и индекс не нужен для `constraint` — возможно, его стоит удалить.

### **Кейс: навесили индексы на все поля — запись стала медленнее.** — каждый индекс удорожает INSERT/UPDATE, тормозит VACUUM; индексы только по паттернам запросов.
Каждый `INSERT`/`UPDATE`/`DELETE` в _PostgreSQL_ обязан поддерживать в актуальном состоянии все индексы таблицы.\
Индекс — это не «бесплатная» структура только для чтения; это дополнительная работа при каждой записи.

- `INSERT` Вставляет запись в каждый индекс
- `UPDATE` Если затронута индексированная колонка → удаляет старую запись из индекса + вставляет новую. Без HOT — во все индексы
- `DELETE` Помечает записи во всех индексах как мёртвые (физически удаляет _VACUUM_)

Каждый индекс это:
- **Дополнительный I/O**: каждый индекс — отдельные страницы, которые надо прочитать, разбить, записать.
- **Больше WAL**: каждая запись в индекс генерирует WAL-запись. Репликация и checkpoint становятся тяжелее.
- **Больше блокировок на страницах индекса** при конкурентной записи.
- **Отключается HOT-оптимизация: если индекс покрывает колонку**, которая меняется при _UPDATE_, новая версия строки не может быть «только в heap» — надо лезть в индекс.
- **Autovacuum теперь должен чистить мёртвые записи не в одном индексе**, а в десяти. Не успевает → index bloat на всех индексах.
- Размер таблицы на диске растёт.
- Планировщик тратит больше времени на выбор плана. Но это мелочь.

**Что делать:**
- **смотрим в `pg_stat_user_indexes` какие индексы реально используются**. **Но осторожно:** возможно, запрос редкий, но критичный (например, ночной/ежемесячный батч).
- Удалить неиспользуемые.
- Проверить дублирование. Индекс _(a, b)_ покрывает запросы также и по чистому (a)
- **Для высоконагруженных таблиц:** Рассмотреть частичные индексы: `CREATE INDEX ... WHERE status = 'new'` вместо полного.
- **Для высоконагруженных таблиц:** Рассмотреть покрывающие индексы (`INCLUDE`), чтобы избежать лишних отдельных индексов.

Если нужен и индекс на чтение, и быстрая запись, можно сделать индек только на реплике попробовать.

### **Как надёжно сохранить данные и отправить событие в Kafka, если транзакция может откатиться?** — Transactional Outbox, идемпотентный consumer, Saga. На System Design в Т-Банке почти всегда всплывает идемпотентность платёжных операций.
**Суть проблемы:** Нельзя атомарно закоммитить в _PostgreSQL_ и отправить в _Kafka_ одной транзакцией — это разные системы.

**Решение:**
1. **Transactional Outbox** - событие пишется в ту же БД и ту же транзакцию, что и бизнес-данные. Отдельный процесс асинхронно забирает события из _outbox_ и публикует в _Kafka_.
- Пишем в одной транзакции и в основную таблицу, и в outbox таблицу. 
- Джоба достаёт из outbox таблицы `SELECT ... FROM outbox WHERE published = false LIMIT 100 FOR UPDATE SKIP LOCKED` → отправка в _Kafka_ → `UPDATE published = true`.
- Вместо рукописной джобы может быть(предпочтительно!) _Debezium + PostgreSQL logical replication_ который читает **WAL** и превращает вставки в _outbox_ в события _Kafka_ без _polling_. \
     **Плюсы:** \
           минимальная latency, нет нагрузки от polling\
  порядок событий по WAL\
  Debezium сам управляет _offset_ в Kafka.\

- Гарантия: _at-least-once_. Потребитель в _Kafka_ должен быть идемпотентным, т.к. транзакция джобы тоже может упасть и повториться.
2. **Упрощённый Transactional Outbox** - простая система с небольшой нагрузкой
- Пишем в БД нашу бизнес сущность.
- После коммита отправляем в _Kafka_.
- Если отправка упала — ретрай с экспоненциальной задержкой.
- В таблице храним `event_sent = false`, фоновый джоб ретраит.



**Нюансы:**
- `outbox` растёт. Используем партиционирование по дате + `DROP PARTITION`, периодический _DELETE published_-строк, или TTL.
- `Kafka transactions (exactly-once)` применимы только внутри `Kafka` (consume-transform-produce с `transactional.id`). Они не решают атомарность `Postgres+Kafka`.
- Идемпотентность на стороне консьюмера обязательна
- Двухфазный коммит нежелательно, т.к. плохо масштабируется, висящие транзакции при отвале координатора.
- `FOR UPDATE SKIP LOCKED` в поллере — чтобы несколько инстансов сервиса не конфликтовали.
- **что если outbox растёт быстрее, чем публикуется?**» — мониторинг backlog'а, шардирование воркеров, _partitioning outbox_ по времени, алерт на разрыв между created_at и моментом публикации.
- **At-least-once — реалистичная гарантия.** Exactly-once между БД и Kafka без дедупликации невозможен.
- **exactly-once** - Outbox + идемпотентный потребитель + дедупликация по _event_id_

### **UUID vs Long/Bigserial для PK — что выбрать и почему?** — размер, случайность вставок в B-tree, фрагментация. Любят обоснование через производительность.
1. **UUID** 
- **UUID v4** - плохой вариант\
  ✅ - Легко генерировать на стороне клиента/сервиса \
  ✅ - Позволяет слить данные из разных БД \
  ✅ - Скрывает к-во записей, номера соседних записей, время создания и **MAC адрес** \
  ❌ - абсолютно случайный, плохо подходит для индекса в БД\
  ❌ - Вставка в B-tree на случайную страницу, соответственно запись в индекс раскидана по диску и вызывает случайный **I/O**\
2. **UUID v7** - лучший варик. Доступен с _Java 26_ и _PostgreSQL 18_.
   ✅ - Скрывает к-во записей, номера соседних записей, **MAC адрес**. Время создания не скрывает \
   ✅ - распределённая генерация + монотонность по времени. \
   ✅ - Вставки в B-tree идут почти последовательно → нет массовых page split. \
   ✅ - Слияние данных из нескольких систем. \
   ❌ - Больше места занимает чем **BIGSERIAL**\
3. **BIGSERIAL**
   ✅ - Занимает минимум места, что сказывается на размере индексов, PK/FK, кэш-эффективности \
   ✅ - Генерируется в БД \
   ❌ - Если генерим в сервисе/на клиенте нужна координация\
4. **UUID + BIGSERIAL** - Используется **BIGSERIAL** для PK в БД и внутри сервиса, а в наружных **АПИ** торчит **UUID**.

### **Что такое распределённая транзакция и как обходиться без неё?** — Saga, eventual consistency, outbox.
1. **2PC (two-phase commit) с координатором** - Классическая реализация:
- **Prepare:** координатор спрашивает всех участников: «Готовы закоммитить?» Каждый блокирует ресурсы и отвечает «да/нет».
- **Commit / Abort**: если все сказали «да» — координатор говорит «коммит». Если хотя бы один «нет» — «откат».
  ✅ - Генерируется в БД \
  ❌ - Блокировки на время между фазами. Ресурсы каждого участника заблокированы, пока координатор собирает ответы. При высокой нагрузке — пулы коннектов, строки, таблицы стоят.\
  ❌ - Если координатор упал, то транзакция зависает\
  ❌ - Доступность всех участников обязательна. Один сервис в деплое — вся транзакция невозможна.\
  ❌ - не поддерживается большинством брокеров/_NoSQL_\
2. **Saga** — Длинная бизнес-транзакция разбивается на цепочку локальных транзакций. Каждая завершается публичным событием. При ошибке на шаге N — выполняются компенсирующие транзакции в обратном порядке.\
Есть два вида оркестрации:
- Хореография - нет центрального узла
- Оркестрация - Центральный оркестратор (например, Camunda, Temporal) управляет шагами

**Ключевое требование:** каждый шаг и каждая компенсация идемпотентны. События могут доставиться повторно.

3. **Transactional Outbox** (для «БД + брокер») - бизнес-данные и событие пишутся в одной локальной транзакции в БД, публикация — отдельным _relay_ (_Debezium_ / _polling_).\
Атомарность Postgres+Kafka заменяется на _at-least-once_ + идемпотентный консьюмер.

### **Почему CREATE INDEX CONCURRENTLY нельзя выполнять в транзакции?** — и чем грозит обычный CREATE INDEX на проде: блокировки записи, долгие очереди на нагруженных таблицах.

**Как работает CREATE INDEX CONCURRENTLY**
1. **Фаза 1.** Берётся снимок активных транзакций. Строится индекс в состоянии _invalid_ по текущим данным. Берётся блокировка `SHARE UPDATE EXCLUSIVE` (не блокирует запись, только **DDL**).\
Это нужно, чтобы все новые транзакции видели: «индекс существует, в него надо писать»
2. **Ожидание.** Ждём, пока завершатся все транзакции, которые могли видеть таблицу до начала фазы 1 и могли «не видеть» новый индекс.
3. **Фаза 2.** Повторно проходим по строкам, которые были вставлены / изменены / удалены во время фазы 1 и Достраиваем индекс.
4. **Валидация.** Индекс помечается как валидный и становится доступным для планировщика.

**Почему внешняя транзакция это ломает** - Если вы обернёте `CREATE INDEX CONCURRENTLY` в явный блок `BEGIN … COMMIT`, _PostgreSQL_ не сможет выполнить эти внутренние коммиты,\
потому что все изменения уже находятся в рамках одной внешней транзакции. Как следствие, СУБД отказывается выполнять команду с ошибкой `CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.\
По сути, `CREATE INDEX CONCURRENTLY` — это не одна атомарная **DDL**-команда, а последовательность из нескольких транзакций, которые не могут быть вложены во внешнюю транзакцию.\
Именно поэтому его также нельзя вызывать из функций, которые неявно выполняются в транзакции.

**Нюансы:**
- Он может упасть с _invalid index_ — если во время фаз ожидания кто-то упал или возник _deadlock_/error, индекс остаётся в состоянии **INVALID** и его надо дропнуть (`DROP INDEX CONCURRENTLY`) и построить заново.\
Мониторить через _pg_index.indisvalid_
- Он медленный: два полных скана таблицы плюс ожидания — на больших таблицах часы
- Он ждёт долгие транзакции
- в **Liquibase** ставим `runInTransaction="false"`

### Отличие **CREATE INDEX CONCURRENTLY** и **CREATE INDEX**: 
1. **CI** бысрее(одно сканирование таблицы), но с блокировкой на модификацию данных. На больших таблицах блокировка записи может длиться минуты или даже часы.
2. **CIC** - медленнее(два прохода и ждём окончания транзакции начавшихся до старта создания индекса), но без остановки записи.

### **Может ли запрос использовать два индекса сразу?** — Bitmap Index Scan, BitmapAnd/BitmapOr.
Да, благодаря Механизму — _Bitmap Index Scan_, но целенаправленно спроектированный индекс всегда лучше при частом использовании

**Как работает:**
- каждый индекс сканируется, и возвращает набор **TID** (identifiers строк: страница + офсет). Из них строится битовая карта страниц. \
- **Потом битмапы комбинируются:**\
   **BitmapAnd** — для `WHERE a = 1 AND b = 2` (пересечение).\
   **BitmapOr** — для `WHERE a = 1 OR b = 2` (объединение).\ 
- Затем _Bitmap Heap Scan_ читает _heap_-страницы в физическом порядке, а не в порядке индекса. Это превращает случайный _I/O_ в почти последовательный.

Для запроса
```openidepostgresql
SELECT * FROM orders WHERE customer_id = 42 AND status = 'ACTIVE';
-- индексы: (customer_id) и (status)
```
получаем план 

```markdown
BitmapAnd
  -> Bitmap Index Scan on idx_orders_customer   (customer_id = 42)
  -> Bitmap Index Scan on idx_orders_status     (status = 'ACTIVE')
-> Bitmap Heap Scan on orders
```

**Почему не «два Index Scan»?** - два _Index Scan_ дают *random heap access* и дублирование чтения страниц;\
_BitmapAnd_ дешевле за счёт компактного битмапа и упорядоченного _heap_-доступа. Поэтому для пересечения индексов **PG** всегда идёт через _bitmap_.

**Два индекса в разных ветках плана** - Это встречается постоянно и не требует bitmap:
- **Nested Loop Join** — внешняя таблица через Index Scan, внутренняя через Index Scan по FK-индексу;
- **Merge Join** — обе стороны через Index Scan (отсортированы индексом);
- **Партиционирование** — Append из нескольких партиций, каждая через свой индекс;
- **UNION/UNION ALL подзапросов** — каждая ветка использует свой индекс;
- **Parallel Append / Parallel Index Scan** — параллельные воркеры сканируют индексы;
- **Self-join одной таблицы с разными условиями** — два индекса на одну таблицу в разных узлах.

**Нюансы:**
- Битмап строится в _work_mem_, при переполнении становится _lossy_ с _Recheck Cond_
- Для очень селективных запросов планировщик предпочтёт один обычный _Index Scan_
- Составной индекс лучше, чем _Bitmap_
- Составной индекс не подходит для OR (кроме ведущей колонки), тут _BitmapOr_ — легитимное решение.\
Когда вы пишете запрос с `OR`, планировщику нужно найти строки, соответствующие любому из условий: `WHERE col1 = 'A' OR col2 = 'B'`\
      * Если искать по col1, индекс может помочь найти все значения 'A'.\
      * Но индекс не может помочь найти все значения 'B' по второму столбику, потому что они разбросаны по всему дереву (в каждой группе первого столбца).\
Чтобы выполнить такой запрос через составной индекс, базе данных пришлось бы просканировать весь индекс целиком, что лишает его всякого смысла.


### **Как ускорить поиск по LIKE '%текст%'?** — обычный B-tree не помогает, нужны pg_trgm и GIN/GiST, functional index по `lower(name)`, text_pattern_ops для префиксного поиска.
_B-tree_ не подходит, т.к. он упорядочен по началу. Но подходит для `LIKE 'текст%'`
1. Основное решение: _trigram_-индексы (_pg_trgm + GIN_)\
   Расширение _pg_trgm_ разбивает строку на последовательности из трёх символов (триграммы). Например, слово _'cat'_ превращается в набор `{' c', ' ca', 'cat', 'at '}`.\
Индекс по этим триграммам позволяет СУБД быстро находить кандидатов, содержащих искомую подстроку, даже если она находится в середине текста.
```openidepostgresql
-- 1. Включаем расширение (один раз для базы данных)
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- 2. Создаём GIN-индекс
CREATE INDEX idx_notes_content_trgm ON notes USING GIN (content gin_trgm_ops);
```
**Почему GIN, а не GiST?** - У pg_trgm есть два типа индексов: **GIN** и **GiST**.
- **GIN** читается примерно в 10 раз быстрее **GiST**, что идеально для _read-heavy_ сценариев. Точный индекс.\
Для каждого уникального элемента (слова в тексте, ключа в JSON, числа в массиве) индекс хранит список всех строк, где этот элемент встречается.
- **GiST** быстрее обновляется и занимает меньше места, поэтому подходит для таблиц с очень частой записью, но поиск по нему медленнее и может требовать перепроверки на heap (_lossy index_).\
Является сбалансированным деревом, которое хранит не сами элементы, а их «сигнатуры» (упрощенные представления)

**Нюансы:**
- Короткие паттерны. Если искомая подстрока короче 3 символов (например, `LIKE '%a%'`), триграмма не формируется, и **GIN**-индекс может деградировать до полного сканирования,
что сведёт на нет весь выигрыш. Для таких случаев нужны другие подходы (например, полнотекстовый поиск, если это поиск по словам, или специализированные решения).
- **pg_trgm** — это не полнотекстовый поиск. Он не выполняет стемминг (не приводит слова к основе), не учитывает стоп-слова и морфологию.
2. **Полнотекстовый поиск (_tsvector_)** - Если задача — искать слова, а не произвольные подстроки.
- ✅ Быстрее и семантичнее(морфология) для слов
- ❌ не находит произвольные подстроки внутри слов — «%провод%» внутри «беспроводные» _tsvector_ не найдёт.
3. **Внешний поисковый движок** - _Elasticsearch_\
   Синхронизация из _PostgreSQL_ через _CDC_ (Debezium → Kafka → ES) или через _pg_logical_replication_, .\
Это уже отдельная инфраструктура, но для продакшен-поиска по миллионам записей — стандарт.

**общие Нюансы:**
- если все поиски с якорем справа: `LIKE '%текст'` то можно завести колонку _reverse(name)_ с индексом
- Перед тем как вешать триграммный индекс на таблицу с миллионами строк — проверить размер и время записи в стейджинге. **GIN**-индекс на текстовой колонке может быть сопоставим с размером самой таблицы.
- LIKE 'абв%' индексируется btree
- **GIN** по триграммам — обычно 2–4× размера текстовой колонки. На миллиардах строк это терабайты — ещё один аргумент за внешний поисковый движок;
- hot-таблица + GIN-триграммы = заметное замедление UPDATE (возвращаясь к кейсу про индексы на всё). Компромисс — индексировать отдельную таблицу-проекцию с текстом, а не основную;

**почему GIN медленнее на записи?** -  одно значение текста разворачивается в множество ключей триграмм, при UPDATE перестраиваются записи по всем изменившимся ключам.

### **Когда B-tree vs GIN vs BRIN?** — B-tree для равенства и диапазонов, GIN для JSONB/массивов/полнотекста, BRIN для больших append-only таблиц по времени.
1. **B-tree** - Для данных, которые можно отсортировать (числа, строки, даты). \
**Где ок и не ок:**
- ✅ Равенства (_=_)
- ✅ Диапазонных запросов (_<, >, BETWEEN_)
- ✅ Проверок на _NULL_
- ✅ Поиска по префиксу (`LIKE 'foo%'`)
- ✅ Сортировки (`ORDER BY`) — это единственный тип индекса в _PostgreSQL_, который может напрямую выдавать отсортированные данные, избавляя от явной сортировки.
- ❌ неэффективен для составных типов данных (JSONB, массивы)
- ❌ для поиска по подстроке с ведущим wildcard (`LIKE '%foo%'`)
2. **GIN (Generalized Inverted Index)** - Инвертированный индекс: для каждого элемента (триграммы, лексемы, ключа JSONB, элемента массива) хранится список строк БД, где он встречается.\
   **Где ок и не ок:**
- ✅ **JSONB**: для операторов `@>`, `?`, `?|`, `?&`
- ✅ **Массивы**: для операторов `&&`, `@>`, `<@`
- ✅ **Полнотекстовый поиск:** для _tsvector @@ tsquery_
- ✅ Поиск по подстроке (_pg_trgm_): для `LIKE '%...%'` и нечёткого поиска.
- ✅ Быстрый поиск
- ❌ дорогая запись: каждая вставка/обновление меняет множество записей в индексе.
- ❌ Размер: может быть сопоставим с таблицей или больше.

**Цена:** GIN-индексы медленнее обновляются и занимают больше места, чем B-tree. Это делает их идеальными для данных, которые чаще читают, чем пишут (static data).
3. **BRIN** (**Block Range Index**) не хранит указатель на каждую строку. Хранит по зонам страниц (по умолчанию 128 страниц на блок) min/max значения колонки.\
Идея: если физический порядок строк коррелирует с порядком колонки, то по «это зона со временем между `10:00 и 10:05`» можно отсеять `99.9%` таблицы.\
Используется когда таблица огромная, и данные в ней физически упорядочены по индексируемому столбцу (высокая корреляция).
- ✅ _Размер:_ в тысячи раз меньше B-tree. Для таблицы на миллиард строк — мегабайты вместо гигабайтов.
- ✅ Поиск: сканируем только те блоки, где диапазон пересекается с условием.
- ✅ Почти бесплатная запись: при append-only данных новые min/max просто дописываются;
- ❌ lossy index (неточный).
- ❌ Если данные в таблице физически не упорядочены (например, после массовых обновлений), **BRIN** становится бесполезен.

со временем корреляция может деградировать (бэкфил-инсерты, UPDATE-ы) — у BRIN есть _pageinspect_-диагностика и _WITH_ (autosummarize = on).

4. **GiST** — пространственные данные и nearest-neighbor».

**а если данные не append-only и BRIN уже деградировал?** - пересоздание индекса возвращает корреляцию, _autosummarize_ помогает частично;\
альтернатива — партиционирование по времени, где каждая партиция маленькая и обычный btree в неё влезает.

### **Что такое HOT-обновление и fillfactor?** — версия строки укладывается на ту же страницу, индексы не трогаются. Работает, если обновляемые колонки не индексированы и на странице есть запас.
При обычном `UPDATE` новая версия строки вставляется в таблицу и каждый индекс получает новую запись, указывающую на неё.
C **HOT** _UPDATE_ может положить новую запись на ту же страницу и не обновлять индексы, а поле _ctid_ старой записи будет указывать на новую.\
Индекс хранит ссылку на старую запись, а по _ctid_ может найти новую запись.\
**Но для **HOT** должны соблюдаться условия:**
- Ни одно из обновляемых полей не должно входить ни в один индекс таблицы.
- Новая версия помещается на ту же страницу, что и старая (есть свободное место)

**Это даёт:**
- Нет записи в индексы → меньше WAL, быстрее _UPDATE_, меньше _bloat_ индексов.
- Меньше random **I/O**.
- Меньше работы для _autovacuum_.

смотреть можно в таблице _pg_stat_user_tables_ по формуле.

**fillfactor** - процент заполнения страницы при вставке (по умолчанию 100 для таблиц, 90 для индексов _btree_).\
Оставленное свободное место — резерв для **HOT**-обновлений.
- **90-100** - орошо для append-only / read-only таблиц (логи, события, справочники)
- **70–90** — для таблиц с частым _UPDATE_ неиндексируемых полей: резервируем место под HOT-обновления.

**Нюансы:** 
- **Изменение fillfactor не перестраивает существующую таблицу** — применяется только к новым страницам.\
Для применения к уже существующим данным нужен _VACUUM FULL_ / _pg_repack_ / _CLUSTER_.
- Для индексов с random-вставками (**UUID v4**) низкий _fillfactor_ бесполезен — вставки всё равно идут в произвольные места
- ❌ Таблица занимает больше места (на 10–20%).
- ❌ Больше страниц → больше чтения при seq scan.
- ❌ Больше страниц в buffer cache.
- иногда вместо добавления индекса на часто меняющуюся колонку имеет смысл вынести её в отдельную таблицу 1:1
- _fillfactor = 70_ «на всякий случай» — ошибка. Ставить осознанно под конкретный паттерн нагрузки.

**Как проверить, что HOT работает**
- `EXPLAIN (ANALYZE)` с heap tup updated-метриками и `Buffers`: `shared hit` — HOT даёт почти нулевой shared read при повторных `UPDATE`
- Доля **HOT** через _n_tup_hot_upd_ в _pg_stat_user_tables_».

### **Почему длинная транзакция опасна для базы?** — удерживает снапшот, мешает VACUUM чистить dead tuples → bloat. Ждут знание `pg_stat_activity` и `idle in transaction`.
Для **OLTP** больше минуты уже долго.

1. Блокируется **VACUUM** - он не может удалить ненужные кортежи, пока существует хотя бы одна транзакция со снимком, в котором эти кортежи ещё видны.
2. Держит блокировки - `SELECT ... FOR UPDATE / FOR SHARE` блокирует строки.
3. DDL внутри транзакции (`ALTER TABLE`) может держать **ACCESS EXCLUSIVE** на таблицу(блокируется даже _SELECT_).
3. _idle in transaction_ - Приложение открыло транзакцию, сделало запрос и ушло думать (ждёт внешнего API, считает в коде, спит), в этом слчае соединение простаивает, но недоступно другим.\
   Снапшот, блокировки, коннекшен удерживаются. Состояние в _`pg_stat_activity = idle in transaction`_
4. _CREATE INDEX CONCURRENTLY_ ждёт завершения долгих транзакций на таблице (его два сканирования должны видеть «стабильное» состояние).
5. _Repeatable Read_/_Serializable_ долгая транзакция с большей вероятностью получит _serialization failure_ (40001) и откатится целиком — вся работа впустую, плюс _retry_. Чем дольше транзакция, тем выше шанс конфликта.

**Как бороться:**
- **idle_in_transaction_session_timeout** — снимает сессии, забытые в _idle in transaction_. Обязателен в проде.
- **statement_timeout** — ограничивает отдельные запросы.
- **lock_timeout** — не даёт висеть в ожидании лока бесконечно.
- **Короткие транзакции:** не держать `@Transactional` вокруг **HTTP**-вызовов
- **Batch-операции** — чанками, с коммитом между чанками, а не одной гигантской транзакцией на миллион строк.
- **Мониторинг:** `pg_stat_activity (state = 'idle in transaction', xact_start)`, алерт на транзакции дольше N секунд

### **Когда партиционировать таблицу?** — сотни миллионов строк, фильтрация по ключу партиции, partition pruning. И что партиционирование не заменяет индексы.
**Когда нужно:**
- **Таблица большая и продолжает расти.**  _В доке_: партиционирование имеет смысл, когда размер таблицы превышает объём оперативной памяти сервера. В инете - >100 ГБ или >20–50 млн строк.\
  Если таблица целиком помещается в _shared_buffers_/_page cache_, выигрыша от партиционирования почти не будет.
- **Запросы всегда фильтруют по ключу партиционирования**. Планировщик делает _partition pruning_ — отсекает нерелевантные партиции на этапе планирования.\
Если запросы не содержат ключ партиционирования — сканируем все партиции → хуже, чем одна таблица.
- **Данные имеют естественный жизненный цикл**. Логи, события, метрики: данные живут 90 дней, потом удаляются - удобно удалять целыми партициями.
- **Разные требования к хранению** - Горячие данные на **SSD**, холодные на **HDD**. Разные настройки _fillfactor_, разные параметры _autovacuum_ на разных партициях.
- **где autovacuum не успевает за запись**. После партиционирования каждая партиция имеет свой _vacuum-cycle_, и _load_ размазывается.

**Как выбрать ключ:**
- по времени
- по региону
- категории
- тенанту

**Когда партиционирование не поможет или навредит**
- **Запросы без ключа партиционирования** — full cross-partition scan работает хуже, чем seq scan по одной таблице
- **Слишком много партиций** — документация _PostgreSQL_ не рекомендует создавать сотни партиций: это ведёт к росту времени планирования запросов и избыточному потреблению памяти
- **Небольшие таблицы**

**Нюансы:**
- **Индексы у каждой партиции отдельные**
- **Автоматическое создание партиций**: через _pg_partman_ или скрипт/крон. Без него вставка в несуществующий диапазон → ошибка.
- **DEFAULT-партиция**: ловит данные, не попавшие ни в один диапазон. Не должна разрастаться — это сигнал, что партиции не создаются вовремя.
- **EXPLAIN**: проверять, что _Partition Pruning_ реально работает, Иначе партиционирование бесполезно.
- **UPDATE ключа партиционирования**: в PG 11+ строка автоматически переезжает между партициями (row movement), но это дороже обычного _UPDATE_.
- Ключ партиционирования обязан входить в _PRIMARY KEY_ и все _UNIQUE_-констрейнты.
- FK из других таблиц на партиционированную — поддерживается (PG 12+), но с оговорками по производительности;

**Миграция существующей таблицы**
- **Dump & Restore**. Создаём партиционированную таблицу, создаём дамп, меняем в нём `CREATE TABLE` на новую структуру и равзворачиваем дамп
- **Атомарное переименование** - Создать новую партиционированную таблицу _new_table_, Создать необходимые партиции для _new_table_,\
Скопировать данные через `INSERT INTO _new_table_ SELECT * FROM old_table;`, переименовать новую таблицу в старую.
- **ATTACH PARTITION** - создать пустую партиционированную «родительскую» таблицу, Для каждого диапазона создать временную таблицу, \
  Перенести туда данные, Прикрепить её как партицию, Повторить для всех исторических данных, в конце переименовать таблицы.
- **Logical Replication** - Используется для таблиц на сотни гигабайт и терабайты. 
1. Создать новую партиционированную БД/таблицу.
2. Настроить Logical Replication с источника на новую таблицу.
3. Дождаться синхронизации исторических данных (это может идти днями, но сервис работает).
4. В момент синхронизации остановить запись на 1-2 минуты, дать репликации догнать хвост транзакций и переключить приложение на новую БД.

### **Streaming vs logical репликация — разница и когда что?** — WAL-стриминг точной копии против репликации отдельных таблиц с трансформацией.
1. **streaming replication** - это побайтовое копирование всего кластера через **WAL**. \
Master сервер пишет **WAL**, _standby_ получает его по потоку (**walreceiver** → **wal sender**) и применяет блоки поверх своих файлов — по сути, воспроизводит те же физические операции, что происходят на мастере.

**Свойства:**
- Реплицируется весь _cluster_: базы, таблицы, индексы, роли, системные каталоги. Нельзя выбрать определённые таблицы и прочее
- Реплика обычно _read-only_: hot standby
- Версии: Primary и standby обязаны быть одной мажорной версии PostgreSQL.
- Обычно лучше и проще в настройке, чем логическая, так как передаётся сырой WAL без декодирования.
- Поддерживает синхронную репликацию для гарантии нулевой потери данных.

**Когда использовать:**
- high availability и отказоустойчивость
- read-реплики для разгрузки чтения
- бэкап-реплики
- rolling-обновления минорных версий.
2. **Logical Replication** - WAL проходит через логическое декодирование, превращаясь в поток строчных изменений (**INSERT**, **UPDATE**, **DELETE**) со всеми вытекающими: сработают триггеры, FK, ограничения.\
Передача идёт по модели _publish_/_subscribe_: публикация на источнике, подписка на приёмнике.
**Свойства:**
- Можно реплицировать отдельные таблицы, или даже подмножество строк через **WHERE** в публикации
- Работает между разными мажорными версиями _PostgreSQL_
- подписчик не «копия», у него могут быть свои таблицы и изменения;
- **!** Sequences автоматически нормально не синхронизируются.
- **DDL** не реплицируется
- Больше накладных расходов, чем у **physical replication**.

**Когда использовать:**
- Миграции между версиями _PostgreSQL_ с минимальным даунтаймом
- Сбор данных из нескольких БД в одну аналитическую.
- _PostgreSQL_ WAL → Debezium → Kafka - Это основа для outbox-паттерна.

**Нюансы:**
- в логической репликации конфликт (нарушение PK на подписчике) останавливает применение. В физической конфликты невозможны — потому что копия точная;
- **logical replication** живёт на **replication slot** — пока подписчик отстаёт, издатель хранит WAL → диск издателя может кончиться
- ретраи применения транзакций возможны — тот же принцип, что у консьюмеров Kafka: операции должны быть безопасно повторяемыми.

**что будет, если подписчик отвалится надолго?** - replication slot копит WAL до заполнения диска издателя; лечится мониторингом слота и, в крайнем случае, принудительным удалением слота с последующим resync подписчика.
**почему логическая репликация медленнее?** - декодирование из WAL + применение через обычные SQL-операции с триггерами и индексами против дешёвого блочного replay у физики.

### **SELECT FOR UPDATE — как работает и какие альтернативы?** — пессимистичная блокировка против оптимистичной (@Version).
**SELECT FOR UPDATE** - берёт строчную эксклюзивную блокировку на выбранные строки и держит её до конца транзакции.\
Любая другая транзакция, которая попытается **UPDATE**/**DELETE** эти строки или тоже взять **FOR UPDATE** — встанет в ожидание.\
**Виды блокировок FOR UPDATE**:
- **FOR UPDATE** — эксклюзивная: конфликтует с **UPDATE**/**DELETE**/**FOR UPDATE**; Пользуемся Когда собираемся менять ключевые поля (**PK**, поля из **UNIQUE**) или удалять строку.
- **FOR NO KEY UPDATE** — слабее: Меняем строку, но не ключевые поля
- **FOR SHARE** — разделяемая: Хотим защитить строку от изменения, но сами не меняем. «Я читаю и хочу, чтобы строка не изменилась подо мной».
- **FOR KEY SHARE** — Автоматически берётся при вставке/обновлении дочерней строки с FK. Вручную почти не нужен — объясняет, почему FOR UPDATE на родителя может блокировать вставки в дочернюю таблицу.

**Плюс модификаторы:**
- **NOWAIT** - если строчка заблокирована - не ждём, сразу кидаем `ERROR: could not obtain lock`
- **SKIP LOCKED** - пропускаем заблокированные строчки.

**Нюансы:**
- На **REPEATABLE READ** / **SERIALIZABLE** - **SELECT FOR UPDATE** ведёт себя иначе: если заблокированная строка была изменена другой транзакцией после начала вашей, вы получите ошибку сериализации (40001), а не будете ждать и читать новую версию, как в Read Committed.
- пессимистичная блокировка в **Hibernate** работает только внутри одной транзакции.

**Альтернативы:**
1. Оптимистичная блокировка через _version_ - перед обновлением читаем версию, и добавляем её в условие update,\
если обновилось 0 строчек, тогда кто-то уже обновил перед нами и нужно повторить.
2. Можно использовать уровень изоляции **SERIALIZABLE**
3. атомарный **UPDATE**

### **Что такое advisory locks?** — прикладные блокировки, не привязанные к строкам; удобно для координации воркеров.
**Advisory lock** — блокировка на произвольном целом ключе, не привязанная к строкам, страницам или таблицам.\
_Advisory lock_ нужен, когда надо защитить логический ресурс, а не конкретную строку.\
Любой, кто не проверил блокировку, спокойно обойдёт её обычным запросом. Это договорённость, а не физический барьер.


```openidepostgresql
BEGIN;

SELECT pg_advisory_xact_lock(123);

-- здесь другая сессия не сможет взять такой же блокирующий ключ

COMMIT;
```
Чем-то похожи на syncronized в Java.\
Есть две области действия:
- **Session** - живут до явного снятия(`SELECT pg_advisory_unlock(42);`) или разрыва соединения:
- **Transaction** - автоматически снимаются при commit/rollback:


**Нюансы:**
- `pg_advisory_lock()` ждёт бесконечно. Обязательно задать _lock_timeout_.
- Не видно в **pg_locks** в виде «заблокированных строк» — мониторить надо отдельно
- Ценность advisory locks — нулевая стоимость в уже существующей БД и согласованность с транзакциями (xact-версии живут в той же ACID-области).\
Именно поэтому они первое, что стоит попробовать, прежде чем тащить Redis для мьютексов.

**а если приложение упало с транзакционным локом?** - снимется вместе с транзакцией при обрыве соединения; поэтому они безопаснее session-локов


### **INSERT ... ON CONFLICT и RETURNING** — upsert без гонок и получение изменённых строк одним запросом.
Вставить запись, а если есть конфликт - то сделать что-то другое/или  ничего
1. `DO UPDATE` - при конфликте обновляем `DO UPDATE SET visits = user_stats.visits + 1;`
2. `DO NOTHING` - при конфликте ничего не делать. Не триггерит триггеры.

**как узнать, был это INSERT или UPDATE?** - обычно есть колонки **created_at** и **updated_at**, по ней посмотреть. Или по технической колонке `xmax = 0`

**RETURNING** - Возвращает данные из фактически затронутых строк — вставленных, обновлённых или удалённых — в рамках той же команды. Работает с **INSERT**, **UPDATE**, **DELETE**, **MERGE** и даже с **WITH**\
Удобно, т.к. не нужен последующий **SELECT**.

**Нюансы:**
- Может вернуть _OLD.*_ и _NEW.*_ (в _UPDATE_/_DELETE_/_MERGE_) — значения до и после изменения;
- Может вернуть отдельные колонки
- RETURNING * — все колонки.
- Нельзя вернуть строки из других таблиц (**join**) — только затронутые.
- В INSERT ... SELECT с триггерами RETURNING даёт значения после BEFORE-триггеров.
- RETURNING возвращает строки, фактически затронутые командой. При ON CONFLICT DO NOTHING конфликтующая строка не возвращается (её «не тронули»). При DO UPDATE возвращается обновлённая строка.


## SQL-задачи, которые дают на секции БД

- **Оконные функции вместо коррелированного подзапроса** — «сотрудники с зарплатой выше средней по отделу»; на Middle ждут именно вариант с окном.
- **«Топ-3 категории по выручке», «5 последних заказов каждого клиента»** — CTE + ROW_NUMBER, и понимание, почему LIMIT не решает задачу.
- **«Клиенты без заказов»** — проверка LEFT JOIN / NOT EXISTS, частый минус за решение «в лоб».
- **Рекурсивный CTE** — иерархия сотрудник → менеджер.
- **Удаление дубликатов без создания новой таблицы** — с удалением всех строк, кроме минимального id.
- **GROUP BY обрабатывает NULL как?** — все NULL попадают в одну группу; ловушка на неожиданно простой вопрос.
- **RANK() vs DENSE_RANK()** — разрывы в нумерации при одинаковых значениях.
