## Теория Spring

### Чем **Spring Boot** отличается от **Spring Framework**? — стартовый вопрос: автоконфигурация, embedded-сервер, стартеры, actuator.
1. `Spring Framework` — это базовый фреймворк для Java-приложений c поддержкой **DI**, **AOP**, **транзакции**, **JDBC/JPA**, **MVC** и т.д.\
Требует ручной конфигурации (XML, Java Config) и явного управления зависимостями и сервером.
2. `Spring Boot` - это надстройка над `Spring Framework`, которая решает его главную проблему — избыточную конфигурацию.\
Spring Boot содержит:
- **Автоконфигурацию** - Boot сам конфигурирует бины по наличию в classpath, объявленным свойствам и условию (`@ConditionalOnClass`, `@ConditionalOnMissingBean`). \
С помощью ключа `-debug` или актуатор можно посмотреть `ConditionsEvaluationReport`(отчёт об инициализации приложения). Отчёт помогает диагностировать конфликты конфигурации, проблемы настройки свойств и неожинданые исключения бинов.
- **Starter-зависимости** - `spring-boot-starter-*` тянет согласованный набор библиотек, что решает проблему конфликта версий транзитивных зависимостей на стороне фреймворка.
- **Встроенный сервер** - По умолчанию упаковывает приложение в _fat jar_ с вшитым **Tomcat/Jetty/Undertow**, запуск через `java -jar` без внешнего контейнера.
- **Externalized configuration** - типа конфигурация которая может меняться из вне - `application.yml`, профили.
- **Инфраструктура** - есть готовые инструменты для продакшена - метрики, актуатор с health checks.
### **Из чего состоит `@SpringBootApplication` и как Boot поднимает контекст?** — три вложенные аннотации; цепочка: Environment → ApplicationContext → создание и инициализация бинов → события → embedded-сервер.
`@SpringBootApplication` — это композит из трёх аннотаций:
- `@SpringBootConfiguration` - является `@Configuration`, помечает класс как источник бинов
- `@EnableAutoConfiguration` - включает механизм автоконфигурации. Импортирует `AutoConfigurationImportSelector` который через `ImportsFiles` загружает автоконфигурации фильтруя их по условиям `@ConditionalOnClass`, `@ConditionalOnProperty`  и тд;
- `@ComponentScan` - сканирует пакет класса и подпакеты

**Как Boot поднимает контекст:**
1. `SpringApplication.run(...)` — точка входа. Определение типа приложения (NONE/SERVLET/REACTIVE) по classpath.
2. Загрузка `ApplicationContextInitializer`(програмная инициализация контекста) и `ApplicationListener`(реакция на события).
3. Создание `ConfigurableApplicationContext` (управления жизненным циклом и конфигурацией контекста приложения)
4. создаётся `ConfigurableEnvironment`, загружаются property sources в порядке приоритета:\
**command line args** → **SPRING_APPLICATION_JSON** → **OS env** → **application-{profile}.yml** → **application.yml** → **defaults**. Активируются профили.
5. Печатается баннер
6. Создаётся `ApplicationContext` и в него помещается `Envieronment`
7. Вызов `refreshContext()`
- Создание `BeanFactory`.
- Выполнение `ComponentScan`.
- Обработка `AutoConfiguration` (на этом этапе применяются условия и регистрируются бины).
- Инстанцирование синглтонов.
8. Запуск embedded server (если Web).
9. Публикация ApplicationStartedEvent.

**Ключевой момент на собеседовании:** `SpringApplication.run()` создаёт нужный тип контекста, загружает **environment** (включая **externalized config**), сканирует компоненты,\
импортирует автоконфигурацию из `AutoConfiguration.imports` с фильтрацией `@Conditional`, затем делает `refresh()` контекста с инстанцированием синглтонов и поднимает embedded-сервер».
**Что важно для Senior:**
- Контекст поднимается в строгом порядке: сначала `BeanFactoryPostProcessor` (меняют определения бинов, например, `@ConfigurationPropertiesBinding`), потом инстанцируются сами бины, и только затем применяются `BeanPostProcessor` (меняют инстансы, например, создают прокси для транзакций).
- Если автоконфигурация мешает (например, мы хотим поднять свой пул HikariCP в нестандартном режиме), мы идем в `ConditionEvaluationReport` (выводится при старте с `--debug` или ищется в логах) и точечно отключаем её через `@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)`.
- Чтобы не ждать лишние секунды на старте, используем `@ConditionalOnClass`, `@ConditionalOnProperty` в своей автоконфигурации и Spring Boot 3 Context Indexer (генерирует `META-INF/spring.components` на этапе сборки, избавляя от рефлексивного сканирования classpath в рантайме).

### **Скоупы бинов и подводный камень с prototype внутри singleton** — singleton получает один экземпляр prototype на всё время жизни; лечится через `ObjectProvider` или proxy-скоуп.
**Скоупы в Spring:**
- **singleton** (по умолчанию) — один экземпляр на `ApplicationContext`.
- **prototype** — новый экземпляр на каждый `getBean()` / каждый `injection point`.
- **request** — один на HTTP-запрос (web).
- **session** — один на HTTP-сессию (web).
- **application** — один на ServletContext.
- кастомные — через **Scope** + **CustomScopeConfigurer**

**singleton** и **prototype** — это скоупы контейнера, остальные — **web-aware** и требуют `RequestContextHolder`/прокси.


**Подводный камень prototype внутри singleton:**\
Singleton инстанцируется один раз при старте контекста, и его зависимости инжектятся тоже один раз.
Решение этой проблемы через **Proxy scope** имеет неожиданное поведение. Бин с объявлением `@Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE, proxyMode=TARGET_CLASS)` автовайрится один раз, и это не просто бин, а прокси.\
А вот дёрганье методов прототайп бина через прокси, будет каждый раз создавать новый бин, и тут вопрос: а точно этого хотел человек?

Поэтому предпочтительным вариантом является:
- использование `ObjectProvider<T>` / `Provider<T>` — ленивый провайдер, вызов `get()` возвращает новый _prototype_ каждый раз.
- `ApplicationContext.getBean(Class)` — ручной lookup из контейнера. Работает, но нарушает инверсию зависимостей и усложняет тестирование.
- Метод помеченный аннотацией `@Lookup`, Spring генерирует CGLIB-подкласс и переопределяет метод, но Работает только для методов, требует **non-final** класса/метода.

**Нюансы:**
- **Prototype** не управляется контейнером после создания — `@PreDestroy` не вызывается. Spring отдаёт бин и забывает о нём; за cleanup отвечает разработчик.



### **Разница JDK dynamic proxy vs CGLIB** — JDK работает только через интерфейсы, CGLIB через наследование; final-классы и final-методы не проксируются.
1. **JDK dynamic proxy**
- Работает только через интерфейсы: Прокси-класс реализует те же интерфейсы, что и target.
- Генерируется в рантайме через `java.lang.reflect.Proxy` + `InvocationHandler`;
- Target-класс может быть `final`, методы могут быть `final` — прокси всё равно перехватит вызов, потому что клиент работает через интерфейс.
- Проксирует только методы интерфейсов. Методы класса, не объявленные в интерфейсе, недоступны через прокси.
- Требует, чтобы бин был инжектирован по интерфейсу. Если инжектить по конкретному классу — `BeanNotOfRequiredTypeException`.
- Быстрее создаётся, но вызов чуть медленнее в старых JVM (сейчас разница несущественна).

2. **CGLIB**
- Работает через наследование: генерируется подкласс target-класса, переопределяются non-final методы.
- Не требует интерфейсов.
- Не может проксировать: final-классы, final-методы, private-методы, static-методы, конструкторы. final-метод молча не будет проксирован — классический баг с `@Transactional` на final-методе.
- Прокси является подклассом target: `proxy instanceof TargetClass == true`. Но `proxy.getClass() != TargetClass.class`.
- Создаётся медленнее (генерация байткода), но вызовы быстрее.

**Нюансы:**
- **Spring Boot** с 2.x по умолчанию `spring.aop.proxy-target-class=true` → всегда **CGLIB**, даже если есть интерфейс, чтобы избежать сюрпризов с внедрением по классу и `@Autowired` на конкретный тип.\
Можно переопределить через `spring.aop.proxy-target-class=false`.
- `@Configuration` — всегда CGLIB (`proxyBeanMethods=true`), чтобы вызовы `@Bean`-методов внутри класса возвращали _singleton_,\
а не создавали новый бин. `proxyBeanMethods=false` (lite mode) отключает это — тогда `@Bean`-методы вызываются как обычные методы.
- **Self-invocation** — вызов метода внутри того же бина (**this.method()**) идёт мимо прокси, AOP не срабатывает. Касается и **JDK**, и **CGLIB**.
- `@Transactional` на final-методе с CGLIB молча не работает.
- Proxy не наследует аннотации target-класса в некоторых сценариях — важно для `@Transactional` на классе и для поиска аннотаций через reflection по прокси-классу

### **`BeanFactoryPostProcessor` vs `BeanPostProcessor`** — первый правит метаданные до создания бина, второй оборачивает готовый бин; на втором держится всё AOP и `@Transactional`.
Оба интерфейса являются хуками в жизненный цикл контейнера, но работают на разных этапах и с разными объектами.
1. `BeanFactoryPostProcessor` - работает сразу после прочтения всех `BeanDefinition`, до создания бинов.
- Вызывается на этапе `invokeBeanFactoryPostProcessors` внутри `refresh()`, до `finishBeanFactoryInitialization`.
- Может менять `BeanDefinition` (**scope**, **property values**, **init**-методы), регистрировать новые определения, удалять существующие.
- На этом этапе нельзя инстанциировать или пробовать получать бины, получим `BeanCurrentlyInCreationException`.
- Позволяет регистрировать новые бины.

2. `BeanPostProcessor` — работает над готовыми экземплярами бинов в процессе их инициализации. Например нужен для внедрения зависимостей через аннотации.
- Вызывается для каждого бина на этапе `initializeBean` внутри `AbstractAutowireCapableBeanFactory`.\
  Порядок внутри `initializeBean`: `postProcessBeforeInitialization` (BPP) -> `@PostConstruct` -> `InitializingBean.afterPropertiesSet` -> `custom init-method` -> `postProcessAfterInitialization` (BPP)
- Может вернуть другой объект вместо исходного — так работают AOP-прокси
- `BeanPostProcessor` не применяется к самому себе и к другим BPP — иначе бесконечная рекурсия.
- Если написать кастомный **BPP**, который зависит от другого бина, этот бин будет создан раньше остальных и не пройдёт через другие **BPP** — частый источник багов.

### **Как инкорпорировать несколько реализаций одного интерфейса?** — инжекция через `List<PaymentService>` или `Map<String, PaymentService>`, плюс `@Primary` и `@Qualifier`.
- через внедрение колекции, Spring соберёт все бины типа `MessageSender` с сортировкой по `@Order`/`Ordered`/`@Priority`. Работает для `List`, `Set` (`LinkedHashSet` — сохраняет порядок), `Map<String, MessageSender>` (ключ — имя бина, значение — бин), массивов.
- `@Qualifier` Если нужно выбрать один из многих. Голый `@Autowired` без квалификатора при нескольких кандидатах → `NoUniqueBeanDefinitionException`.
- `@Primary`  Один бин помечается приоритетным и используется при внедрении без квалификатора. `@Qualifier` имеет приоритет над `@Primary`.
- `ObjectProvider<T>` ленивый поиск, но он по сути перекрывает первые три варианта.

**Нюансы:**
- Порядок в **List**/**Set**/**массиве** — определяется `@Order`, `Ordered`, `@Priority`, затем именем бина как **_fallback_**
- `Primary` + `@Qualifier` вместе — квалификатор побеждает;
- Коллекции и Map — основа для plugin-архитектуры, **chain of responsibility**, **strategy pattern**.
- Если нужна фильтрация по условию — использовать `@ConditionalOnProperty` на самих реализациях.


### **`401 vs 403`** — не аутентифицирован против не авторизован.
**401 Unauthorized** — не аутентифицирован: сервер не знает, кто ты. Возникает когда пользователь не предоставил валидные учётные данные или токен \
**403 Forbidden** - аутентификация пройдена успешно, но недостаточно прав для доступа к ресурсу.

**Нюансы:**
- если пользователь анонимный, запрос на защищенный ресурс сначала получит 401. Чтобы аноним сразу получал 403, нужно явно разрешить анонимный доступ (permitAll или anonymous()), тогда AccessDeniedHandler перехватит отсутствие прав.
- для микросервисов `AuthenticationEntryPoint` и `AccessDeniedHandler` почти всегда переопределяются. Первый — чтобы вернуть `JSON` вместо страницы логина браузера, второй — чтобы прокинуть в ответ специфический код ошибки (например, `INSUFFICIENT_SCOPE`) для фронтенда.

### **Как обработать исключение в REST-контроллере?** — `@ControllerAdvice`/`@ExceptionHandler`, `ProblemDetail`.
**RestControllerAdvice + @ExceptionHandler** - рекомендуемый подход. Единый контракт ответа: Всегда возвращать структурированный _JSON_ (_code_, _message_, _timestamp_, _path_), а не _stacktrace_.

**Нюансы:**
- `@ControllerAdvice` можно сузить скоуп. Например, обрабатывать исключения только для пакетов конкретного модуля (`basePackages = "com.company.payment"`) или только для аннотированных контроллеров (`annotations = RestController.class`).
- в **handleGeneric** критично не логировать `ex.printStackTrace()`, а использовать структурированный лог с **traceId** (из MDC), который передается клиенту в теле ошибки для поддержки.
- `BindingResult`: ошибки валидации параметров запроса (`@Valid`) не бросают исключения, а заполняют `BindingResult`. Для их централизованной обработки в `@ControllerAdvice` ловят `MethodArgumentNotValidException`.
- Обрабатывать `ConstraintViolationException` (`bean validation` на параметрах) и `MethodArgumentNotValidException` (`@Valid` на теле) отдельно — у них разная структура ошибок.
- Исключения из фильтров не попадают в @`ControllerAdvice` — Security-фильтры стоят до `DispatcherServlet`. Для Security-ошибок (401/403) — только `AuthenticationEntryPoint` / `AccessDeniedHandler`
- Логирование в обработчике с уровнем по типу: 4xx — warn без стектрейса (клиент виноват), 5xx — error со стектрейсом. Иначе логи засоряются «ошибками» на каждый неверный запрос.

### **Как вручную открыть транзакцию, не прибегая к `@Transactional`?** — `TransactionTemplate` или `PlatformTransactionManager` напрямую.
1. `TransactionTemplate`
- Чёткие границы транзакции.
- Можно настроить _propagation_, _isolation_, _timeout_ через _setPropagationBehavior()_ и т.д. 
- Легко тестировать (мокать `TransactionTemplate`).
2. `PlatformTransactionManager`
- Полный контроль, но больше `boilerplate`.
- Используется, когда нужна нестандартная логика управления статусом.

**Когда нужно вместо `@Transactional`:**
- Динамическое управление границами транзакции (условное открытие/закрытие).
- Транзакция внутри цикла или batch-операции.
- Избегание self-invocation проблемы (когда `@Transactional` не работает при вызове метода того же класса).
- Микротранзакции в рамках большого сервиса, где декларативный подход слишком грубый. 
- Тестирование транзакционного поведения без подъёма полного контекста.

**Будут ли проблемы, если вернуть из `@RestController` JPA-модель с `ManyToOne`?** — да: `LazyInitializationException` и циклическая сериализация Jackson.
1. Если транзакция закрылась получаем - `LazyInitializationException`
2. Если транзакция открыта, или `open-session-in-view=true` то на связях `ManyToOne` можно получить бесконечный цикл и `StackOverflowError`(оч похожий как на `toString()`)
3. также на ленивые связи будут генерироваться дополнительные запросы, `N + 1` проблема.

**Как правильно:**
- Использование DTO
- не использовать `Hibernate.initialize(entity.getCustomer())`
- `JOIN FETCH`, или `@EntityGraph` в репозитории. `JOIN FETCH` ломает distinct для коллекций, т.е. дубликаты будут.
- `@JsonIgnore` как временное решение.

### Code review-задачи

Задача «сервис платежей, найдите баги»:

- **`@Transactional(REQUIRES_NEW)` на self-invocation** — вызов `this.sendNotification(p)` идёт мимо прокси, новая транзакция молча не создаётся.
- **REST-вызов во внешний антифрод внутри `@Transactional`** — соединение с БД удерживается всё время запроса; при таймаутах пул HikariCP исчерпывается, сервис встаёт.
- **Kafka внутри транзакции** — commit БД и публикация события не атомарны; ждут разговора про Transactional Outbox и Saga.
- **`static Map` как кеш в контроллере** — `HashMap` не потокобезопасен, плюс stale data; на senior-уровне ждут обсуждения memory leak'ов.
- **Отсутствие идемпотентности платёжного эндпоинта** — архитектурный баг, отличающий сеньора.

Другая задача (сервис тарификации вознаграждений):

- Field injection вместо конструктора.
- `Optional.get()` без проверки.
- Внешние вызовы внутри цикла в транзакции.

Кейс про производительность: «сервис + Postgres + third-party API тормозит под нагрузкой — что смотреть?» — latency, GC, блокировки в БД, circuit breaker, rate limiter.

## Каверзные вопросы с собесов в целом

### **Что произойдёт при вызове `@Transactional`-метода из того же класса?** — транзакция не откроется: вызов `this.method()` минует AOP-прокси. Самая частая ловушка.
### **`@Transactional` на private-методе** — приложение поднимется, метод отработает, но транзакции не будет: CGLIB не может переопределить private-метод.
### **Когда происходит коммит и что попадает под rollback?** — коммит после успешного завершения метода; по умолчанию откатываются `RuntimeException` и `Error`, для checked нужен `rollbackFor`.
### **`@Transactional` внутри `@PostConstruct`** — прокси уже создан, но прямой вызов всё равно минует его; обходят через self-injection с `@Lazy` или `ApplicationContext`.
Ни аннотация на самом методе `@PostConstruct`, ни вызовы его транзакционных методов того же бина через `this` транзакцию не откроют.\
А вот вызов метода другого бина транзакцию откроет, но нужно следить за порядком инициализации. \
`@PostConstruct` выполняется на сыром `target`-объекте, до создания прокси. `TransactionInterceptor` ещё не подключён — вызов идёт мимо аспектной логики.\
Обойти можно вызовом `TransactionTemplate` внутри `@PostConstruct` — если инициализация должна быть именно в фазе создания бина.
Или, если возможно, то слушаньем события `@EventListener(ApplicationReadyEvent.class)` и выполнить транзакцию когда приложение полностью поднялось. 
### **`@Cacheable` из `@PostConstruct`** — кеш-аспект инициализируется позже, поэтому даже через прокси не сработает;.
Тоже что и с `@Transtional`
### **Чем `@Async` может удивить?** — self-invocation, нужен `@EnableAsync`, дефолтный executor часто не подходит; исключение из `void`-метода пропадает без `AsyncUncaughtExceptionHandler`.
1. асинхронный метод никогда не должен вызываться из соседнего метода того же бина. Выносите @Async методы в отдельный `@Component` или `@Service`.
2. Если метод возвращает `void`, исключение проглатывается. Вызывающий код никогда не узнает о `failure`. Решение: всегда возвращать `CompletableFuture<T>` / `Future<T>` и обрабатывать `.exceptionally()`
3. По умолчанию используется `SimpleAsyncTaskExecutor` потоки в котором не переиспользуются, а только создаются заново при необходимости.\
К-во потоков не ограниченно. Соответственно лучше его не использовать. В новом спринге есть флаг `setVirtualThreads(boolean)`, Что должно поправить ситуацию с конкурентностью, но вообще лучше использовать отдельный пул.
4. **MDC**, **SecurityContext**, **RequestAttributes**, **TransactionContext** не передаются в async-поток автоматически. Логи теряют **traceId**, `SecurityContextHolder.getContext()` возвращает `null`. Решение: `TaskDecorator` для копирования контекста или `ContextSnapshotFactory`
5. `@Transactional` + `@Async` на одном методе, или взаимовызов метода с одной из аннотаций из другого помеченного метода ничего не тригернёт.
6. Тесты завершаются раньше, чем async-метод выполнится. Нужен `TestExecutionListener` с `AsyncTestUtils.waitForAsyncTasks()`
7. Если асинхронный метод в процессе работы синхронно ждет результат другого `@Async`-метода (`future.get()`), а размер пула ограничен (например, _corePoolSize=4_, _maxPoolSize=4_), можно легко поймать дедлок. Все 4 потока пула будут заняты и ждать друг друга.\
   `@Async` не должен содержать синхронных блокировок (`get()`, `Lock.lock()`, тяжелых **JDBC**-запросов) без веской причины. Для тяжелых `I/O` используйте `@Async` в связке с неблокирующим `WebClient` или увеличьте размер пула.
8. `@Async` из коробки не имеет таймаута выполнения. Зависшая задача будет висеть в пуле вечно, занимая поток. Таймаут нужно предусмотреть через `CompletableFuture#orTimeout`


### **Разница `@Controller` и `@RestController`** — второй это `@Controller + @ResponseBody`; ждут понимания, что JSON получается через `HttpMessageConverter`.
1. `@Controller` для **MVC**, возвращаемое строковое значение интерпретируется как имя **view**. Для возврата JSON нужно явно добавить `@ResponseBody`.\
Аннотация `@Controller` не наследуется в контексте AOP-обработки.
2. `@RestController` - комбинация `@Controller` и `@ResponseBody`. Возвращаемое значение метода всегда сериализуется в тело ответа (JSON/XML) через `HttpMessageConverter`.\
   `@RestController` наследуется. Если вы создаете абстрактный базовый класс с `@RestController`, все наследники автоматически станут REST-контроллерами.

### **Жизненный цикл бина целиком** — создание → DI → Aware-коллбеки → `BeanPostProcessor.before` → `@PostConstruct` → `afterPropertiesSet` → `BeanPostProcessor.after` (тут вплетаются прокси) → `@PreDestroy`. `@PreDestroy` сработает только на graceful shutdown, не на `kill -9`.
1. **Instantiation** — Контейнер находит `BeanDefinition`  и создает экземпляр класса через рефлексию.
2. **Dependency Injection** — заполнение `@Autowired`, `@Value`, **setter injection**.
3. **Aware interfaces** — если бин реализует **Aware** интерфейсы `BeanNameAware`, `BeanFactoryAware`, `ApplicationContextAware`, тогда вызываются соответствующие **_set_** методы.
4. `BeanPostProcessor.postProcessBeforeInitialization()` — все **BPP**, включая обработку `@PostConstruct`.
5. **Инициализация** — если интерфейс `InitializingBean` реализован, то `InitializingBean.afterPropertiesSet()`
6. **Custom init-method** — если указан в `@Bean(initMethod=...)` или XML.
7. `BeanPostProcessor.postProcessAfterInitialization()` — AOP-проксирование(`@Transactional`, `@Async`, `@Cachable`) происходит здесь.
8. Бин готов к использованию.
9. Уничтожение singleton - `PreDestroy` / `DisposableBean.destroy()` / `custom destroy-method` — при закрытии контекста.

**Нюансы:**
- Для **singleton**'ов весь цикл проходит при старте контекста. Для **prototype** — при каждом **getBean()**
- ```BeanDefinition → конструктор → @Autowired → Aware → BPP(before) → @PostConstruct → afterPropertiesSet → initMethod → BPP(after, тут прокси) → [работа] → @PreDestroy → destroy() → destroyMethod```
- Проблема циклических зависимостей: Spring решает её через «ранние смарт-ссылки» (early references).\
Когда бин A требует бин B, а B требует A, на этапе внедрения A получит не готовый бин B, а временную прокси-ссылку (`ObjectFactory` или `DependencyObject`).\
Если в `@PostConstruct` бина A вы вызовете метод на этой прокси-ссылке, а она в этот момент еще не прошла свой `@PostConstruct`, вы получите `BeanCurrentlyInCreationException`.

### **Потокобезопасен ли бин?** — нет, если есть изменяемое состояние: singleton-бин живёт в пуле потоков Tomcat.
- **Singleton** - Нет, если не соблюдать правила. Вот правила - бин должен быть `stateless`, неизменяемым или использовать потокобезопасные подходы: синхронизацию, конкурентные коллекции, атомарные переменные и т.д.
- **Prototype** - Потокобезопасен по определению — каждый поток/запрос получает свой экземпляр. Но если `prototype` внедрён в `singleton` без **прокси/ObjectProvider**, тогда прототип не будет меняться на каждый запрос и может быть проблема с конкурентностью как и у синглтона.

### **Чем ApplicationContext отличается от BeanFactory?** — ленивая загрузка бинов против eager, поддержка событий, i18n, автоматическая регистрация постпроцессоров.

1. `BeanFactory` — минимальный интерфейс **IoC-контейнера**: регистрация, создание и получение бинов **getBean()**, управление их жизненным циклом. В прод не нужен. Фичи:
- **Ленивая инициализация**
- **Реализует только базовые функции DI**

2. `ApplicationContext` наследует `BeanFactory` добавляя enterprise-функциональность. Фичи:
- **Eager initialization singleton'ов** — все **singleton**-бины создаются при старте контекста (раннее обнаружение ошибок конфигурации)
- **Event publishing** — `ApplicationEventPublisher`, event-driven архитектура (`@EventListener`)
- **i18n / MessageSource** — поддержка локализации
- `Resource loading` — ResourceLoader для доступа к файлам, classpath, URL.
- `AOP integration` — автоматическое проксирование, `@Transactional`, `@Cacheable`.
- `Annotation processing` — `@Autowired`, `@Value`, `@PostConstruct` через встроенные BPP.
- `Environment abstraction` — Доступ к `Environment` для работы с **профилями**, **property sources**, **conditional beans**.

Нюансы:
- В **Spring Boot** используется **WebApplicationContext**, реализация `ApplicationContext`.
- В современных монолитах и микросервисах разница в скорости старта между ленивым `BeanFactory` и жадным `ApplicationContext` нивелируется. Жадная инициализация предпочтительнее, так как она выполняет **fail-fast**:
- `ListableBeanFactory` — именно через него `ApplicationContext` умеет перебирать все бины.

# Вопросы по Spring Framework для Senior Java Developer (Т‑Банк и другие финтех‑компании)

## Код‑ревью (формат Т‑Банка: найти баги в готовом коде)

### **Field injection через `@Autowired` вместо constructor injection**  
**Проблемы field injection:**
- Невозможность создать **immutable-бин** — поля не могут быть final(@Autowired на поле не сработает, если поле помечено final).
- Нарушение single responsibility  — если конструктор имеет слишком много параметров, это сигнал к рефакторингу. Field injection скрывает это.
- Нельзя использовать без контейнера — тестирование требует **reflection** или **Spring Test Context**. Нет возможности передать зависимости через конструктор в unit-тесте.
- Циклические зависимости маскируются - **Spring** резолвит их через **proxy/setter** **post-processing**. При **constructor injection** цикл обнаруживается сразу при старте(`BeanCurrentlyInCreationException`) → **fail fast**
- Порядок инициализации непредсказуем — нет гарантии, что поле заполнено до использования (особенно в `@PostConstruct`).\
- Явная связь с инфраструктурой фреймоврка( через `@Autowired`)
- 
**Когда допустимо:**
- Тестовые классы (**@SpringBootTest**) — допустимо для удобства.
- Опциональные зависимости + `@Autowired(required = false)` — но лучше `ObjectProvider<T>` или `Optional<T>` в конструкторе.

- **`double` для денег**  
  Пояснение: приводит к ошибкам округления и проблемам при автоупаковке; в финтехе используют `BigDecimal`.
- **`System.out.println` вместо SLF4J**  
  Пояснение: такие логи не попадают в централизованную систему (Kibana и т. п.); в проде используют SLF4J.
- **Обработка исключений: `catch (Exception e) { e.printStackTrace(); return e.getMessage(); }`**  
  Пояснение: скрывает реальную причину ошибки, пишет в stderr, раскрывает детали реализации клиенту; правильно — `@ControllerAdvice` + `ProblemDetail`.
- **Self‑invocation с `@Transactional(REQUIRES_NEW)`: `this.sendNotification(p)`**  
  Пояснение: вызов через `this` минует прокси, поэтому `@Transactional` не срабатывает; решения: вынести в другой бин, использовать `TransactionTemplate`.
- **REST‑вызов в антифрод внутри `@Transactional`**  
  Пояснение: при долгом ответе соединение к БД остаётся открытым, быстро исчерпывается пул соединений (HikariCP); решение: вынести вызов до транзакции или использовать circuit breaker.
- **`kafka.send()` внутри транзакции без Transactional Outbox**  
  Пояснение: нет атомарности между БД и Kafka; ожидают паттерн Transactional Outbox и идемпотентного consumer’а.
- **Статический `HashMap` как кэш**  
  Пояснение: не потокобезопасен, плохо масштабируется; в продакшене используют специализированные кэши (Caffeine, Redis).
- **Отсутствие идемпотентности (Idempotency‑Key)**  
  Пояснение: повторные запросы могут создавать дубликаты; в платёжных сервисах обязательно предусматривают идемпотентность.
- **N+1‑запросы в цикле + `Optional.get()` без проверки**  
  Пояснение: N+1 сильно снижает производительность; `Optional.get()` без проверки вызывает `NoSuchElementException`; ждут `EntityGraph`, `batchSize`, безопасные методы `Optional`.

## Транзакции и прокси (частые «точки среза» на Senior)

### **Почему `@Transactional` не работает при self‑invocation?**  
  Пояснение: прокси перехватывает вызовы через интерфейс/бин, а `this.method()` идёт напрямую; решения: другой бин, `TransactionTemplate`, `ApplicationContext`.
### **Почему `@Transactional` не работает из `@PostConstruct`?**  
  Пояснение: на момент инициализации (`@PostConstruct`) прокси ещё не полностью настроен; транзакционный контекст не создаётся.
### **Почему не работает на `private`/`final` методах?**  
  Пояснение: CGLIB не может переопределить `final`, а прокси не перехватывают `private`; AOP работает только на публичных методах.
### **Propagation‑стратегии и когда нужен `REQUIRES_NEW`**  
- **REQUIRED** (дефолт) — присоединиться к существующей транзакции или создать новую.
- **REQUIRES_NEW** — всегда создавать новую независимую транзакцию, текущую приостановить.
- **NESTED** — создать savepoint внутри текущей транзакции. Откатывается только до savepoint'а, не ломая внешнюю транзакцию. Работает только с JDBC (не JPA/Hibernate). Откат внешней транзакции откатывает и NESTED.
- **SUPPORTS** — выполнить в существующей транзакции, если есть; иначе без транзакции. Хорошо для чтения.
- **NOT_SUPPORTED** — выполнить без транзакции, приостановив текущую.
- **MANDATORY** — выполнить только в существующей транзакции, иначе исключение. Хорошо для библиотечного кода.
- **NEVER** — выполнить только без транзакции, иначе исключение.

**Когда нужен REQUIRES_NEW:**
- **Аудит / логирование** - запись аудита должна сохраниться даже если основная бизнес-транзакция откатится.
- **Генерация sequence / ID** - счётчик должен инкрементироваться независимо от rollback'а основной операции.
- **Внешние side-effects** - отправка уведомления, запись в очередь, где откат недопустим.
- Изоляция long-running операций — чтобы не держать блокировки основной транзакции.
- **Разграничение изоляции**: внешней нужен **READ COMMITTED**, внутренней — **SERIALIZABLE** на коротком участке; REQUIRES_NEW позволяет задать разный `isolation`.

Нюансы: 
- Два соединения с БД одновременно — под нагрузкой может исчерпать pool.
- Не видит незакоммиченные данные внешней транзакции (при изоляции READ_COMMITTED).
- Deadlock risk — если новая транзакция обращается к тем же строкам, что и приостановленная(она всё ещ держит блокировки при `SELECT ... FOR UPDATE`).
- Не работает при self-invocation — нужен вызов через прокси.
- Потеря контекста Persistence Context. При suspend родительской транзакции Hibernate-сессия отсоединяется от БД.\
Сущности из родительского контекста перестают отслеживаться. Если передать такую сущность в метод с **REQUIRES_NEW** и попытаться ее изменить, будет `DetachedEntityException`.
- Тайм-аут родительской транзакции не наследуется. У вложенной транзакции свой счетчик времени.
- Родительская транзакция коммитится после вложенной. Если в родительской произойдет сбой после успешного коммита аудита, возникнет инконсистентность (аудит говорит, что действие было, а в бизнес-данных его нет).\
Для решения этой проблемы на проде используют паттерн Outbox или двухфазный коммит (2PC), если БД это поддерживает.

- **Что rollback’ается по умолчанию?**  
  Пояснение: по умолчанию откатываются только unchecked‑исключения и `Error`; для checked‑исключений нужно явно указать `rollbackFor`.
- **Чем JDK proxy отличается от CGLIB?**  
  Пояснение: JDK proxy работает через интерфейсы, CGLIB — через наследование; это влияет на работу AOP и ограничения по методам.

## Контейнер, бины, AOP

### **Жизненный цикл бина по шагам**  
  Пояснение: BeanDefinition → конструктор → инжекция → `beforeInitialization` → `@PostConstruct` → `afterInitialization` → `@PreDestroy`.
### **Что такое `BeanPostProcessor` и на чём он основан?**  
**BeanPostProcessor** — это расширение Spring IoC-контейнера, позволяющее перехватывать и модифицировать бины до и после инициализации каждого бина.\
**Нужен для:**
- **Создания прокси**
- **Обработка аннотаций** `@Autowired` и `@Value`
- **Внедрение Aware-интерфейсов**

**Нюансы:**
- Применяется к каждому бину в контексте, соответственно производительность критична.
- Может заменить бин на другой объект
- Сам BPP тоже бин, но создаётся раньше остальных и не проходит через другие BPP (кроме специальных infrastructure-процессоров)
- `InstantiationAwareBeanPostProcessor` (расширение) позволяет перехватывать даже фазу инстанциации (до `DI`).
- Кастомный BPP оправдан только при создании фреймворка/библиотеки или нестандартной cross-cutting логики, которую нельзя выразить через AOP.
- Процессоры регистрируются через `@Bean` в `@Configuration` или через `@Component` (если включена авто-детекция). Кастомный процессор не должен быть «бизнес-бином», он — инфраструктурный код.
- `BeanPostProcessor` работает с объектами (готовыми экземплярами бинов). `BeanFactoryPostProcessor` работает с метаданными (`BeanDefinition`) до создания любых объектов и используется для подмены плейсхолдеров (`${...}`) или динамической регистрации бинов.
- При объявлении через `@Bean` в `@Configuration` классе метод должен быть `static`, Если `@Bean`-метод не является `static`, контейнеру сначала придётся создать экземпляр самого `@Configuration`-класса, что может запустить преждевременную инициализацию других бинов и конфигураций.
### **Prototype внутри Singleton — сколько экземпляров создастся?**  
  Пояснение: один экземпляр при создании синглтона; для динамического получения используют `ObjectFactory` или `@Lookup`.
### **Два бина реализуют один интерфейс — как внедрить оба?**  
  Пояснение: `@Primary`/`@Qualifier` для одного, `List<PaymentService>` или `Map<String, PaymentService>` для всех.
### **Как вызвать `@Cacheable`/`@Async`-метод из того же класса?**  
  Пояснение: аналогично `@Transactional`, self‑invocation минует прокси; решения: вынести логику в другой бин или использовать `ApplicationContext`.
### **Разница `@Component` / `@Service` / `@Repository`**  
  Пояснение: семантические маркеры; `@Repository` дополнительно транслирует исключения в `DataAccessException` и добавляет специфическую обработку.
### **Разбирается ли circular dependency и как?**  
В _Spring Boot 2.6+_ по умолчанию запрещены т.к. намекают на пробему в дизайне, включаются через `allow-circular-references`.\
На более ранних версиях возможны через _field injection_ между синглтонами и синглтоном с прототипом, но всё ещё не возможны через `constructor injection` вызывая `BeanCurrentlyInCreationException` и между прототипами. 
Как быть:
- выделить общий компонент в отдельный бин
- Временное решение: использовать `@Lazy`;
- `ObjectProvider` — для опциональных/ленивых зависимостей
- более плохое решение -> Заменить **constructor injection** на **setter/field injection**
- включить `allow-circular-references` в проперти.
Да, но только для пары singleton, или singleton + prototype.
  Пояснение: Spring может разрешить циклические зависимости через кэш ранних ссылок; в Spring Boot 2.6+ по умолчанию запрещены, включаются через `allow-circular-references`.

## Spring Boot

### **Из чего состоит `@SpringBootApplication`?**  
  Пояснение: `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`; Boot управляет контекстом, автоконфигурацией и embedded‑сервером.
### **Как работает автоконфигурация?**  
  Пояснение: через `@Conditional`-аннотации; наличие определённых классов в classpath активирует соответствующие конфигурации (например, JPA при наличии `DataSource`).
### **Как узнать, какие автоконфигурации применились?**  
  Пояснение: используют Actuator endpoint `/conditions` или вывод логов при старте.
### **«Добавьте Spring Security» — что изменится?**  
  Пояснение: стартер автоматически защищает все эндпоинты, требуя аутентификации; нужно явно настраивать правила доступа.
### **Как различать уровни логов по окружениям (dev/qa/prod)?**

### **Как тюнить пул соединений к БД?**
- Запустить с дефолтными настройками и собрать метрики - `hikaricp.connections.pending`, `hikaricp.connections.active`, `hikaricp.connections.usage` - время владения соединением.
- если `active ≈ max` + высокий pending → увеличить pool или оптимизировать запросы/транзакции.
- если `active << max` постоянно → уменьшить pool, освободить ресурсы БД.
- Частые `connection-timeout` → либо pool мал, либо транзакции слишком долгие.
- для быстрой настройки заходит такая формула - `connections = (core_count * 2) + effective_spindle_count(0)` + не забываем про запас на внутренние нужды БД(модификация таблиц, индекс добавляются и прочая админская работа).
- дефолт таймаут 30 сек это жёстко, редк когда кто-то будет столько ждать, лучше упасть быстро за 3 - 5 сек.

### **Как обрабатывать ошибки в `@Scheduled`?**
По умолчанию исключения в `@Scheduled` логируются, но не пробрасываются. Следующее выполнение состоится по расписанию, но о `failure` никто не узнает.
**Способы обработки:**
- `Try-catch` внутри `@Scheduled` метода.
- **Глобальный ErrorHandler** для всех `@Scheduled` задач
- `Retry`
### **Как запускать `@Scheduled` в нескольких инстансах?**
    Распределённые локи, ShedLock, leader election, внешние планировщики.
83. **Какие проблемы у `@Cacheable`?**
- Self-invocation не работает, аналогично `@Transactional` проблеме. Соответственно метод в тихую выполняется каждый раз.
- Нет автоматической инвалидации при изменении данных. Без явного `@CacheEvict` / `@CachePut` возвращает stale data.\
В распределённых системах (несколько инстансов) локальный кэш рассинхронизируется мгновенно. Решение: TTL + event-driven invalidation (`Redis Pub`/`Sub`, `Kafka`) или distributed cache.
- Когда срок жизни горячего ключа (TTL) истекает, сотни или тысячи потоков одновременно обнаруживают, что кэша нет (miss). Все они одновременно идут в БД, создавая лавинообразную нагрузку и, как правило, роняя базу.\
  Лечение: `@Cacheable(sync = true)` — Spring синхронизирует вычисление для одного ключа через lock по ключу, но работает только для локальных кэшей.\
Распределённый кэш нужно прогревать заранее.
- Java-сериализация по умолчанию хрупкая, любое изменение класса и старые записи не десериализуются.
- Нужно настраисвать размер локального кэша, дабы избежать OOM.
- Если сам кэш недоступен, Redis down: по умолчанию исключение пробросится наружу и сломает запрос. Обычно переопределяют на «логировать и работать мимо кэша» — graceful degradation.

Нюансы:
- Задаём вопрос «зачем кэш»: часто вместо кэша нужно — материализованное представление в БД, реплика для чтения, или оптимизация самого запроса. Кэш — последний инструмент, который добавляет рассогласованность; на собеседовании вопрос «чем хуже просто быстрый запрос» — здоровый.
- Метрики кэша — обязательны
- не кэшировать `List<Product>` или `Pageable`
84. **Как бороться с cache stampede?**
- `@Cacheable(value =, key =, sync = true)` - работает только в пределах одного инстанса.
- Для распределённого кэша Требуется внешний лок (**Redis**, **Zookeeper**). Важно выставлять `lockTimeout` больше времени выполнения запроса в БД, иначе лок протухнет, и в БД снова пойдет несколько запросов.
- проверять сколько осталось жить кэшу и если в районе 10% +-, обновлять его с рандомной вероятностью, например 70% в параллельном потоке.
- Объединить запросы в батч.
- `Cache Warming` - скрипт, который дергает горячие эндпоинты после старта пода.
- Caffeine умеет писать кэш на диск для warm start


Нюансы:
- Не бороться со stampede, пока он не измерен.
- Комбинировать разные подходы

Через редис(Redisson), или БД что медленнее. Использовать tryLock с таймаутом чтобы не ждать вечно, c TTL (или watchdog)чтобы его не держал упавший сервис.
    Redis, DB, ZooKeeper; TTL, владение, корректное освобождение.

## Финтех‑специфика и архитектура вокруг Spring

- **Kafka: семантика доставки, Outbox, идемпотентность**  
  Пояснение: важно понимать at‑least‑once / exactly‑once, использовать Transactional Outbox для согласованности и обеспечивать идемпотентность consumer’ов.
- **Виртуальные потоки (Loom) и Structured Concurrency**  
  Пояснение: меняют подход к масштабированию и управлению параллелизмом; уменьшают зависимость от пулов потоков.
- **Reactive: WebFlux vs MVC**  
  Пояснение: нельзя одновременно использовать оба подхода в одном приложении; Spring Boot выбирает один на основе classpath.
- **Kubernetes: Readiness vs Liveness, OOM Killer**  
  Пояснение: Readiness — готов ли сервис принимать трафик, Liveness — жив ли сервис; OOM Killer убивает поды при превышении лимитов памяти.
- **«Сервис на 10K RPS тормозит под нагрузкой — что смотреть?»**  
  Пояснение: метрики (latency, error rate), пулы соединений, GC, трейсы, CPU/memory, очереди, внешние вызовы.
