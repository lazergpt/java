# Kafka, Spring Kafka и Kafka Streams — вопросы с собеседований (Senior Java)

## Контекст: как Kafka спрашивают в Т-Банке

Отдельного «Kafka-интервью» в Т-Банке нет: вопросы по Kafka приходят внутри технической секции (Spring, микросервисы, гарантии доставки) и внутри System Design — там типовые задачи это платёжный шлюз, сервис уведомлений с гарантией доставки, система обработки заявок на брокерские операции. Формат собеса — три секции по 60–75 минут, сильный акцент на надёжность интеграций, retry-стратегии и работу под нагрузкой в финтех-домене. Минимум по Kafka: producer/consumer, партиции, гарантии at-least-once/exactly-once. В банках Kafka почти всегда пересекается с вопросами про идемпотентность и паттерн Outbox — их стоит знать «на зубок».

## Kafka Core: базовые вопросы, которые спрашивают почти всегда

### **Что такое топик, партиция, оффсет?**
1. **Топик** — логический канал/поток сообщений. Kafka хранит данные в распределённом, отказоустойчивом, масштабируемом журнале (логе), разбитом на партиции.
2. **Партиция** — уже то место, где физически лежат данные единица параллелизма и хранения.  Внутри партиции гарантируется порядок.\
Между партициями порядка нет. Один консьюмер в группе читает максимум одну партицию.  Ключ сообщения определяет партицию через `hash(key) % numPartitions`
3. **Оффсет** — позиция сообщения внутри партиции.

### **Почему Kafka быстрая?**
1. Сообщения пишутся в конец файла, что позволяет использовать последовательное чтение, которое значительно быстрее произвольного.
2. Kafka не держит данные в JVM-куче. Запись и чтение идут через файловый дескриптор в обход JVM, используя OS page cache. Нет GC-пауз на данных, нет двойного копирования в пользовательское пространство.
3. Zero-copy (`sendfile`). При отправке консьюмеру данные из файла уходят в сетевой сокет напрямую через `sendfile syscall`, минуя буферы пользовательского пространства.
4. Продюсеры и брокеры агрегируют сообщения в батчи. Сетевые издержки амортизируются на пачку. Компрессия (lz4, zstd, snappy) снижает I/O и network overhead.
5. Консюмер сам забирает данные пачками в свой темп, брокер не тратит ресурсы на push и не держит backpressure-очереди.


3. **Что такое Consumer Group и как работает балансировка?**
**Consumer Group** — набор потребителей, которые совместно читают топик.
**Rebalance** - процесс перераспределения партиций между членами группы.\
**Запускается, когда:**\
- новый член присоединяется или существующий уходит
- член перестаёт слать heartbeat дольше `session.timeout.ms`
- Консьюмер не успел обработать батч за `max.poll.interval.ms`
- Изменилась топология: добавлены/удалены партиции, подписка на топик изменилась.

**Три протокола rebalance:**\
- **Eager** — stop-the-world: все consumer'ы отдают все свои партиции, лидер группы считает новый assignment, затем все получают назначения и возобновляют работу.
- **Cooperative** - consumer'ы отдают только те партиции, которые реально переезжают, остальные продолжают обрабатывать. Требует двух раундов rebalance.

**Нюансы:**
- В `Spring Kafka` rebalance перехватывается через `ConsumerRebalanceListener`, там удобно вклинить in-flight обработку и коммитить оффсеты перед losing partitions.
- Если консьюмеров в группе больше чем партиций, лишние консьюмеры будут простаивать.
- Есл консьюмеров в группе меньше чем партиций, некоторые консьюмеры будут обрабатывать несколько партиций. 
    
### **Какие гарантии доставки и как настраивается exactly-once?**
1. **At-most-once** - сообщение может потеряться, но не дублируется. Консюмер коммитит оффсет до обработки.\
Максимальная пропускная способность, нулевая дедупликация — годится, когда потеря допустима (метрики, тики)
2. **At-least-once** - сообщение не теряется, но может быть обработано повторно. Коммит после обработки + ретраи продюсера.\
Дефолт для большинства систем, дедупликация на стороне консюмера (idempotent handler по ключу/ID)
3. **Exactly-once** - обработка ровно один раз, даже при сбоях и повторных доставках. Именно обработка, а не физическая доставка.\
Для **Exactly-once** необходимо:
- **Идемпотентный продюсер.** Включается `enable.idempotence=true`. Каждый продюсер получает **PID** и каждый батч — sequence number.\
Брокер дедуплицирует ретраи по этим номерам, поэтому `max.in.flight.requests.per.connection` может быть до 5 без риска переупорядочивания.\
Ретрай с тем же seq не создаёт дубль.\
- **Транзакционный продюсер**. Должен иметь `transactional.id=my-app-instance-1`, стабильный идентификатор.
- `isolation.level=read_committed` читатель не увидит незакоммиченные/aborted записи.

**Нюансы:**
- `transactional.id` при перезапуске одного и того же экземпляра не должен меняется, иначе _Kafka_ откатит незавершённые транзакции (и ты получишь _at-least-once_).
- `transactional.id` - должен быть постоянным в пределах жизни экземпляра приложения, но разным между экземплярами.
- Если у нескольких сервисов одинаковый `transactional.id`, старые продьюсеры будут приостановлены.
- В `Kafka Streams` **EOS** включается флагом `processing.guarantee=exactly_once_v2`
- Гарантия атомарности работает только для цикла _consume_ → _process_ → _produce_ внутри _Kafka_.\
Если пишется в базу, или вызывается внешний API — цепочка рвётся

   At-most / at-least / exactly-once: коммит до обработки = можно потерять, после = возможны дубли; exactly-once собирается из идемпотентного продюсера + транзакций + read_committed у консьюмера.

### **Чем отличается `acks=all` от `acks=1`?**
1. `acks=1` — лидер партиции подтверждает запись после того, как записал её в свой локальный лог, не дожидаясь репликации на follower'ы. Продюсер получает ack сразу.\
   Риск: leader записал сообщение в свой лог, ответил продюсеру и умер до того, как фолловеры успели реплицировать. После выбора нового leader запись теряется.
2. `acks=all` (= -1) — лидер подтверждает запись только после того, как её записали все реплики в **ISR** (in-sync replicas). Только тогда продюсер получает ack.\
Минимальный порог **ISR** задаётся брокерской настройкой `min.insync.replicas` и если живых синхронизированных реплик меньше, продюсер получает `NotEnoughReplicasException` и запись отклоняется.

**Нюансы:**
- `acks=all` без `min.insync.replicas>1` не имеет смысла, при деградации **ISR** до 1 реплики гарантия превращается в `acks=1`, но система продолжает принимать записи.
- `acks=all` — обязательное условие idempotent producer
- На практике при linger.ms/батчинге рост латентности от `acks=1` к `acks=all` в пределах одного ДЦ — единицы миллисекунд, поэтому в выбор «acks=all везде, acks=0 для метрик/тиков» — разумный дефолт. 
- Надёжная связка: `replication.factor=3, min.insync.replicas=2, acks=all`.

### **Гарантируется ли порядок сообщений?**
Внутри одной партиции — да, порядок строго гарантирован. Это следствие append-only лога: сообщения нумеруются монотонным оффсетом, консьюмер читает последовательно.
В топике можно сделать тоже порядок, если оставить в нём одну партицию.

**Когда порядок нарушается:**
- Разные партиции. Топик — это набор независимых логов. Сообщения с разными ключами (или без ключа) могут уйти в разные партиции, и глобального порядка между ними нет.
- Продюсер с ретраями без идемпотентности. Классический баг: батч A ушёл, упал по таймауту, продюсер отправил батч B, B записался, потом ретрай A записался после B — порядок нарушен.
Решается через `enable.idempotence=true`, или `max.in.flight.requests.per.connection=1` но такой вариант медленный.
- При Изменении числа партиций(ребалансировка), старые и новые сообщения с одним ключом могут оказаться в разных партициях т.к. `murmur2(key) % numPartitions`

## Продюсер: «под капотом»

### **Что такое идемпотентный продюсер и чем он отличается от транзакционного?**
**Идемпотентность** — это про дедупликацию отдельных записей при ретраях, включена по умолчанию. Включается через `enable.idempotence=true`\
Который принудительно включает `acks=all, retries=MAX, max.in.flight.requests.per.connection ≤ 5`.\
Дедупликация живёт только в рамках сессии, Т.к. **PID** меняется после рестарта.
**Транзакции** — это атомарная запись в несколько партиций и топиков плюс коммит оффсета как единая операция.\
Транзакционный продюсер включает в себя идемпотентность, но не наоборот. Это база **EOS**

### **Что произойдёт, если увеличить число партиций?**
✅ - Увеличится параллелизма консьюмера\
✅ - вырастет пропускная способность записи\
❌ - Сломается упорядочивание по ключу, расчёт партиции `murmur2(key) % numPartitions` будет давать другой результат
❌ - ребалансировка. На больших группах это секунды простоя.
❌ - Новые партиции не видны продюсерам и консьюмерам мгновенно — они появятся после обновления метаданных (`metadata.max.age.ms`).\
В это окно часть трафика всё ещё идёт в старый набор партиций.
❌ - Возможна потеря сообщений при `auto.offset.reset=latest` - консюмеры молча пропустят то, что успеет записаться до первого poll.\
Если консьюмер сконфигурирован с `latest` и обнаружит новую партицию с задержкой,\
он начнёт читать её с конца и пропустит всё, что продюсеры успели туда записать за окно между созданием партиции и обновлением метаданных у клиента.
❌ - при `replication.factor=3` каждая новая партиция создаёт три реплики, которые нужно разместить, синхронизировать и мониторить.

### **Что такое горячая партиция и как с ней бороться?**
**Горячая партиция** — это партиция, которая получает непропорционально большую долю трафика (записи или чтения) по сравнению с остальными.

**Обнаруживается через:**
- Per-partition метрики продюсера: `record-send-rate`, `byte-rate`

**Причины:** 
- Если ключей мало.
- Ключи неравномерны.
- Кастомный партиционер с плохой логикой.
- Null-ключи. В старых версиях — round-robin, в новых — sticky partitioning: один продюсер «прилипает» к одной партиции на время батча. При малом числе продюсеров это даёт перекос.
 
**Решение:**
- Кастомный партиционер. Явно маппить «тяжёлые» ключи в отдельные партиции, а остальные — равномерно.
- Поменять ключ
- Если один ключ генерирует непропорциональный объём — вынести его в отдельный топик с собственной ёмкостью и консьюмером.
- Если бизнес-ключ слишком грубый можно попробовать разбавить его другим полем с большим к-вом состояний.
- Добавить соль, тоже что и в предыдущем пункте, но здесь не сохраняется порядок
- Увеличить к-во партиций, если ключей много но так совпало, что они неправильно ложаться
- Двухуровневое партиционирование через внутренний топик. Сначала пишешь в шардированный topic-raw (контент-агностично), отдельный сервис перераспределяет с учётом фактической нагрузки.

## Консьюмер, ребалансировка, эксплуатация

### **Как именно работает rebalance и когда он происходит?**
**Запускается, когда:**\
- новый член присоединяется или существующий уходит
- член перестаёт слать heartbeat дольше `session.timeout.ms`
- Консьюмер не успел обработать батч за `max.poll.interval.ms`
- Явный вызов `enforceRebalance()` или из _admin API_
- Изменилась топология: добавлены/удалены партиции, подписка на топик изменилась.

**Как работает:**
1. **Обнаружение изменения.** Координатор группы (брокер, на котором лежит партиция __consumer_offsets для данной группы) фиксирует событие.
2. **JoinGroup.** Координатор рассылает всем участникам ответ с ошибкой `REBALANCE_IN_PROGRESS` на очередной `poll()`.\
Каждый консьюмер отправляет `JoinGroupRequest` со списком топиков и поддерживаемых Assignor'ов.
3. **Выбор лидера.** Координатор назначает одного из участников лидером группы. Лидер получает полный список участников и их подписки.
4. **Назначение партиций (на стороне лидера).** Лидер запускает стратегию (_RangeAssignor_, _RoundRobinAssignor_, _StickyAssignor_, _CooperativeStickyAssignor_) и вычисляет маппинг партиций → консьюмерам.\
Отправляет результат координатору.
5. **SyncGroup.** Координатор рассылает каждому участнику его персональный набор партиций. До получения _SyncGroupResponse_ консьюмер не читает данные.
6. **Возобновление потребления.** Каждый консьюмер начинает `poll()` только со своих партиций.

**Есть протоколы:**
- **Eager (Stop-the-world)**. Устаревший. Все консьюмеры отзывают все свои партиции.
- **Cooperative (Incremental)** - Отзываемые партициизабираются только у тех, у кого необходимо, а Консьюмеры, чей набор не изменился, продолжают читать без остановки.\
Может потребоваться два цикла _JoinGroup_/_SyncGroup_: первый отзывает, второй переназначает.
- **Static membership** - Консьюмер с фиксированным _instance.id_ при кратковременном переподключении не триггерит ребаланс, пока не истёк _session.timeout.ms_
- **Lag-based rebalancing** - новый протокол, где балансировка учитывает и нагрузку: rebalance управляется broker-side через маленькие инкрементные апдейты, быстрее в разы.

**Нюансы:**
- если `session.timeout.ms` слишком мал + GC-паузы / сетевые лаги получаем постоянные flapping ребалансы

### **Что такое static membership (`group.instance.id`)?**
**Static membership** - это механизм, который даёт consumer-инстансу стабильную идентичность в группе через group.instance.id.\
В отличие от динамического членства, где member ID генерируется брокером случайно и теряется при рестарте,\
static member при перезапуске в пределах `session.timeout.ms` возвращается в группу с тем же ID и сохраняет свой прежний assignment без запуска rebalance.\
С ним инстанс, ушедший и вернувшийся с тем же id, не триггерит ребаланс — почти безболезненный rolling deploy.\

Присвоение `group.instance.id` меняет два ключевых поведения протокола:
- Обычный consumer при close() явно покидает группу, мгновенно триггеря rebalance. Static member этого не делает — координатор продолжает считать его «временно отсутствующим» и держит слот за ним.
- Возврат в пределах `session.timeout.ms` не создаёт rebalance. Если инстанс с тем же `group.instance.id` снова шлёт **JoinGroup** до истечения session timeout, координатор просто возвращает ему его прежние партиции.

**Нюансы:**
- `group.instance.id` должен быть уникален. В группе не может быть двух живых членов с одинаковым static ID. Если новый инстанс стартует с тем же ID, он получит `FencedInstanceIdException`
- Не спасает от rebalance по `max.poll.interval.ms`. Если обработка батча затянулась дольше этого порога, consumer сам инициирует выход из группы — static membership тут не поможет.
- Если консюмер держит локальное состояние (кеш, RocksDB), привязанное к партиции, static membership экономит его прогрев при rolling рестартах — главная выгода для Kafka Streams
- `session.timeout.ms` нужно выставлять с запасом: время рестарта пода + время инициализации Spring-контекста.
- Если инстанс отвалился насовсем, координатор будет держать его слот до истечения `session.timeout.ms`.\
Чем больше этот таймаут, тем дольше партиции мёртвого члена остаются необработанными.

### **Consumer lag — что это и что делать, если консьюмер отстаёт?**
**Consumer lag** — разница между самым свежим оффсетом (log end offset) партиции и оффсетом, который группа закоммитила/обработала.\
Посмотреть можно через _akhq_, или `kafka-consumer-groups.sh --describe --group X`, Micrometer `kafka.consumer.fetch.manager.records.lag.max`, _Spring Kafka_ `KafkaListenerEndpointRegistry`\
В проде lag — обязательная алерт-метрика.

**Причины:**
- **Потребитель не успевает** — CPU-bound обработка, медленный внешний вызов (БД, HTTP) на каждое сообщение, узкий пул.
- **Партиций больше, чем консьюмеров** - некоторые консьюмеры читают несколько партиций, что увеличивает нагрузку на них.
- **Партиций меньше, чем консьюмеров** - некоторые консьюмеры простаивают, хотя могли делать полезную работу
- **Слишком большой max.poll.records** — один poll() возвращает пачку, обработка которой дольше `max.poll.interval.ms` → rebalance-цикл, lag не догоняется никогда.
- **одна горячая партиция** при нормальной суммарной пропускной способности.
- **Poison pill** Одно сообщение вызывает исключение и бесконечно ретраится -> партиция стоит, lag растёт. Лечится _dead-letter topic_ / _bounded retries_
- постоянная ребалансировка

**Диагностика**:
- **Lag у одной партиции** → горячая партиция или партиция с тяжёлыми сообщениями, или с исключением.
- **Lag у всех равномерно растёт** → потребитель не справляется в принципе.

**Решение:**
- решения направлены на исправление причин.
- запустить «догоняющий» консьюмер на отдельной группе и потом смержить состояние — сложно, применяется в экстренных случаях.
- **Skip-to-latest** как крайняя мера

**Нюансы:**
- важен не столько lag, насколько старые данные обрабатываются — 1000 отставших сообщений за 10 секунд и за 10 часов — принципиально разные ситуации.

### **Kafka vs RabbitMQ — когда что выбирать?**

| Критерий                                                   | Kafka                            | RabbitMQ                        |
|------------------------------------------------------------|----------------------------------|---------------------------------|
| Нужна история / повторное чтение                           | ✅                                | ❌                               |
| >100k msg/s стабильно                                      | ✅                                | ⚠️                              |
| Несколько независимых консьюмеров на один поток            | ✅                                | Только через fanout-копирование |
| Сложная маршрутизация, приоритеты, TTL                     | ❌                                | ✅                               |
| Минимальная латентность при малом объёме                   | ⚠️ (батчинг добавляет задержку)  | ✅                               |
| Зрелая экосистема стриминга (Kafka Streams, Flink, ksqlDB) | ✅                                | ❌                               |
| Простота эксплуатации для маленькой команды                | ⚠️ (KRaft, партиции, репликация) | ✅ (проще поднять и забыть)      |

1. _Kafka_ создана для экстремальных нагрузок: миллионы сообщений в секунду на кластер и горизонтальное масштабирование за счёт партиций.\
_RabbitMQ_ обеспечивает десятки тысяч сообщений в секунду на узел с предсказуемо низкой задержкой
2. _Kafka_ гарантирует строгий порядок внутри партиции (по ключу сообщения).\
_RabbitMQ_ гарантирует порядок внутри одной очереди (при наличии одного консьюмера)
3. В _Kafka_ консьюмер может сбросить оффсет и перечитать историю (event sourcing, восстановление состояния).
В _RabbitMQ_ после подтверждения сообщение удаляется, и повторное чтение невозможно.
4. _RabbitMQ_ здесь вне конкуренции благодаря богатой системе Exchange'ей: можно маршрутизировать по точному ключу, по паттерну, по заголовкам или вещать во все очереди (fanout).\
В _Kafka_ маршрутизация сводится к выбору топика и партиции по ключу; всё остальное — на стороне приложения.

**Выбирать _Kafka_**:
- Event streaming, high-throughput, фанаут нескольким группам консюмеров;
- Event sourcing, CDC (Debezium), интеграция с аналитикой (Kafka → Flink/Spark), data pipelines;
- Нужен replay, долгое хранение, audit log;
- Гарантия порядка в рамках ключа.

**Выбирать _RabbitMQ_**:
- Сложная маршрутизация по содержимому, много очередей с разными правилами;
- **Классическая очередь задач.** Задача выполнена → сообщение удаляется. Не нужна история.
- **Низкая латентность на малых объёмах.** При тысячах сообщений в секунду и коротких очередях RabbitMQ быстрее, т.к. нет оверхеда на батчинг и дисковую запись.
- **Протоколы**: нужна поддержка AMQP, MQTT, STOMP из коробки

### **Log compaction: как работает и что такое tombstone?**
1. **Log compaction** - это политика хранения (`cleanup.policy=compact`), которая в отличие от стандартного удаления по времени или размеру сохраняет последнее известное значение для каждого ключа в партиции на неопределённый срок.\
Лог концептуально делится на две части - _Dirty section_ — сегменты с потенциальными дубликатами ключей, ещё не прошедшие compaction,\
и _Clean section_ — уже компактированные сегменты, где для каждого ключа осталось только последнее значение.\
Партиция физически состоит из сегментов — неизменяемых файлов. _Log cleaner_ (пул фоновых потоков на брокере) периодически перекопирует сегменты, удаляя записи, ключи которых встречаются позже в логе.
- Активный сегмент (в который идёт запись) никогда не компактируется
- Оффсеты не переиндексируются. Оффсеты — монотонные и с дырами.
- Порядок не нарушается: compaction только удаляет записи, но никогда не переупорядочивает их.
2. **Tombstone** — это сообщение с ключом и _null_-значением. Она сигнализирует: «удалить все предыдущие сообщения с этим ключом».
- Все предыдущие записи с ключом удаляются.
- Tombstone остаётся в логе ещё `delete.retention.ms` (по умолчанию 24 часа), чтобы консьюмеры успели его прочитать и узнать об удалении, чтобы что-то сделать на своей стороне, если необходимо

**Используется в:**
- KTable в Kafka Streams
- системные топики: `__consumer_offsets`, `_schemas`

### **Как устроены и KRaft?**
**KRaft** — это встроенный в Kafka протокол консенсуса на основе Raft. Метаданные _Kafka_ (топики, партиции, ISR, конфигурации, ACL) — это тоже лог.\
**KRaft** хранит их в специальном внутреннем топике `__cluster_metadata`, который реплицируется через _Raft_-консенсус между выделенными узлами-контроллерами.\
_Kafka_ использует саму себя для хранения метаданных. Он убирает внешнюю зависимость, радикально ускоряет failover контроллера и снимает потолок в ~200k партиций.\
Кворум требует большинства: 3 контроллера переживают 1 отказ, 5 — 2 отказа. Чётное число контроллеров не даёт выигрыша в отказоустойчивости, только лишние накладные расходы.

## Spring Kafka

### **@KafkaListener и KafkaTemplate.**
1. `KafkaTemplate` - Обёртка над `KafkaProducer`, интегрированная в _Spring_.

**Штуки:**
- Метод `send()` возвращает `CompletableFuture<SendResult<K, V>>`. Это означает, что вызов не блокирует поток до подтверждения от брокера.
- Игнорирование результата `Future` — частая ошибка, которая приводит к «тихой» потере сообщений при ошибках.\
Правильный подход — либо подписаться на `Future` через `whenComplete()`/`addCallback()`, либо сконфигурировать `ProducerListener` для централизованной обработки успехов и ошибок отправки.
- Синхронная отправка: Вызов `future.get()` превращает отправку в блокирующую операцию.\
Это приемлемо только в особых случаях, когда нужно дождаться подтверждения перед продолжением, но в высоконагруженных системах этого следует избегать.
- `KafkaTemplate` является потокобезопасным и предназначен для переиспользования в рамках всего приложения.

2. `@KafkaListener` - это аннотация, которая превращает обычный метод _Spring_-бина в слушателя _Kafka_.
Под капотом она создаёт и управляет `MessageListenerContainer`, который отвечает за жизненный цикл консьюмера, назначение партиций и вызов вашего метода.

**Штуки:**
- параметр `concurrency` определяет количество потоков-консьюмеров, которые будут созданы для данного слушателя.
- **AckMode**: **BATCH** (по умолчанию): Оффсеты коммитятся после обработки всего батча, полученного в рамках одного poll(). \
               **RECORD**: Коммит после обработки каждой записи.
               **MANUAL / MANUAL_IMMEDIATE**: Полный контроль в руках разработчика через параметр `Acknowledgment`\
               **MANUAL** позволяет накопить подтверждения и закоммитить их в конце батча, а **MANUAL_IMMEDIATE** коммитит немедленно при вызове `ack.acknowledge()`
- **Пакетная обработка (batchListener = true)**: Позволяет принимать в методе `List<ConsumerRecord<?, ?>>` или `List<Payload>`,\
что может значительно повысить пропускную способность за счёт уменьшения накладных расходов на вызов метода и коммит.
- **Обработка ошибок:** Spring Kafka предоставляет `ErrorHandler`, который управляет повторными попытками и восстановлением.\
Для сообщений, которые стабильно вызывают ошибку, используется `DeadLetterPublishingRecoverer` для отправки в DLQ, чтобы разблокировать партицию.
- Десериализация: Всегда оборачивайте реальные десериализаторы в `ErrorHandlingDeserializer`. Это гарантирует, что некорректное сообщение будет передано в `ErrorHandler`, а не «уронит» цикл poll() с фатальной ошибкой.

**Нюансы:**
- нельзя использовать асинхронную отправку при exactly-once — нужен ``get()`` или коллбек

### **DefaultErrorHandler: как работает и чем отличается от старых ErrorHandler?**
`DefaultErrorHandler` - Перехватывает исключение, выброшенное из `@KafkaListener`-метода. Является блокирующим, т.е. никакие другие сообщения не обрабатываются, пока ретраим.
**Алгоритм:**
- Исключение → `DefaultErrorHandler.handleRemaining(...)` или `handleOtherException(...)`.
- Проверяется `RetryTemplate` (через `BackOff`): можно ли ретраить.
- Если ретраи не исчерпаны → _seek_ на текущий оффсет, сообщение перечитывается.
- Если ретраи исчерпаны → вызывается `ConsumerRecordRecoverer` (обычно `DeadLetterPublishingRecoverer`).
- Оффсет коммитится, обработка переходит к следующему сообщению.

**Нюансы:**
- По умолчанию `FixedBackOff(0, Long.MAX_VALUE)` бесконечные ретраи без пауз. Без `DeadLetterPublishingRecoverer` — сообщение ретраится вечно.
- В batch-режиме `DefaultErrorHandler` по умолчанию ретраит весь батч. Для поэлементной обработки — `setBatchRecoverAfterException(true)`.
- не все ошибки имеет смысл повторять. `DefaultErrorHandler` содержит список исключений, которые считаются неповторяемыми и сразу отправляются в recoverer.\
По умолчанию это `DeserializationException`, `MessageConversionException` и другие ошибки, связанные с конвертацией/десериализацией. Вы можете расширить этот список через `addNotRetryableExceptions()`.
- счётчик ретраев живёт в контейнере, а не в оффсете — рестарт приложения обнуляет счётчик.
- `DeserializationException` возникает до передачи в `@KafkaListener`. Перехватывается через `ErrorHandlingDeserializer`, а не через `DefaultErrorHandler` напрямую. Нужно оборачивать десериализатор.
-  Является блокирующим, т.е. никакие другие сообщения не обрабатываются, пока ретраим.

### **@RetryableTopic — блокирующие vs non-blocking ретраи.**
`@RetryableTopic` аннотация в нагрузку к `@KafkaListener`, которая автоматически создаёт цепочку ретрай-топиков и DLT.\
Превносит неблокирующий подход к ретраям.\
При ошибке сообщение не перечитывается, а отправляется продюсером в `orders-retry-N` с задержкой через `DeliveryAttemptHeader` и `@RetryableTopic`-инфраструктуру.

**Нюансы:**
- Поскольку проблемная запись «откладывается», а следующие за ней обрабатываются, строгая гарантия порядка внутри партиции нарушается.
- Можно использовать оба подхода вместе, для определённых исключений выполняются быстрые блокирующие ретраи прямо на месте,\
а если они не помогли, тогда запись пересылается в неблокирующий retry-топик для дальнейших, более длительных попыток. Некоторые исключения можно сразу отправлять в DLT, минуя любые ретраи.

**Example:**
```java
@RetryableTopic(
    attempts = "4",                          // 1 основная + 3 ретрая
    backoff = @Backoff(delay = 2000, multiplier = 2.0, maxDelay = 10000),
    dltStrategy = DltStrategy.FAIL_ON_ERROR, // что делать после исчерпания
    retryTopicSuffix = "-retry",
    dltTopicSuffix = "-dlt",
    autoCreateTopics = "true"                // авто-создание топиков
)
@KafkaListener(topics = "orders")
public void handle(OrderEvent event) { ... }
```
### **Нюанс, который любят копнуть: кастомный DefaultErrorHandler «конфликтует» с @RetryableTopic.**
`@RetryableTopic` перехватывает исключение до того, как оно дойдёт до `DefaultErrorHandler` и Если `@RetryableTopic` обработал исключение, `DefaultErrorHandler` его не увидит.\

**Как быть:**
- не использовать совместно `@RetryableTopic` и кастомный `DefaultErrorHandler`
- если всё-таки хочется, нужно `@RetryableTopic` писать в `deadLetterTopic`, а в consumer'е, читающем dead-letter topic, реализовать свою логику

### **JSON-сериализаторы Spring Kafka и заголовок `__TypeId__`.**
- __TypeId__ нужен чтобы консьюмер знал, в какой класс десериализовать. Без него пришлось бы жёстко привязывать один класс на топик.
- С __TypeId__ можно в один топик писать разные события и десериализовать полиморфно.

## Kafka Streams

### **KStream vs KTable.**
    KStream и KTable — две фундаментальные абстракции Kafka Streams, отражающие две разные модели данных: поток фактов и таблицу состояний
1. **KStream** - каждое сообщение — независимый факт («insert»). Ничего не перезаписывается, история полная. KStream — это бесконечный поток immutable-записей.\
Использование: аудиты, алерты, транформации потоков, репликация, аналитика по факту происшедшего.
2. **KTable** - каждая запись это апсерт по ключу: «текущее состояние». Новая запись с тем же ключом замещает старую (а значение null — это удаление, тот самый tombstone).\
Таблица на компакченном топике = снимок состояния на данный момент. Использование - материализованные представления, дедупликация по ключу, обогащение потока справочником.\
Тут changelog топик компакченный. _KTable_ может быть материализована в локальный _RocksDB_ (по умолчанию).
### **Что такое state store и как Kafka Streams переживает падение инстанса?**
**State store** — это локальное, встроенное в процесс приложения _key_-_value_ хранилище, которое _Kafka Streams_ создаёт для каждой _stateful_-операции (_count_, _aggregate_, _reduce_, _join_).\
Оно нужно, чтобы хранить промежуточное состояние обработки, не отправляя его во внешнюю БД на каждый запрос.

**Как устроено:**
- Store привязан к партиции (_task_). Каждый инстанс _Streams_-приложения обрабатывает свой набор партиций и держит локальную копию стейта только для своих партиций. Это не распределённая база на весь кластер, а шарды, разъехавшиеся по инстансам.
- Changelog-топик — источник истины. Каждая запись в `state store` дублируется в компакченный changelog-топик (`<app-id>-<store-name>-changelog`).\
Запись в `store` идёт так: сначала в локальный RocksDB, затем _async_ в _changelog_. Формат: ключ — _<key>_, значение — текущее состояние; для оконных сторов ключ включает окно.
- Checkpoint-файл. После каждого коммита (по умолчанию каждые `commit.interval.ms = 100` мс в _exactly-once_, 30 с в _at-least-once_) инстанс пишет checkpoint-файл с оффсетами, соответствующими текущему стейту. Это чтобы при рестарте не переигрывать весь _changelog_ с нуля.

**Порядок восстановления при падении:**
1. **Стандартный путь (быстрый).** 
- Инстанс рестартует
- Streams видит checkpoint-файл 
- восстанавливает RocksDB из локального стейта (он же на диске, если вы не использовали in-memory store)
- позиционирует себя на оффсеты из checkpoint
- продолжает обработку. Локально всё уже есть, восстановление из changelog не требуется.
2. **Деградированный путь (медленный).**
- Локальный стейт недоступен (диск отвалился, под пересоздался в K8s без PV, или in-memory store)
- _restore consumer_ читает _changelog_-топик с начала и материализует стейт заново. На большом changelog это минуты–часы. Отсюда важность: changelog компакченный (маленький после компакции), стейт не больше, чем нужно, и — PV в Kubernetes, если store большой.
3. **Миграция партиций.**
- При ребалансе партиции переезжают между инстансами: новый владелец восстанавливает стейт для этих партиций из changelog (у него локальной копии нет).\
_Kafka Streams_ обрабатывает это как «restore task». Если _changelog_ большой — ребаланс становится дорогим; чем меньше стейт, тем быстрее миграция.

**Ключевая настройка: Standby Replicas - `props.put(StreamsConfig.NUM_STANDBY_REPLICAS_CONFIG, 1);`**
Каждый инстанс держит _hot-standby_ копии стейта для чужих партиций (пассивно, не обрабатывает, только хранит).\
При падении инстанса его партиции переезжают на _standby_-владельца — _restore_ почти мгновенный (восстанавливать нужно только данные, пришедшие с момента последнего коммита standby).\
Цена: x2 диска/памяти на каждый стейт. В K8s rolling деплой + _standby_ — лучшая комбинация против простоя обработки.

**Exactly-once и стейт:** транзакции Kafka покрывают и записи в input-топик (оффсеты), и changelog-топик, и output.\
При краше транзакция откатывается целиком — стейт и output консистентны. Чекпоинты пишутся только на границе транзакций (`commit.interval.ms` — дефолт 100 мс в EOS).\
Без **EOS** при краше между коммитом и записью в _changelog_ возможна рассинхронизация: стейт «дальше» оффсетов — лечится wipe'ом локального стейта и полным восстановлением (_Streams_ делает это автоматически: если _checkpoint_ и _changelog_ расходятся — задача идёт в restore с wipe).

**Нюансы:**
- `state.cleanup.delay.ms` — сколько ждать перед удалением локальных файлов стейта после того, как партиция ушла другому инстансу (защита от flapping).
- Cторы лучше именовать(`Materialized.as("name")`), иначе сгенерится нечитаемый внутренний топик; именованный `store` легче мониторить и не будет пересоздан при изменении топологии.
- **Interactive Queries** — позволяют читать стейт наружу (**REST** endpoint поверх _RocksDB_), но помните: данные local-only, для консистентных ответов нужен metadata-сервис (KafkaStreams.metadataForStateStore) с перенаправлением запросов на «правильный» инстанс.
- Должен быть TTL в стейте (через punctuator или windowed store с retention), иначе _changelog_ и _RocksDB_ растут бесконечно. _Windowed stores_ имеют retention по времени, KV-сторы — нет.
- In-memory store оправдан только для маленьких состояний, где полный replay при старте приемлем, либо когда персистентность не нужна.
- Changelog auto-created — помните, что stateful-топология тихо создаёт дополнительные топики и партиции; при нескольких агрегациях и join'ах их число может вырасти кратно.
- Мониторьте restore time и lag warmup/standby-реплик — именно эти метрики предсказывают, насколько болезненным будет следующий failover.
### **Что такое `num.standby.replicas`?**
`num.standby.replicas` - настройка задающая число горячих резервных копий каждого стейт-стора, которые каждый инстанс держит для партиций, обрабатываемых другими инстансами группы.

**Без standby - `num.standby.replicas=0`**
```markdown
Node A: task-0 (active, State Store)
Node B: task-1 (active, State Store)

Падает Node A → task-0 переназначается на Node B
→ Node B читает changelog с нуля → восстановление секунды/минуты
→ Всё это время партиции этого task не обрабатываются → лаг растёт
```

**С standby `num.standby.replicas=1`**
```markdown
Node A: task-0 (active)
Node B: task-1 (active), task-0 (standby) ← реплицирует состояние

Падает Node A → task-0 переключается на Node B
→ State Store уже на месте, восстановление мгновенное
→ Лаг не растёт (или растёт минимально)
```

_Standby_-нода постоянно читает те же _changelog_-топики и поддерживает локальную копию _State Store_ в актуальном состоянии, Но не обрабатывает записи и не коммитит оффсеты.

**Нюансы:**
- Каждая _standby_-реплика — это полная копия store. При `num.standby.replicas=1` потребуется вдвое больше дискового пространства на кластере (1 активная копия + 1 standby).
- Для маленьких стейтов (in-memory, мегабайты) выгода от standby почти нулевая — восстановление из changelog и так быстрое. Standby имеет смысл, когда стейт большой (сотни МБ–ГБ на инстанс).

### **Kafka Streams vs Flink/Spark.**
1. **Kafka Streams** — это Java-библиотека, которая встраивается прямо в ваше приложение (Spring Boot-сервис).
- Ей не нужен отдельный кластер, **YARN** или Kubernetes-кластер для вычислений — только _Kafka_ как транспорт
- Масштабирование происходит за счёт запуска нескольких экземпляров приложения: каждый становится членом _Consumer Group_ и автоматически координирует распределение партиций.\
- Состояние хранится локально в _RocksDB_ и бэкапится в changelog-топики _Kafka_.
- _Exactly-once_ — транзакциями _Kafka_ (EOS v2), и это дёшево, потому что всё остальное — тоже _Kafka_.
- Модель ресурсов предсказуемая и простая — это просто ещё один _consumer_ на _Kafka_-кластере.

**Ограничения:** 
- время события слабее (_event-time_ грациозность появилась, но no delayed-join семантики уровня Flink);
- нет обогащения через внешние источники на каждый элемент (просят кешировать в _GlobalKTable_);
- окна беднее (нет _per-session_ с произвольным merge, нет зонных поздних элементов как в Flink);
- процессинг-гарантии завязаны на Kafka-транзакции.

**Используем когда:** когда вы строите микросервис, который потребляет и производит данные в Kafka, и хотите нулевую дополнительную инфраструктуру.\
Идеально для событийно-ориентированных микросервисов, простых агрегаций, обогащения потоков данными из Kafka.
Ограничения: только Kafka как источник, ограниченный объём состояния (диск одного узла), нет сложных CEP и многоstream join'ов.
2. **Flink** — это отдельный распределённый кластер с _JobManager_ (координатор) и _TaskManager_ (воркеры).\
Состояние также хранится в _RocksDB_, но периодически чекпоинтится в распределённую файловую систему (S3, HDFS) с использованием алгоритма _Chandy-Lamport_.\
Чекпоинты инкрементальные — сохраняются только изменения с прошлого снапшота, что позволяет держать терабайты состояния с низкими накладными расходами.
- **Exactly-once** — чекпоинты + two-phase commit sink'и; стейт большой (ТБ на job) — норма.
- **Сложные паттерны**: CEP (паттерны последовательностей событий), итеративные графы, сложные многопоточные топологии.
- несколько источников помимо Kafka (файлы, БД, HTTP).

**Используется когда** нужна сложная stateful-обработка:антифрод, CEP (обнаружение паттернов), джойны нескольких потоков, обработка с разными источниками (Kafka, CDC из БД, файлы),\
а также когда состояние не помещается на диск одной машины. Цена — более сложная эксплуатация (управление _JobManager_/_TaskManager_) и более высокий порог входа (_event time_, _watermarks_, _state backend_).
3. **Spark Structured Streaming** - кластерный движок, но с микробатчевой моделью: поток нарезается на небольшие батчи, которые обрабатываются как обычные Spark-задачи.
- подходит там, где уже есть _Spark_: переиспользование экосистемы (_Delta_ Lake, _ML_, _SQL_), единый кодбатч/стрим.
- по умолчанию работает в микробатч-режиме с задержкой 100 мс+. Экспериментальный continuous-режим (~10 мс) существует, но не является основным сценарием.

**Используется когда** команда уже глубоко в экосистеме _Spark_ (batch ETL, Lakehouse, Databricks) и может принять секундную задержку.\

### **Как обрабатывается event time и что такое окно?**
**Event time** — время, когда событие произошло на источнике; **processing time** — когда его обработал ваш код; **ingestion time** — когда запись попала в _Kafka_\
**Окно (window)** — это способ сгруппировать события с одним ключом по временному интервалу для агрегации (_count_, _reduce_, _aggregate_) или _join'а_.\
Окна применяются только к _KStream_ (не к _KTable_) и только через `groupByKey().windowedBy(...)`.\
**Четыре типа окон в Kafka Streams:**
1. **Tumbling** `TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5))` - Окна по 5 минут, не перекрываются: `[0–5), [5–10), [10–15)`.\
Каждое событие попадает ровно в одно окно. Классика для «количество заказов за 5 минут».
2. **Hopping** `TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ZERO).advanceBy(Duration.ofMinutes(1))` Окно длиной 5 минут, сдвиг — 1 минута.\
Событие попадает в несколько окон (до 5). Даёт «скользящее среднее за 5 минут, обновляемое каждую минуту». Дороже по state.
3. **Sliding** `SlidingWindows.ofTimeDifferenceWithNoGrace(Duration.ofMinutes(5))` Окно определяется интервалом между событиями, а не фиксированной сеткой.\
Окно для события e — все события в диапазоне `[e.time - 5min, e.time]`. Используется для «сколько событий произошло в пределах 5 минут от данного».
4. **Session** `SessionWindows.ofInactivityGapWithNoGrace(Duration.ofMinutes(10))` Окно — это сессия активности: события группируются, пока пауза между ними не превысит inactivity gap.\
Сессия «растёт» при каждом новом событии внутри gap'а, а при паузе — закрывается. Идеально для веб-аналитики.

Реальные события приходят не по порядку: событие с _timestamp_ _12:00:03_ может прийти после события _12:00:05_ (сеть, ретраи, разные продюсеры).\
Если бы окно закрывалось сразу по наступлении границы, мы бы потеряли «опоздавшие» события.

**Grace period** — окно «терпения» после закрытия окна, в течение которого опоздавшие события всё ещё принимаются и обновляют результат.\
Окно `[0–5)` формально закрывается в _5:00_, но grace до _6:00_ позволяет событиям с timestamp в `[0–5)`, пришедшим с опозданием до _6:00_, обновить агрегат.

**Нюансы:**
- _stream time_ — это временная метка, привязанная к конкретному событию (обычно из поля timestamp сообщения или заголовка).\
Stream time не меняется, пока нет данных. При новом событии — перепрыгивает на его метку (не плавно идёт)\
Равна почти всегда — `event time`, иначе окна «плывут» при задержках.
- Если пришла очень старая запись, она будет отброшена.
- По умолчанию _windowed_-агрегация эмитит каждое обновление окна _downstream_ — то есть для окна `[0–5)` вы получите результат после каждого входящего события.\
Часто это не нужно: хочется один финальный результат, когда окно закрылось. `suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded()))`\
_untilWindowCloses_ буферизует все обновления и эмитит только финальный результат после истечения окна + grace.\
Требует дополнительного _state store_, поэтому нужно следить за памятью. _untilTimeLimit_ — альтернатива, эмитит по таймауту (более «мягкий» вариант, не гарантирует одно значение на окно)
- _suppress_ работает только для windowed _KTable_ и только с _emitEarlyWhenFull_ или _unbounded_ в зависимости от гарантий. Для _session_ windows он исторически не поддерживался в полном смысле.
- Каждое окно держит state до истечения grace. При большом _grace_ и коротких окнах state может расти нелинейно — следите за _rocksdb_ размером и `windowstore.changelog.additional.retention.ms`.

## Schema Registry и Avro

### **Зачем нужен Schema Registry?**
**Проблемы Продюсера и консьюмера:**
Kafka хранит байты, а не типизированные объекты. Если каждый продюсер сериализует по-своему, а консьюмер десериализует «как получится»,\
любое изменение модели данных (добавили поле, переименовали, сменили тип) ломает потребителей в рантайме — часто молча, через `ClassCastException` или `NullPointerException` в глубине бизнес-логики.\
В распределённой системе с десятками сервисов, читающих один топик, это гарантированный инцидент.\
_Schema Registry_ превращает это в явный контракт с проверкой на этапе регистрации: продюсер не сможет зарегистрировать несовместимую схему, и поломка обнаруживается до того, как «плохое» сообщение попадёт в топик.

**Как это работает:**
1. **Регистрация схемы.**  Продюсер при старте регистрирует схему в _Registry_ под субъектом (_<topic>-value_ / _<topic>-key_). _Registry_ присваивает ей глобальный ID и сохраняет в своём хранилище (Kafka-топик _schemas).
2. **Сериализация.** `KafkaAvroSerializer` (или _Protobuf_/_JSON Schema_) кладёт в сообщение только ID схемы (5 байт: magic byte + 4-байтовый ID) плюс сериализованный _payload_. Полная схема не дублируется в каждом сообщении — это ключевая экономия трафика.
3. **Десериализация.** _KafkaAvroDeserializer_ читает _ID_ из заголовка сообщения, идёт в _Registry_ (с кэшем), получает схему и десериализует _payload_. Консьюмеру не нужно знать точный класс **DTO** — он получает _GenericRecord_ или _SpecificRecord_, соответствующий схеме.
4. **Эволюция схем.** Новая версия схемы регистрируется под тем же субъектом и получает новый **ID**. Старые **ID** остаются, поэтому старые сообщения читаются старыми схемами, новые — новыми. Это и есть _schema evolution_.

**Форматы схем**
- **Avro** — исторически основной формат для _Confluent Schema Registry_. Компактный бинарный формат, богатая поддержка эволюции (_default_ values для новых полей), **SpecificRecord** генерируется из .avsc. 
- **Protobuf** — популярен в _polyglot_-средах, эффективен по размеру, но эволюция строже (номера полей, reserved для удалённых).
- **JSON Schema** — компромисс: человекочитаемо, но менее эффективно по размеру и слабее по эволюции.

### **Режимы совместимости: Backward / Forward / Full (+ транзитивные).**

| Режим                                                       | Правило                                                                    | Пример                                                          |
|-------------------------------------------------------------|----------------------------------------------------------------------------|-----------------------------------------------------------------|
| BACKWARD (дефолт)                                           | 	Добавлять опциональные поля,удалять поля	                                 | Новые консьюмеры читают старые данные                           |
| FORWARD                                                     | 	Добавлять поля, удалять опциональные                                      | 	Старые консьюмеры читают новые данные                          |
| FULL	                                                       | Только безопасные изменения в обе стороны                                  | 	Совместимо и вперёд, и назад                                   |
| NONE	                                                       | Всё что угодно                                                             | 	Никто не защищён — только для прототипов                       |
| BACKWARD_TRANSITIVE / FORWARD_TRANSITIVE / FULL_TRANSITIVE	 | То же, но проверяется против всех предыдущих версий, а не только последней | 	Строже, но безопаснее при откате на произвольную старую версию |

**Нюансы:**
- Изменение типа поля (_int_ → _long_, _string_ → _enum_) несовместимо ни в одном режиме кроме **NONE**.
- Переименование поля в _Avro_ допустимо через _aliases_. В _Protobuf_ — через _reserved_. В _JSON Schema_ — нет нативной поддержки.
- Транзитивные режимы замедляют регистрацию. При **FULL_TRANSITIVE** и 100 версиях каждая регистрация проверяет все 100.
- BACKWARD не защищает от удаления обязательного поля. Если в старой схеме поле было обязательным, новая схема его не содержит, и дефолта нет → старые данные не парсятся.
### **Ловушка: «Можно ли добавить required-поле в Avro-схему?»**
Технически — да, но с оговоркой: в _Avro_ нет явного маркера _required_. «Обязательным» поле делает отсутствие значения по умолчанию (_default_).
- При **BACKWARD**: новая схема читает старые данные. В старых записях нового поля нет. Если поле обязательное (без дефолта), десериализатор не знает, какое значение подставить → ошибка.
- При **FORWARD**: старая схема читает новые данные. Старый код не знает о новом поле и игнорирует его. Здесь бы сработало, но **BACKWARD** уже сломан.
- При **FULL**: оба условия. **BACKWARD** сломан → **FULL** тоже.

Нюансы:
- Добавить поле без _default_ технически можно, но это нарушает **BACKWARD** и **FULL** совместимость.
- _default_ — это не значение для новых записей. В _Avro_ _default_ подставляется при чтении старых данных новым reader'ом, когда поля в writer-схеме нет.
- Безопасный путь для **BACKWARD**/**FULL** — двухэтапный: сначала с _default_, позже (если действительно нужно) без него.
- _Avro_ не даёт «_required_» из коробки — строгая обязательность достигается отсутствием _default_, а это всегда конфликт с чтением старых данных.

## «Каверзные» вопросы senior-уровня из реальных собесов

### **Как защитить сообщение от дублей на стороне консьюмера?**
1. Храним идемпотентный ключ в БД(редис или обычная) и проверять его при каждой обработке. В сообщение кладётся уникальный бизнес-идентификатор (_orderId_, _transactionId_, _eventId_).
2. Идемпотентность операции в целом - при повторении операции ничего не меняется. Есть минус, т.к. мы выполняем операцию занимая ресурсы. 

**Что не работает:**
- `exactly-once` - Как только есть запись в БД, HTTP-вызов или отправка письма — гарантия рвётся. Дубли во внешних системах остаются.
- Дедуп в памяти (_ConcurrentHashMap_). Теряется при рестарте и не работает при нескольких инстансах (каждый видит свою часть партиций, но после ребаланса может получить уже обработанные). Годится только как «быстрый фильтр» перед БД-дедупом.
- **Redis** - если редис отваливается, то делаем дубли.

**Senior-подход** — сначала спроектировать операцию идемпотентной (upsert, conditional update), и только если это невозможно — вводить dedup store с eventId и транзакционной границей.

### **Как гарантировать доставку при записи в БД + Kafka?**
**Transactional Outbox**
Идея: не писать в **Kafka** напрямую из бизнес-транзакции. Вместо этого — писать событие в таблицу outbox в той же БД и в той же транзакции, что и бизнес-данные.\
А отправку в **Kafka** выносить в отдельный процесс, который читает outbox.

### **Что такое poison pill и как не заблокировать партицию?**
- **Poison pill** Одно сообщение вызывает исключение и бесконечно ретраится -> партиция стоит, lag растёт. Лечится _dead-letter topic_ / _bounded retries_

### **Что делает транзакционная сессия консьюмера и почему нельзя naively коммитить оффсеты при параллельной обработке?**
Kafka хранит не множество завершённых оффсетов, а один максимальный закоммиченный оффсет на партицию. Всё, что ниже этого оффсета, считается «потреблённым», и повторно доставлено не будет.\
Если вы обрабатываете записи одной партиции параллельно и коммитите оффсеты по мере завершения каждой задачи, порядок завершения может не совпадать с порядком оффсетов.\
Тоесть можно закоммитить офсет 10, потом закомитится 5 (или прилага упадёт до коммита 5 - мы пропустим 5 окончательно и безповоротно, что не ок), то чтение начнётся с 5, что не ок ибо дубликаты.\

Нельзя  коммитить оффсеты «по мере готовности» отдельных сообщений из одного батча (нарушает монотонность и порядок), доверять auto-commit в сочетании с async-обработкой (auto-commit вообще не знает про in-flight), отправлять оффсеты из треда пула.

**Неправильная транзакционная сесия:**
```java
messages.forEach(msg -> {
    CompletableFuture.runAsync(() -> {
        process(msg);
        consumer.commit(msg.offset()); // ← each thread commits independently
    });
});
```

**Правильная транзакционная сессия** 
```java
consumer.begin();
try {
    // Process all messages (parallel internally is fine)
    messages.forEach(msg -> process(msg));
    // Write results to output topics
    producer.send(outputTopic, results);
    // Commit offset atomically
    consumer.commit();
    producer.commit();
} catch (Exception e) {
    consumer.abort();
    producer.abort();
    // Offset NOT committed, writes NOT visible
}
```
### **Что делать, если для чтения нужен произвольный порядок (например, по клиенту, а не по orderId)?**
Суть проблемы: При записи партиционирование было по _orderId_. Сообщения с одним _orderId_ в одной партиции, порядок по заказам сохраняется.\
Но на стороне чтения нужно обрабатывать в порядке _clientId_ — группировать все заказы клиента и обрабатывать их последовательно.\
Партиции, в которые попали заказы разных клиентов, перемешаны. В рамках одной партиции нет порядка по _clientId_.
1. **Перепартиционирование в промежуточный топик**
✅ - простой, масштабируемый, порядок по clientId гарантирован.\
❌ - дополнительный топик, дополнительная задержка, дополнительная инфраструктура.
2. **Kafka Streams repartition()** - Под капотом — тот же промежуточный топик, но управление в рамках одного приложения.
3. Писать события в БД (или хранилище с сортировкой), читать `ORDER BY customer_id, event_time`
4. Поменять ключ на продюсере

### **Когда Kafka — плохой выбор?**
1. **Request-response**
2. **Тяжёлая аналитика поверх необработанных данных** - Kafka не хранилище
3. **Сложная маршрутизация.** 
4. **Delayed / scheduled messages, per-message TTL.**
5. **Selective consumption по контенту.**
6. «Читать только сообщения, где `type=PAYMENT`» — в Kafka нельзя без чтения всего и фильтрации на клиенте (что убивает смысл).
7. **Приоритеты сообщений.** - _Kafka_ не поддерживает приоритеты. Все сообщения в партиции равны
8. Мало сообщений
9. Маленькая OPS команда.

### **Что мониторить в проде?**
1. **Under-Replicated Partitions** - Реплика отстала от лидера. Риск потери данных при падении лидера. **> 0 → алерт**
2. **Consumer Lag**
3. **Rebalance Duration**
4. **Rebalance Rate**
5. **Размер партиций** - Горячие партиции
6. **CPU / Memory на брокер**

    Under-replicated partitions, частота shrink/expand ISR, p99 latency запросов, consumer lag по группам.

## Пара слов про Т-Банк отдельно

На System Design там ждут не «Kafka и микросервисы на всё», а трезвый дизайн: связка Kafka (event streaming) + PostgreSQL (транзакции) + Redis (кэш), компромиссы consistency vs availability, синхронное vs асинхронное взаимодействие. Проверяют, можете ли вы за 45 минут спроектировать event-driven сервис с оценкой нагрузки. Показательный момент из реального опыта: кандидату на System Design однажды указали, что архитектура «плохая, потому что много компонентов и медленный Kafka» — то есть там ценят простоту решения не меньше, чем масштабируемость.
