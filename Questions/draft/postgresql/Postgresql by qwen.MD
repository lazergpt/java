## 🏗 Архитектура и внутренности (MVCC, WAL, Vacuum)

1. **Как в PostgreSQL устроена MVCC (Multi-Version Concurrency Control)?**
   *Чтение и запись не блокируют друг друга. При обновлении строки создается новая версия (tuple), старая помечается как неактуальная.*

2. **Что такое dead tuples и как работает VACUUM / AutoVacuum?**
   *Dead tuples — это устаревшие версии строк после UPDATE/DELETE. VACUUM очищает место для переиспользования, AutoVacuum делает это автоматически на основе статистики.*

3. **Что такое WAL (Write-Ahead Logging) и как он обеспечивает durability?**
   *Изменения сначала пишутся в журнал WAL на диск, и только потом применяются к самим данным. Это позволяет восстановить БД после краша.*

4. **Что такое Checkpoint и как он влияет на производительность?**
   *Момент, когда все грязные страницы из памяти сбрасываются на диск. Частые чекпоинты могут вызывать I/O spikes (решается настройкой `checkpoint_completion_target`).*

## 🔒 Транзакции, изоляция и блокировки

5. **Чем отличаются уровни изоляции Read Committed, Repeatable Read и Serializable в Postgres?**
   *В RC видны коммиты других транзакций между чтениями. В RR используется снимок (snapshot) — фантомы и неповторяемые чтения исключены. Serializable (SSI) использует сериализацию снимков для предотвращения аномалий сериализации.*

6. **В чем разница между `SELECT ... FOR UPDATE`, `FOR SHARE` и `FOR NO KEY UPDATE`?**
   *`FOR UPDATE` блокирует строку для обновления/удаления. `FOR SHARE` разрешает читать, но запрещает обновлять. `FOR NO KEY UPDATE` блокирует строку, но позволяет обновлять поля, не входящие в уникальные индексы (полезно для снижения contention).*

7. **Как Postgres обнаруживает и разрешает дедлоки (deadlocks)?**
   *Есть фоновый процесс `deadlock_detector`, который периодически строит граф ожиданий и откатывает транзакцию-жертву при обнаружении цикла.*

8. **Что такое Hot Standby и как читающие реплики видят данные?**
   *Реплика применяет WAL, но для чтений использует MVCC-снимки. Если вакуум на мастере удалил данные, которые еще читает реплика, возникает конфликт, и реплика может отменить читающий запрос.*

## 📇 Индексы и типы данных

9. **Когда стоит использовать BRIN-индекс вместо B-Tree?**
   *Для данных, которые физически упорядочены на диске (например, временные ряды или `created_at`). Он занимает в сотни раз меньше места, чем B-Tree.*

10. **Чем отличаются индексы GIN и GiST? Когда какой применять?**
    *GIN (Generalized Inverted Index) быстрее для поиска (полнотекст, JSONB, массивы), но медленнее при вставке. GiST (Generalized Search Tree) хорош для геометрических данных и полнотекста с ранжированием.*

11. **Как правильно индексировать JSONB? В чем разница между `jsonb_ops` и `jsonb_path_ops`?**
    *`jsonb_ops` создает индекс для всех ключей и значений (поддерживает `?`, `@>`). `jsonb_path_ops` индексирует только пути (поддерживает только `@>`), но он намного меньше и быстрее.*

12. **Почему UUID v4 — плохой выбор для первичного ключа в B-Tree индексе?**
    *Из-за случайности он вызывает сильную фрагментацию B-Tree и постоянные page splits при вставке, что убивает производительность на больших объемах. Лучше использовать UUID v7 (временной) или `BIGSERIAL`.*

13. **Что такое Index-Only Scan и Heap-Only Tuples (HOT)?**
    *Index-Only Scan читает данные прямо из индекса, не обращаясь к таблице (требует `INCLUDE` или покрытия всех полей). HOT позволяет обновлять строку без изменения индексов, если затронуты неиндексируемые поля.*

## ⚡ Оптимизация запросов и Партицирование

14. **Как Postgres выбирает тип соединения (Nested Loop, Hash Join, Merge Join)?**
    *Nested Loop — для маленьких таблиц или при наличии индекса. Hash Join — для больших несортированных выборок (требует памяти). Merge Join — если обе стороны уже отсортированы (например, по индексу).*

15. **Как работают уникальные индексы на партицированных (partitioned) таблицах?**
    *Уникальный индекс в Postgres **обязан** включать все столбцы ключа партицирования. Глобальных уникальных индексов (как в Oracle) нет.*

16. **Что такое `EXPLAIN (ANALYZE, BUFFERS)` и на что смотреть в выводе?**
    *Показывает реальный план выполнения. Смотреть на `shared hit` (чтение из RAM) vs `read` (чтение с диска), а также на реальное время vs estimated time (если сильно отличается — статистика устарела, нужен `ANALYZE`).*

17. **В чем разница между CTE (Common Table Expressions) и подзапросами? Что такое `MATERIALIZED`?**
    *До PG 12 CTE были "оптимизационными барьерами" (всегда материализовались). В PG 12+ они инлайнятся, но можно принудительно материализовать через `MATERIALIZED`, чтобы вычислить тяжелый запрос один раз.*

## ☕ Связка Java + PostgreSQL (Специфика для Java-разработчика)

18. **Как оптимизировать массовую вставку (batch insert) через Hibernate / JDBC?**
    *В JDBC нужно включить `reWriteBatchedInserts=true` (для PostgreSQL драйвера), чтобы он переписывал `INSERT INTO ... VALUES (1), (2)` в один запрос. В Hibernate настроить `batch_size` и использовать `StatelessSession` или `StatefulSession` с правильной стратегией генерации ID (Sequence).*

19. **Что такое `fetchSize` в JDBC и как он влияет на потребление памяти?**
    *Определяет, сколько строк драйвер JDBC подгружает в память за один сетевой round-trip. По умолчанию в Postgres он равен 0 (грузит всё сразу), что может привести к OOM при больших выборках. Нужно ставить 100–500.*

20. **Как настроить HikariCP для высоконагруженного приложения?**
    *Не завышать `maximumPoolSize` (формула `core_count * 2 + effective_spindle_count`, обычно 10–30 хватает). Настроить `leakDetectionThreshold`, использовать `prepareStatement` кэширование.*

21. **В чем разница между режимами PgBouncer: Session, Transaction и Statement?**
    *Session — пул на сессию БД. Transaction — пул на транзакцию (экономит подключения, но нельзя использовать `SET` или `LISTEN`). Statement — пул на один запрос (самый жесткий, нельзя использовать транзакции).*

22. **Как в Java правильно работать с большими транзакциями, чтобы не "повесить" БД?**
    *Дробить на батчи, использовать курсоры (в JDBC это автоматическое переключение на серверный курсор при большом `fetchSize`), избегать удержания блокировок на время сетевых вызовов или бизнес-логики.*
