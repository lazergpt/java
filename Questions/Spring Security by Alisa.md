# Вопросы по Spring Security для собеседований (Senior Java Developer)

## Базовый блок — спрашивают почти всем

### **Чем аутентификация отличается от авторизации?**
1. **Аутентификация** — «кто ты», проверка логина и пароля, токена. `AuthenticationManager` -> `UserDetailsService`, создание объекта `Authentication` с `principals` и `credentials` и помещение его в `SecurityContextHolder`.
2. **Авторизация** — «что тебе можно». `AuthorizationManager`, `FilterSecurityInterceptor` / `AuthorizationFilter`, аннотации `@PreAuthorize`/`@PostAuthorize`, конфигурация `authorizeHttpRequests`.

Аутентификация бывает один раз при логине, а авторизация при каждом доступе к защищённому ресурсу.

### **В чём разница между 401 и 403?**
**401 Unauthorized** — не аутентифицирован: сервер не знает, кто ты. Возникает когда пользователь не предоставил валидные учётные данные или токен \
**403 Forbidden** - аутентификация пройдена успешно, но недостаточно прав для доступа к ресурсу.

**Нюансы:**
- если пользователь анонимный, запрос на защищенный ресурс сначала получит 401. Чтобы аноним сразу получал 403, нужно явно разрешить анонимный доступ (permitAll или anonymous()), тогда AccessDeniedHandler перехватит отсутствие прав.
- для микросервисов `AuthenticationEntryPoint` и `AccessDeniedHandler` почти всегда переопределяются. Первый — чтобы вернуть `JSON` вместо страницы логина браузера, второй — чтобы прокинуть в ответ специфический код ошибки (например, `INSUFFICIENT_SCOPE`) для фронтенда.

### **Что такое `SecurityContextHolder` и как он работает?**
`SecurityContextHolder` — это статический _holder_ для объекта `SecurityContext`, который содержит `Authentication` (информацию об аутентифицированном пользователе).\
Контекст привязывается к текущему потоку. Любой код внутри этого потока (сервис, репозиторий) может получить пользователя через `SecurityContextHolder.getContext().getAuthentication()` без передачи параметров.\
Стратегии хранения (задаются через `SecurityContextHolder.setStrategyName()` или системное свойство `spring.security.strategy`:
- **MODE_THREADLOCAL** по дефолту.
- **MODE_INHERITABLETHREADLOCAL** — дочерние потоки наследуют контекст родителя, но для `@Async`
- **MODE_GLOBAL** — один контекст на всё **JVM** (для _standalone_-приложений, в вебе не используется)

**Нюансы:**
- Если вызывается `@Async` или используете `ExecutorService`, `ThreadLocal` не передаст контекст в новый поток автоматически.\
Для этого **Spring Security** предоставляет обертки вроде `DelegatingSecurityContextRunnable` или `DelegatingSecurityContextExecutor`, которые копируют контекст из текущего потока в целевой и очищают его после выполнения.
- контекст автоматически чистится после завершения запроса
- `SecurityContextHolder.MODE_INHERITABLETHREADLOCAL` не спасает при работе с пулами потоков, потому что пул переиспользует потоки, созданные раньше, наследование срабатывает только в момент создания потока.
- Прямой доступ к **principal** лучше получать через `@AuthenticationPrincipal` или `SecurityContextHolderStrategy` это удобнее для тестов, чем статический вызов.
### **Как устроен фильтр-чейн Spring Security?**
`FilterChain` в `Spring Security` — это цепочка сервлет-фильтров, которые обрабатывают каждый HTTP-запрос до попадания в контроллер.\
Порядок работы:
- Контейнер вызывает `DelegatingFilterProxy`. 
- `DelegatingFilterProxy` передаёт управление `FilterChainProxy`. 
- `FilterChainProxy` перебирает свой список `SecurityFilterChain` (в порядке, заданном аннотацией @Order или порядком объявления) и находит первую, чей RequestMatcher совпал с запросом.
- Далее запрос проходит через фильтры, определённые в этой конкретной `SecurityFilterChain`.

Ключевой компонент — `DelegatingFilterProxy` (единственный фильтр, регистрируемый в `Servlet Container`), который делегирует обработку внутреннему `FilterChainProxy`.\
`FilterChainProxy` - точка входа для всех запросов и содержит в себе список цепочек `SecurityFilterChain`\
**Основные фильтры, имеют строгий порядок:**
- `ChannelProcessingFilter` — редирект **HTTP→HTTPS**
- `CsrfFilter` — проверка **CSRF**-токена
- `LogoutFilter` — обработка logout
- `UsernamePasswordAuthenticationFilter` — аутентификация по логину/паролю
- `BearerTokenAuthenticationFilter` — аутентификация по **JWT**
- `DefaultLoginPageGeneratingFilter` — генерация страницы логина
- `ExceptionTranslationFilter` — перевод исключений безопасности в HTTP-ответы
- `AuthorizationFilter` — проверка прав доступа
- `SecurityContextHolderFilter` — сохранение/очистка **_SecurityContext_**

**Нюансы:**
- Порядок фильтров определяется через `.addFilterBefore()`, `.addFilterAfter()` или кастомный `SecurityFilterChain` bean.\
  Место вставки критично. Например, кастомный фильтр для проверки JWT-токена логично ставить до `UsernamePasswordAuthenticationFilter`, чтобы он успел заполнить контекст.
- Фильтры выполняются для ВСЕХ запросов, даже если endpoint публичный
- Можно отключать фильтры: `.csrf().disable()`, `.cors().disable()`
- Кастомные фильтры: наследовать от `OncePerRequestFilter` или `GenericFilterBean`
- `FilterChainProxy` находит только первое совпадение. Если запрос совпал с цепочкой, он не будет проверять остальные, даже если они тоже подходят.\
Поэтому более специфичные цепочки (например, для `/api/**`) должны иметь более высокий приоритет (меньший `@Order`), чем общие (например, для `/**`)
- В приложении можно (и нужно) определять несколько бинов `SecurityFilterChain`
- Чтобы увидеть, какие именно фильтры активны в вашей цепочке, включите логирование на уровне **DEBUG** для `org.springframework.security.web.DefaultSecurityFilterChain`.\
В логах при старте приложения будет выведен полный список фильтров в порядке их выполнения.
- Фильтры работают до `DispatcherServlet` — значит, контроллеры, AOP и `@ExceptionHandler` из **MVC** не видят исключений фильтров. 
- Обработку ошибок в фильтре делают через `authenticationEntryPoint` и `accessDeniedHandler`.

### **Чем `Role` отличается от `Authority`?**
Технически разницы в типе нет — и роль, и _authority_ это `GrantedAuthority`(интерфейс, представляющий одно право). Разница — в семантике и в префиксе.\
1. **Authority** — атомарное право (_permission_): _user:read_, _order:cancel_, _product:write_. Тонкий уровень доступа.
2. **Role** —  это частный случай _Authority_ с префиксом `ROLE_`, группа _authority_, логический «ярлык» пользователя: _ROLE_ADMIN_, _ROLE_USER_.

**Проверка:**
- `.hasAuthority("READ_ORDERS")` — проверяет точное совпадение.
- `.hasRole("ADMIN")` — автоматически добавляет префикс `ROLE_` и проверяет `ROLE_ADMIN`

**Нюансы:**
- Префикс настраивается: через `GrantedAuthorityDefaults` можно изменить префикс ролей (по умолчанию _ROLE_)
- В токенах **JWT** роли часто хранятся как **claims**, которые маппятся в `GrantedAuthority` через `JwtAuthenticationConverter`
- пользователь может иметь и роли, и отдельные `authority` одновременно

### **Session vs JWT — что выбрать и почему?**
1. Session-based
**Плюсы:**
- Проще отозвать доступ (удалил сессию из хранилища — пользователь разлогинен)
- Меньший размер токена (только session ID в cookie)
- Просто реализовать мгновенный logout на всех устройствах

**Минусы:**
- Требует sticky sessions или shared session store (_Redis_) в кластере
- Не подходит для mobile/native apps (проблемы с cookies)
- Сервер хранит состояние → хуже масштабируемость

2. **JWT**
**Плюсы:**
- stateless, но если нужен logout то уже и нет
- Работает из коробки для mobile, SPA, API
- Токен содержит claims → меньше запросов к БД за информацией о пользователе

**Минусы:**
- Невозможно отозвать до истечения TTL (без blacklist/whitelist, что убивает stateless)
- Большой размер токена (особенно с множеством claims)

**Нюансы:**
- Spring Security 6+: `BearerTokenAuthenticationFilter` для JWT, `SessionManagementFilter` для сессий
- Для Logout в JWT нужен blacklist (Redis с TTL = время жизни токена) или versioning токенов
- Для JWT обязательно `SessionCreationPolicy.STATELESS` и отключение **CSRF** (так как нет cookie-аутентификации)
- Может быть Две цепочки `SecurityFilterChain` с разными `@Order`. Одна — для `/ui/**` (formLogin + Session), другая — для `/api/**` (JWT + Stateless)
- JWT не шифрует данные (только подпись). Не кладите туда чувствительные данные.
- Где хранить **JWT** на фронте: `localStorage` уязвим к **XSS**. **HttpOnly** cookie безопаснее от **XSS**, но возвращает проблему **CSRF** (нужен токен). Для browser-based **SPA** часто выбирают **cookie** + **CSRF**, для мобилок — header.

**В итоге:**
- JWT для микросервисов и REST API которым пользуется множество разных UI
- Для односервисного монолита лучше сессии.

### **Что делает `@PreAuthorize` и чем отличается от `@Secured`?**
1. `@Secured` 
- устаревшая
- поддерживает только роли и только в виде строк в виде строк. Аналог `@PreAuthorize("hasRole('...')")`
- нет SpEL выражений
- нет доступа к аргументам метода 
- Включается через `@EnableGlobalMethodSecurity(securedEnabled = true)`
2. `@PreAuthorize`
- Полная поддержка _SpEL_ (Spring Expression Language)
- Доступ к аргументам метода, return value, authentication object
- Кастомные expression handlers
- Включается через `@EnableMethodSecurity` (**_Spring Security 6+_**) или `@EnableGlobalMethodSecurity(prePostEnabled = true)`

**Нюансы:**
- `@PreAuthorize` парсит SpEL при каждом вызове - может влиять на производительность
- Proxy-based: работает только через Spring AOP proxy → не работает при вызове методов внутри того же класса (this.method())
- `@PreAuthorize` проверяется до входа в метод, `@PostAuthorize` — после (может использовать return value)
- могут спросить про `@RolesAllowed`это _**Jakarta EE**_ стандарт, по сути тот же механизм, что `@Secured`

## JWT и токены — обязательный блок для REST/микросервисов

### **Опишите жизненный цикл JWT-аутентификации.**
1. Получение токена (Login)
```-POST /auth/login {username, password}
   → AuthenticationManager.authenticate()
   → UserDetailsService.loadUserByUsername()
   → Проверка credentials (PasswordEncoder)
   → Генерация JWT (JwtEncoder / JwtGenerator)
   ← Response: {accessToken, refreshToken}
```
2. Доступ к защищённому ресурсу (Request) - Клиент отправляет запрос к защищённому эндпоинту, добавляя заголовок `Authorization: Bearer <access_token>` .
```
GET /api/orders (Header: Authorization: Bearer <jwt>)
→ BearerTokenAuthenticationFilter.extractToken()
→ JwtDecoder.decode() ← парсинг + проверка подписи + claims
→ JwtAuthenticationConverter.convert() ← маппинг claims → GrantedAuthority
→ Создание JwtAuthenticationToken (authenticated=true)
→ SecurityContextHolder.setContext()
→ AuthorizationFilter.checkAccess() ← @PreAuthorize / .hasRole()
→ Controller
```
3. Обновление токена (Refresh)
```
POST /auth/refresh {refreshToken}
→ Валидация refresh token (отдельный JwtDecoder или opaque token store)
→ Проверка: не отозван? не истёк?
→ Генерация НОВОГО access + refresh (rotation)
← Response: {newAccessToken, newRefreshToken}
```  
4. Logout - Поскольку Access Token stateless, «мгновенный» logout невозможен. Обходится через blacklist
- при разлогине добавить токен в blacklist (Redis с TTL = оставшееся время жизни)
- в кастомном `JwtDecoder` или `BearerTokenResolver` проверять _blacklist_ перед валидацией

**Нюансы:**
- Старый Refresh Token инвалидируется, и выдаётся новый. Если злоумышленник украл старый Refresh Token и попытается его использовать после того,\
как легитимный клиент уже обновил токен, сервер обнаружит повторное использование отозванного токена и сможет заблокировать всю сессию злоумышленника.
- `JwtDecoder` vs `JwtEncoder`: _**Decoder**_ — валидация (симметричный/асимметричный ключ), _**Encoder**_ — генерация. В микросервисах: Auth Service подписывает (private key), Resource Services только проверяют (public key)

**В Spring Security существует два подхода к реализации JWT цикла:**
 - Ручной (кастомный фильтр): Вы пишете `JwtAuthenticationFilter`, сами парсите и валидируете токен (например, через библиотеку `jjwt`). Это даёт полный контроль, но требует написания большего количества кода.
 - Встроенный (OAuth2 Resource Server): Если вы используете стандартный **_OAuth2/OIDC_**, **_Spring Security_** предоставляет готовый `BearerTokenAuthenticationFilter` и `JwtAuthenticationConverter`.\
Вы только настраиваете `JwtDecoder` (через JWKS URI или публичный ключ), а фреймворк сам делает всю тяжёлую работу по валидации и маппингу claims в authorities . Для нового проекта это предпочтительный путь.
### **Как отозвать JWT до истечения срока жизни?**
1. Token Blacklist (наиболее распространённый) - при логауте помещаем JTI или токен в Redis а в кастомном `JwtDecoder` проверяем наличие, если есть значит логаученый токен и ничего рефрешить не нужно.\
   ✅ - точный контроль, TTL автоматически истекает\
   ❌ - убивает pure stateless\
   ❌ - зависимость от Redis
2. **_Token Versioning / Generation Counter_** - в токене храним версию, при генерации версию инкрементируем и кладём в токен и БД, когда нужно отозвать токен инкрементируем версию в БД.\
Когда приходит запрос проверяем версию в токене, если не совпадет, тогда токен устарел и инвалидирован.
   ✅ - один ключ на пользователя вместо blacklist per token\
   ❌ - отзыв всех токенов сразу (нет гранулярности)/
3. Короткоживущий Access + ротация Refresh Token - ограничение урона при утечке токена
4. JWK Key Rotation - Сменить signing key и все ранее выданные токены становятся невалидными. Используется при утечке приватного ключа.

**Нюансы:**
- Не используйте blacklist для каждого запроса в high-load → кешируйте проверки локально (Caffeine + Redis)

### **Как устроен refresh-токен и зачем он нужен?**
Это обычный JWT (или opaque-строка), но с другим набором claims: type: "refresh", subject, jti, exp — обычно без ролей, потому что роли должны браться заново при выпуске нового access.\
Access token делают короткоживущим для безопастности, но заставлять пользователя логинится каждые 15 минут неприемлемо.\
Для этого применяют `Refresh token` который живёт 24 и более часа. Его задача - получать новые Access token.\
**На клиенте можно хранить:**
- **Web:** HttpOnly + Secure + SameSite=Strict cookie (не localStorage!)
- **SPA:** BFF pattern (backend-for-frontend хранит refresh, фронтенд получает только short-lived access)

**Нюансы:**
- Каждое использование refresh → выдача нового refresh. Старый инвалидируется. Это предотвращает replay-атаки.
- Хранится на серверной стороне хотя бы частично: либо сам токен (или его хеш) в БД/Redis со статусом, либо одна запись на пользователя (версионирование). Именно хранение даёт возможность отзыва.
- **reuse detection** - если «отозванный» **refresh** внезапно предъявлен повторно, это почти наверняка кража: легитимный клиент пользуется новым токеном, а старым пользуется вор, как результат инвалидируется вся семья токенов
- race condition. Если у пользователя плохой интернет и запрос на обновление токена «потерялся» после того, как сервер уже ротировал токен, клиент попытается использовать старый refresh-токен.\
Сработает **reuse detection**, и пользователя выкинет. Поэтому в продакшене часто добавляют «льготный период» (grace period) в 30–60 секунд, в течение которого старый токен еще принимается, чтобы покрыть сетевые сбои.
-  токен связывают с device id или fingerprint, чтобы refresh, украденный с одного устройства, не работал с другого.

### **Где хранить JWT на клиенте и почему?**
1. **localStorage / sessionStorage** - очень не рекомендуется, прям считается за косяк\
❌ - Доступен через JavaScript, соответственно при любой XSS-уязвимость = кража токена\
❌ - localStorage не имеет механизма автоматического истечения — токен остаётся там, пока его не удалят вручную \
❌ - Нет защиты от CSRF (но JWT в header обычно не уязвим к CSRF)\
2.  **Memory (JavaScript variable)** - обычно хранят **Access Token**\
✅ - Безопаснее _localStorage_ (не персистентный)\
❌ - Но всё ещё доступен через JS → XSS уязвим\
❌ - Теряется при перезагрузке страницы\
❌ - Подходит только для SPA с сильным CSP и отсутствием inline scripts\
3. **HttpOnly + Secure + SameSite Cookie** - лучший вариант для приложений, HttpOnly делает куки невидимым для JS. 
✅ - Недоступен через JavaScript → защита от чтения токена через XSS\
✅ - Secure → только HTTPS\
✅ - SameSite=Strict/Lax → защита от CSRF. SameSite - говорит браузеру не отправлять куки при межсайтовых запросах.\
❌ - HttpOnly не предотвращает выполнение вредоносным скриптом аутентифицированных запросов от имени пользователя. Он лишь защищает сам токен от чтения. Поэтому XSS всё равно остаётся серьёзной угрозой, просто её последствия иные.
4. **Mobile:** Keychain (iOS) / Keystore (Android) - для мобилок
✅ - Зашифрованное системное хранилище\
✅ - Недоступно другим приложениям\
✅ - Единственный правильный вариант для native apps\

**Нюансы:**
- **Access Token** и **Refresh Token** хранятся по разному. Аccess в памяти + refresh в HttpOnly cookie + CSRF-защита refresh-эндпоинта
- Для SPA и браузерных клиентов паттерн Backend-for-Frontend (BFF) считается наиболее безопасным. В этой модели браузер вообще не получает JWT.\
Вместо этого бэкенд (BFF) управляет токенами на сервере, а клиенту выдаёт только HttpOnly cookie с идентификатором сессии. Это полностью исключает токен из зоны досягаемости JavaScript.
- Если BFF избыточен, используйте HttpOnly cookie для refresh-токена (он самый ценный) и короткоживущий access-токен в памяти (in-memory).\
Access-токен в переменной JavaScript исчезает при закрытии вкладки, а при перезагрузке страницы клиент «молча» обновляет его через refresh-cookie.\
Это усложняет кражу, хотя и не устраняет XSS-риск полностью.

### **Что за нагрузка `aud`, `iss`, `jti` в JWT?**
1. `iss` - кто выдал токен
- Проверяется на стороне resource server
- Предотвращает подмену токена от другого authorization server
- В Spring: `JwtValidators.createDefaultWithIssuer("https://auth.example.com")`
2. `aud` - Для кого предназначен токен.
- Resource server проверяет, что он есть в списке получателей
- Предотвращает использование токена, выданного для сервиса A, в сервисе B
- В Spring: `.audience(List.of("orders-service"))` в validator
- Может быть string или array
3. `jti` - Уникальный идентификатор токена.
- Обязателен для token revocation (blacklist по jti), Без jti отзыв конкретного токена невозможен.\
Именно jti кладут в Redis-blacklist при логауте (о чём мы говорили в предыдущем вопросе), чтобы можно было точечно инвалидировать конкретный access-токен до истечения его exp
- Предотвращает replay-атаки (при проверке уникальности)
- Должен быть глобально уникальным (UUID v4)

**Нюансы:**
- Валидация обязательна: никогда не доверяйте JWT без проверки `iss` и `aud`. Это базовая защита от token confusion attacks

## OAuth2 и микросервисы

### **Объясните flow Authorization Code Grant.**
Authorization Code Grant — это трёхсторонний flow (клиентское приложение, пользователь, Authorization Server), в котором клиент никогда не видит пароль пользователя.\
Ключевая идея: клиентское приложение получает краткоживущий, одноразовый authorization code через браузер, а затем обменивает его на токены по защищённому back-channel соединению.\

Как это работает (упрощенная схема)\
Представьте, что вы (Пользователь) хотите дать приложению (Клиент, например, сервису для планирования задач) доступ к вашему календарю в Google (Сервер ресурсов).

1. Запрос авторизации. Вы нажимаете в приложении кнопку «Войти через Google». Приложение не спрашивает у вас пароль.\
Вместо этого оно перенаправляет ваш браузер на страницу авторизации Google.\
В ссылке передаются идентификатор приложения (client_id), запрашиваемые права (например, calendar.read) и специальный временный адрес (redirect_uri), куда Google должен вернуть пользователя.
2. Аутентификация и согласие. На странице Google вы вводите свой логин и пароль (приложение их не видит).\
Google спрашивает: «Приложение "Планировщик" хочет читать ваш календарь. Разрешить?». Вы нажимаете «Разрешить».
3. Выдача кода (Authorization Code). Google не пускает приложение сразу. Он перенаправляет ваш браузер обратно по адресу redirect_uri,\
который указало приложение. В URL этого адреса добавляется временный одноразовый параметр — code (тот самый Authorization Code).\
Приложение видит этот код в адресной строке браузера.
4. Обмен кода на токен (Back-channel request). Приложение берет этот код и напрямую, со своего сервера (не через ваш браузер!),\
обращается к Google по защищенному каналу (back-channel). Оно предъявляет этот код и свой секретный ключ (client_secret), который знает только само приложение и Google.
5. Выдача токена. Google проверяет код и секрет. Если всё верно, он отдает приложению Access Token (токен доступа) и часто Refresh Token (токен обновления).
6. Доступ к данным. Теперь приложение может ходить в Google API, предъявляя этот Access Token в заголовках запросов, и читать ваш календарь. Пароль пользователя приложение так и не узнало.

**Authorization Code Grant полностью устраняет проблемы:**
- **Утечка пароля**	- Приложение никогда не видит ваш пароль. Если оно окажется вредоносным или его взломают, злоумышленники не получат доступ к вашему аккаунту Google, почте или банку.
- **Отсутствие контроля доступа** - Вы даете приложению только те права, которые запросили. Вы можете отозвать доступ для конкретного приложения в настройках основного сервиса, не меняя пароль.
- **Отсутствие (2FA)** - Если бы приложение знало пароль, ему пришлось бы как-то имитировать и ваш второй фактор (SMS, код из приложения). Поток с кодом делегирует проверку личности Google, где уже настроена вся ваша сложная защита.
- **Компрометация через браузер (CSRF)** - В спецификацию встроен обязательный параметр state — случайная строка, которую приложение генерирует в начале. Google возвращает этот state вместе с кодом. Приложение проверяет, совпадает ли он. Если злоумышленник попытается подменить запрос, state не совпадет, и приложение отклонит код.
- **Перехват кода**	- Код, прилетающий в браузер, сам по себе бесполезен. Чтобы обменять его на токен, нужен client_secret, который хранится на сервере приложения и не передается через браузер.
- **Долговременный доступ** - Использование Refresh Token позволяет приложению работать долго (например, ежедневно синхронизировать календарь), не заставляя пользователя каждый раз заново логиниться, при этом не храня его пароль.

**Как работает PKCE (пошагово):**

1. **Генерация секрета:** Перед тем как отправить пользователя на страницу авторизации, приложение на устройстве генерирует случайную длинную строку — code_verifier. Это его одноразовый секрет.
2. **Создание вызова:** Приложение хеширует эту строку (обычно алгоритмом SHA-256) и кодирует результат в Base64URL. Получается code_challenge.
3. **Запрос кода:** Приложение отправляет пользователя на сервер авторизации, передавая в запросе code_challenge (и метод хеширования, например S256).
4. **Привязка кода:** Сервер авторизации получает code_challenge, сохраняет его у себя во временном хранилище и привязывает к выдаваемому Authorization Code. Теперь этот код валиден только в паре с этим конкретным вызовом.
5. **Обмен кода на токен:** Пользователь разрешает доступ, браузер возвращает приложение с code. Теперь приложение напрямую (без участия браузера) отправляет запрос на обмен кода на токен. В этом запросе оно передает сам code и оригинальный code_verifier (незахешированную строку).
6. **Проверка:** Сервер берет полученный code_verifier, хеширует его тем же способом и сравнивает с тем code_challenge, который сохранил на шаге 4. Если хеши совпадают — сервер отдает Access Token.

Таким образом, PKCE динамически создает временный «секрет» для каждой попытки входа, который не нужно нигде постоянно хранить и который невозможно восстановить, перехватив данные из браузера.

**Почему это безопасно:**
- Злоумышленник, перехвативший Authorization Code в браузере, не знает code_verifier. Он знает только code_challenge, который прилетел в открытом виде.\
Превратить хеш обратно в исходную строку (от code_challenge получить code_verifier) невозможно из-за необратимости функции хеширования.
- Приложение-отправитель и приложение-получатель — это одно и то же приложение на одном устройстве. Оно сохранило code_verifier только в своей оперативной памяти.\
Никакой другой процесс или приложение на устройстве (без root-доступа или джейлбрейка) не может его прочитать.
- Сервер отклонит запрос злоумышленника, так как тот не сможет предоставить правильный code_verifier, который бы захешировался в сохраненный code_challenge.

**Нюансы:**
- PKCE — обязателен для публичных клиентов. Для SPA и мобильных приложений (которые не могут безопасно хранить client_secret) используется расширение PKCE.\
PKCE заменяет статичный client_secret на динамический криптографический вызов.\
Клиент генерирует случайный code_verifier, вычисляет от него code_challenge (SHA256) и отправляет challenge на Шаге 1. При обмене на Шаге 4 он передаёт исходный code_verifier, и сервер проверяет соответствие.\
Это защищает от перехвата authorization code.
- **client_secret** живет: В веб-приложениях он хранится в переменных окружения сервера или в защищенном хранилище секретов.\
В мобильных и десктопных приложениях (публичных клиентах): он не живет нигде. Хранить его внутри приложения (в коде, бинарном файле или конфигурациях) бессмысленно.\
Как только приложение установлено на устройство пользователя, злоумышленник может декомпилировать его, проанализировать сетевой трафик или просто выкачать файл приложения и достать секрет за считанные минуты.

### **Resource Server vs Authorization Server — кто что делает?**
1. **Authorization Server** - выдаёт токены и управляет ими. 
- Аутентификация пользователей (login, MFA)
- Выдача access/refresh tokens (JWT или opaque)
- Публикует свой публичный ключ (JWKS endpoint) для того, чтобы Resource Server мог проверять подпись токена.
- Хранение credentials, sessions, refresh tokens.
- Для создания такого сервера используется зависимость `spring-boot-starter-oauth2-authorization-server`
2. **Resource Server** - Сервис, который обслуживает бизнес-запросы и проверяет токены.
- Валидация access token (подпись, `iss`, `aud`, `exp`)
- При каждом запросе к API он ожидает заголовок `Authorization: Bearer <token>`
- Проверяет подпись токена (через JWKS) или обращается к Authorization Server за интроспекцией (если токен непрозрачный)
- Извлекает из токена _authorities_/_scopes_ и проверяет, хватает ли прав для доступа к конкретному эндпоинту (обычно через `@PreAuthorize` или `authorizeHttpRequests`)
- Настраивается через `oauth2ResourceServer(jwt)` или `oauth2ResourceServer(opaqueToken)` в `SecurityFilterChain`
- никогда не хранит пользовательские пароли и не знает ключей подписи — только публичные.

**Нюансы:**
- в монолите «AS» и «RS» могут жить в одном приложении

    Resource server валидирует access-токен (`BearerTokenAuthenticationFilter`, JWKS-проверка), authorization server выпускает токены. Ожидают понимания, что JWT сам по себе «не безопасность», а формат.

### **Как Spring Security настроен в реактивном стеке (WebFlux)?**
    `SecurityContextHolder` с ThreadLocal не работает — вместо него `ReactiveSecurityContextHolder` с Reactor Context. Хороший маркер того, что человек видел не только servlet-стек.

## Практические ловушки и «интересные» вопросы

16. **Как работает CSRF и зачем он нужен в SPA?**
**Cross-Site Request Forgery** — атака, при которой злонамеренный сайт выполняет запросы к вашему приложению от имени аутентифицированного пользователя, используя его cookie.

**Нюансы:**
- CSRF актуален только если аутентификация основана на cookies, так как Браузер автоматически прикрепляет cookies к cross-origin запросам. Когда токен в Headers — то такого не происходит.

**Защита:**
- CSRF-токен (стандарт Spring): сервер выдаёт случайный токен (синхронизатор, double-submit cookie или HttpOnly-независимый), клиент обязан вернуть его в каждом мутирующем запросе (X-CSRF-TOKEN). Злоумышленник его не знает — same-origin policy не даёт прочитать чужой токен. Spring Security держит его в CsrfTokenRepository (cookie-based для SPA — CookieCsrfTokenRepository.withHttpOnlyFalse(), чтобы JS мог читать и слать).
- SameSite cookie (Lax/Strict): браузер не прикладывает cookie к кросс-сайт запросам.

`CsrfFilter` - Сервлет-фильтр, который проверяет валидность CSRF-токена для state-changing запросов (POST, PUT, DELETE, PATCH).\
`CookieCsrfTokenRepository` — это одна из стратегий хранения CSRF-токена, которая хранит его в cookie (вместо сессии), что делает её удобной для SPA и JavaScript-клиентов.\

### **Как защититься от brute-force?**
1. Ограничение попыток на уровне инфраструктуры или приложения. Это самый прямой способ предотвратить автоматизированный подбор. Обычно реализуется на уровне фильтра `OncePerRequestFilter`.\
Для каждого IP-адреса или имени пользователя(а часто их комбинации) ведется счетчик запросов в скользящем окне времени. Если количество попыток входа превышает лимит (например, 5 раз за 15 минут), сервер возвращает статус `429 Too Many Requests`
2. **Блокировка учетной записи** - После N неудачных попыток входа (например, 3 или 5) аккаунт блокируется на определенное время (например, на 30 минут) или до ручной разблокировки администратором.\
Обычно реализуется через кастомный `UserDetailsService`. В сущности пользователя добавляются поля `failedAttempts` и `lockTime`.\
При неудачном логине они инкрементируются, а при успешном — сбрасываются. Если `lockTime` в будущем, аккаунт считается заблокированным.
3. **Использование CAPTCHA** - Создается кастомный фильтр (наследник `OncePerRequestFilter`), который проверяет наличие и правильность введенного кода.\
Фильтр необходимо вставить в цепочку до `UsernamePasswordAuthenticationFilter`, чтобы отсечь ботов до проверки пароля.
4. Мониторинг и Алёрты - всплеск 401 с одного IP, неудачи по множеству username с одного источника (password spraying — атака «один пароль на много пользователей»,

**Нюансы:**
- Проверка лимитов должна происходить до вызова `PasswordEncoder.matches()`, иначе атакующий нагружает CPU медленным хешированием.
- атакующий может намеренно залочить учётные записи чужих пользователей. Поэтому комбинируют: блокировка по IP + username, а не только по аккаунту.
- `AccountStatusUserDetailsChecker` — это стандартный компонент из экосистемы **Spring Security**.\
Его задача — проверить статус учетной записи пользователя (загруженной в виде объекта `UserDetails`) непосредственно в момент аутентификации (входа в систему).\
Т.е. вызывается он сразу после доставания из БД и проверки пароля.

### **Как безопасно мигрировать пароли с одного хеша на другой?**
Самый безопасный и бесшовный для пользователя путь — обновлять хеш в момент успешного логина.\
Начиная со Spring Security 5.0, `DelegatingPasswordEncoder` является рекомендуемым решением для миграции.\
Он работает по принципу префикса: каждый хеш в базе данных хранится в формате _{id}encodedPassword_, где _{id}_ указывает, какой алгоритм использовался (например, _{bcrypt}, {sha256}, {md5}_.\
- Пользователь логинится со старым паролем.
- `DelegatingPasswordEncoder` успешно проверяет его через legacy-энкодер. 
- В кастомном `AuthenticationSuccessHandler` (или `AuthenticationProvider`) вы проверяете, начинается ли хеш с _{bcrypt}_. 
- Если нет — берете «сырой» введенный пароль и хешируете его новым `BCryptPasswordEncoder`, сохраняя в БД с префиксом _{bcrypt}_.

**Нюансы:**
- Если пользователь давно не заходил, то при следующем логине просим его поменять пароль.
- Разовый перенос «всё сразу» не работает, потому что исходный хеш не расшифровывается — пароль можно перевычислить, только зная его в открытом виде, а он есть только у пользователя в момент логина.
- Если ленивая миграция не подходит, тода Нужно обнулить все пароли сразу -> всем пользователям уведомление + принудительный сброс пароля через email-ссылку.
- `DelegatingPasswordEncoder` создан именно для таких переходов: каждый хеш самодокументируется префиксом, поэтому миграцию можно растягивать по времени.

### **Зачем соль и почему нельзя просто SHA-256?**
- _SHA-256_ очень быстро вычисляется, на ГПУ можно считать миллионы в секунду, _bcrypt_ вычисляется намного медленнее, что в данной ситуации хорошо.
- BCrypt имеет параметр _strength_ который в значении 12 даёт 2^12 итераций и выполняется около 250 мс. Если поставить _strength_ слишком большой, то можно поставить под грозу DDOS атаки сервис.
- bcrypt технически не может быть без соли.
- в bcrypt два одинаковых пароля с использованием одной и той же соли и одинаковой стоимости будут выглядеть одинаково.
- Угроза, против которой работает медленный хеш — offline: атакующий вытащил дамп БД и перебирает на своём железе. Каждая попытка стоит 250 мс × миллиарды вариантов.
- Без соли одинаковые пароли дают одинаковый хеш. Злоумышленник может использовать предвычисленные таблицы (rainbow tables) для мгновенного обратного поиска.
- Обычно соль уникальная для каждого пользователя, а не одна на всю базу, и хранится рядом с хешом.
- Pepper - Секретная константа, добавляемая к паролю перед хешированием: `H(pepper || salt || password)`.\
В отличие от соли, не хранится в БД — живёт в конфиге/KMS приложения. При утечке только базы (без файловой системы приложения) перебор невозможен вовсе — атакующий не знает pepper.\
Это дополнительный слой, а не замена: соль обязательна, pepper — хорошая практика, где возможна.


### **Как добавить свой фильтр в цепочку?**
1. Создаём фильтр через наследование от `OncePerRequestFilter`
2. Добавляем в одну из следующих позиций:
- `addFilterBefore(filter, class)`   Перед указанным фильтром 
- `addFilterAfter(filter, class)`   После указанного фильтра 
- `addFilterAt(filter, class)`   Замена указанного фильтра
3. **Выбор позиции в цепочке:**
- Аутентификация → перед `AuthorizationFilter`
- Логирование/аудит → после `AuthorizationFilter` (знаем пользователя)
- Rate limiting → перед аутентификацией (экономим ресурсы)
- CORS → до CSRF (preflight OPTIONS не должен блокироваться)

**Нюансы:**
- Не регистрировать security-фильтр как обычный `@Bean Filter` т.к. он будет автоматически применятся ко всем запросам вне цепи
- Не забывать вызывать `chain.doFilter()` иначе запрос зависнет
- Не модифицировать response после `chain.doFilter()`
- у `OncePerRequestFilter` есть гарантия того, что логика фильтра выполнится ровно один раз для каждого реального HTTP-запроса. `GenericFilterBean` не даёт такой гарантии и его лучше не использовать.
- Не хардкодить порядок через числовые значения `@Order` — используйте относительное позиционирование через `addFilterBefore/After`

### **Что произойдёт с `SecurityContext` в асинхронной задаче или `CompletableFuture`?**
`SecurityContext` теряется. По умолчанию он хранится в `ThreadLocal`, в то время как асинхронные задачи выполняются в другом потоке.
Способы исправления:
1. Для `@Async` нужно обернуть `TaskExecutor` в `DelegatingSecurityContextAsyncTaskExecutor`.
```java
@Bean
public TaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor delegate = new ThreadPoolTaskExecutor();
    // настройки delegate
    return new DelegatingSecurityContextAsyncTaskExecutor(delegate);
}
```
2. Для `CompletableFuture` нужно обернуть `ExecutorService` в `DelegatingSecurityContextExecutorService`
```java
ExecutorService delegate = Executors.newFixedThreadPool(10);
ExecutorService secureExecutor = new DelegatingSecurityContextExecutorService(delegate);

// Теперь контекст пробросится
CompletableFuture.supplyAsync(() -> {
    // SecurityContextHolder.getContext().getAuthentication() доступен
    return someService.doSomething();
}, secureExecutor);
```
3. Ручная передача через `DelegatingSecurityContextRunnable`/`Callable`
```java
Runnable task = () -> {
    Authentication auth = SecurityContextHolder.getContext().getAuthentication();
    // ✅ работает
};

executor.execute(new DelegatingSecurityContextRunnable(task));

// Или для CompletableFuture:
CompletableFuture.supplyAsync(
    new DelegatingSecurityContextSupplier<>(() -> service.getData())
);
``` 
4. Глобальная настройка `SecurityContextHolder.MODE_INHERITABLETHREADLOCAL`. Нежелательно, так как контекст наследуется всеми дочерними потоками, включая thread pool.\
Возможны утечки между запросами. Не рекомендуется для production.\

**Нюансы:**
- Всегда очищать контекст при ручной реализации через декоратор, иначе другой запрос переиспользует поток и увидит чужой контекст. Обёртки Spring делают это автоматически.
- `SecurityContextHolder.MODE_INHERITABLETHREADLOCAL` не работает с виртуальными потоками.
- Та же проблема касается _SLF4J MDC_ и других ThreadLocal-данных.
- Можно сделать через `TaskDecorator`, но `DelegatingSecurityContext*` делает тоже самое из коробки.
- Реактивщина это другой мир: там нет ThreadLocal-привязки, контекст живёт в Reactor Context.\
`SecurityContext` достаётся через `ReactiveSecurityContextHolder.getContext()`, и его нужно явно пробрасывать через операторы `contextWrite(...)`

### **Как отдавать единый формат ошибок 401/403?**
В _Spring Security_ ошибки **401/403** обрабатываются `ExceptionTranslationFilter` до попадания в `@ControllerAdvice`, поэтому обычные `@ExceptionHandler` не работают. Нужны кастомные **entry points** и **handlers**.
- `AuthenticationException` → `AuthenticationEntryPoint` → 401
- `AccessDeniedException`   → `AccessDeniedHandler`      → 403
- для Bearer немного другое. `BearerTokenAuthenticationEntryPoint` допом вернёт заголовок `WWW-Authenticate: Bearer` \
`AuthenticationException` → `BearerTokenAuthenticationEntryPoint` → 401
`AccessDeniedException`   → `BearerTokenAccessDeniedHandler`      → 403
- `WWW-Authenticate Header` обязателен в ответе, без него некоторые библиотеки и браузер могут вести себя не корректно.

23. **Что проверит интервьюер через code review?**
    Типовой финтех-кейс: в сервисе есть `@Transactional` с сохранением в БД и вызовом внешнего API/антифрода внутри — ожидают, что вы заметите connection starvation и риск «данные закоммичены, а уведомление ушло/не ушло», и предложите outbox pattern или идемпотентность.
