### Реактивное программирование - это декларативная парадигма, которая фокусируется на асинхронных потоках данных и автоматическом распространении изменений.
#### Базовые компоненты реактивного программирования
1. **Издатель (Publisher)** - Источник, который асинхронно выдает данные. Продюсер.
2. **Подписчик (Subscriber)** - Потребитель, который получает и обрабатывает выданные данные.
3. **Подписка (Subscription)** - связь между издателем и подписчиком, управляющее потоком данных и обеспечивающее контроль обратного давления.
4. **Процессор (Processor)** - Компонент, который одновременно выступает как подписчик и издатель, преобразуя данные при их прохождении через поток.
### Манифест реактивных систем
Манифест описывает именно реактивные системы, а не реакивное программирование.
1. **Отзывчивость(Responsive)** - Система должна обеспечивать стабильно быстрое время отклика, упрощать обработку ошибок. Реализуется через:
- неблокирующие стеки(Spring WebFlux).
- таймауты.
- fallback-логику.
2. **Устойчивость(Resilient)** - Система остаётся отзывчивой даже при сбоях отдельных компонентов. Достигается благодаря:
- Автоматическое восстановление - репликация, перезапуск, повторные попытки, предохранители. Реализуются через Resilience4j;
- Graceful degradation - При частичном отказе система продолжает работать с ограниченной функциональностью.
- Изоляция сбоев - Компоненты работают независимо, ошибки не «протекают» на всю систему.
3. **Эластичность (Elastic)** - Система сохраняет отзывчивость при изменении нагрузки — от низкой до пиковой. Достигается благодаря:
- Горизонтальное масштабирование(Kubernetes, Docker). Нагрузка распределяется балансировщиком.
- Эффективное использование ресурсов - Неблокирующий ввод‑вывод, реактивные потоки позволяют обрабатывать больше запросов на тех же мощностях.
- Автомасштабирование - Кластер автоматически добавляет или убирает реплики по метрикам (CPU, RPS, latency).
4. **Взаимодействие на основе сообщений** - Компоненты общаются асинхронно через сообщения, а не через синхронные вызовы.
- Очереди и брокеры сообщений(Kafka, RabbitMQ, AWS SQS). (Spring Cloud Stream)
- Слабая связанность, Сервисы не знают друг о друге напрямую, они только публикуют и слушают события.
- Буферизация и устойчивость к временным сбоям, Если один сервис недоступен, сообщения накапливаются и обрабатываются позже.
### Реактивное программирование VS виртуальные потоки
После появления виртуальных потоков реактивщина лишилась самого важного достоинства, неблокирующего IO.
Если нет желания блокироваться на операциях ввода вывода, то проще использовать виртуальные потоки.
Но, если всё же нужно использовать backpressure, то реативный подход будет проще, так как идёт из коробки.
