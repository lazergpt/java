# java 9 notes
- в java 9 приватный метод интерфейса может быть статическим, соответственно такой метод будет доступен статическим дефолтым методам интерфейса. 
 - в приватные методы интерфейса выносится общая логика, используемая в дефолтных и статических методах интерфейса

- takeWhile() - работает подобно фильтру, но на первом же элементе, для которого предикат вернёт false, обработка стрима будет прервана и последующие элементы, независимо от предиката, будут проигнорированы.
- Этот момент нужно учитывать при работе с коллекциями в которых порядок неопределён.

- Коллекции созданные через статически метод of являются не модифицируемыми.

### Модули 
- **requires** - в модуле потребителе помечает какой модуль необходим для работы(**transitive** делает доступным зависимость для других модулей)
- **exports** - указывает на пакеты текущего модуля, которые будут доступны в модуле "пользователе"
- **exports ... to ...**  - тоже что и exports, но дополнительно можем указать каким модулям будет доступен пакет.
- **uses** - в модуле потребителе указывает интерфейс, или абстрактный класс, который должен быть доступен для _ServiceLoader_ SPI. используется с **requires**
- **provides ... with ...** - указывает интерфейс, или абстрактный класс в текущем модуле, который должен быть доступен для _ServiceLoader_ SPI модуля потребителя.

### Вопросы после главы

- Зачем в интерфейсы добавили приватные методы?
Чтобы убрать дублирование логики между default-методами интерфейса, инкапсулировать вспомогательные операции и не засорять публичный контракт.

- В чём разница между takeWhile() и limit() в Stream API?
limit(n) берёт первые n элементов независимо от их значений. takeWhile(predicate) берёт элементы, пока они удовлетворяют условию; как только встретился первый «неподходящий» — останавливается (для упорядоченных стримов).

- Когда использовать dropWhile()?
Когда нужно пропустить элементы в начале стрима, пока они соответствуют условию, и дальше работать с оставшейся частью. Например, пропустить пустые строки в начале списка или игнорировать префикс данных до определённого маркера.

- Как создать неизменяемый List?
Использовать List.of(...) (для фиксированного набора элементов) либо List.copyOf(collection) (скопировать существующую коллекцию в неизменяемый список).

- Для чего нужен Map.ofEntries() и чем отличается от Map.of()?
Map.of(k1, v1, k2, v2, ...) удобен для небольшого числа пар. Map.ofEntries(Map.Entry<?, ?>... entries) позволяет собрать мапу из заранее подготовленных записей — удобно, когда пары формируются динамически или передаются как массив.

- Как работает Arrays.mismatch()?
Сравнивает два массива и возвращает индекс первого несовпадающего элемента. Если массивы идентичны (или оба пустые) — возвращает -1. Полезно для быстрого поиска различий без полного ручного перебора.

- Как использовать ifPresentOrElse() из Optional?
Выполняет одно действие, если значение есть (consumer), и другое — если его нет (emptyAction). Пример:`opt.ifPresentOrElse(
v -> System.out.println("Есть: " + v),
() -> System.out.println("Нет значения")
);`
- Что такое ObjectInputFilter.Status и какие у него возможные значения?
Это статус проверки при десериализации объектов. Возможные значения: ALLOWED (объект разрешён), REJECTED (отклонён фильтром) и UNDECIDED (фильтр не смог принять решение). Помогает безопасно контролировать, какие объекты можно восстанавливать из потока.

- Как работает метод submit() у SubmissionPublisher?
Отправляет элемент подписчикам. Если есть свободные буферы и подписчики готовы — данные передаются. Если очередь переполнена, поведение зависит от стратегии (например, может быть отбрасывание старых элементов или блокировка). Это часть API для реактивных потоков (Flow API).

- В чём разница между директивами requires и requires transitive в модуле?
requires M — модуль зависит от M, но эта зависимость не видна клиентам этого модуля. requires transitive M — зависимость транзитивна: любой модуль, который требует текущий, автоматически получает и зависимость от M. Удобно, когда типы M используются в публичных сигнатурах текущего модуля.

- AppCDS(Application Class Data Sharing) убирает затраты на загрузку, парсинг и верификацию классов при старте JVM, что ускоряет загрузку приложения. 
При использовании AppCDS эти классы берутся из заранее подготовленного архива (shared archive) через memory‑mapping, минуя тяжёлые этапы инициализации.
Также снижает потребление памяти на 10–30% на каждый процесс позволяя нескольким JVM на одном хосте совместно использовать одни и те же страницы памяти для классов.
Это снижает RSS (реальное потребление памяти) на каждый экземпляр и повышает плотность размещения. 
легко автоматизируется, например можно указать JVM создать архив, и другим флагом указать использовать этот архив при AppCDS при следующем старте.
Если новый класс загружается не при старте, а позже (через рефлексию, плагины, ClassLoader‑хаки), то AppCDS не даст выигрыша по этому классу.

# Java 14
- оказывается при использовании switch, оператора case без блока, объявленные переменные распространяются на весь блок switch. У case есть свой блок, то переменная видна только в его блоке.

```        
        switch (a)
        {
            case 1:
                int b = 1;
                System.out.println(b);
                break;
            case 2:
                b = 2;
                System.out.println(b);
        }
```

- Скрытые классы - это специальный вид классов, которые создаются динамически в памяти во время работы программы, не имеют постоянного имени в байт-коде и полностью изолированы от остального приложения.
Используются разработчиками библиотек и фреймворков для:
* Динамическая генерация кода: Позволяют фреймворкам создавать классы «на лету» (например, прокси-классы для транзакций или заглушки в тестах, Лямбда‑выражения. )
* Безопасность и инкапсуляция: Скрытый класс невозможно найти по имени через Class.forName(), к нему нельзя обратиться напрямую в коде или через стандартную рефлексию из других модулей
* Экономия памяти (сборка мусора): Обычные классы привязаны к своему загрузчику (ClassLoader) и живут, пока жив он. Скрытые классы могут выгружаться из памяти независимо, как только на них исчезают ссылки. Это предотвращает утечки памяти (Metaspace leak) при частой генерации кода
Свойства:
* Не обнаруживаются. Их нельзя найти через Class.forName, ClassLoader.loadClass и т.п. Единственный способ получить к ним доступ — через объект Class, который вернул Lookup::defineHiddenClass
* Нельзя использовать в сигнатурах. Скрытый класс не может быть типом поля, параметром метода, возвращаемым типом или суперклассом.
* Могут быть выгружены. Если на экземпляры скрытого класса и на сам Class нет ссылок, он может быть удалён из памяти даже при «живом» загрузчике классов — это экономит Metaspace.
* Доступ к приватным членам. С помощью опции ClassOption.NESTMATE скрытый класс можно сделать «соседом по гнезду» (nestmate) с хост‑классом и тем самым дать ему доступ к его private-членам. Так же можно получить доступ через Lookup объект.
* Нельзя использовать его в типизации: нельзя объявить поле

  }
