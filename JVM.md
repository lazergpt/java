# Сборка мусора

## Как JVM понимает, что объект «мусор»
Объект считается живым, если на него есть ссылка из «корней» (GC Roots). Если до объекта нельзя добраться из корней — он становится мусором.
Что считается GC Roots:
- локальные переменные и параметры методов в стеке;
- активные потоки;
- статические поля классов;
- ссылки из JNI.
- захваченные мониторные объекты;

## Три основные фазы работы GC
- Mark: Граф обходится от GC Roots; все доступные объекты помечаются как живые.
  В современных GC(ZGC, Shenandoah) разметка происходит параллельно работе кода. Используются барьеры чтения/записи (Load/Store Barriers) и окрашенные указатели (Colored Pointers).
  Когда приложение обращается к объекту, специальный микро-код JVM проверяет цвет бита в указателе. Если объект еще не размечен, поток приложения сам «помогает» GC, быстро помечая его живым, и идет дальше.
  Потоки приложения и GC размечают память вместе, не мешая друг другу.
- Sweep: Память, занимаемая непомеченными (мертвыми) объектами, освобождается.
  Современные GC (включая G1, ZGC и Shenandoah) вообще не делают фазу Sweep в её классическом понимании.
  Вместо этого память делится на страницы/регионы. Если в регионе в процессе маркировки не осталось живых объектов, JVM просто мгновенно сбрасывает счетчик этого региона в ноль. Регион очищен за одну системную операцию.
- Compact: Оставшиеся живые объекты перемещаются в единый сплошной блок в начале кучи для устранения фрагментации.
  Перемещение объектов тоже стало конкурентным. Потоки GC копируют живые объекты из полупустых регионов в новые прямо во время работы приложения.
  Если GC переместил объект в памяти, то все старые ссылки в коде вашего приложения мгновенно стали невалидными (они указывают на старое место).
  В ZGC это решено через Self-Healing указателей. Когда код пытается прочитать объект по старой ссылке, срабатывает Load Barrier.
  Он видит, что объект переехал, смотрит в специальную таблицу переадресации (Forwarding Table), перенаправляет ваш код к новому адресу объекта и сразу же перезаписывает старую переменную правильным адресом.
Следующее обращение по этой переменной пройдет уже по прямому адресу.

## Поколения памяти GC
Большинство объектов в Java живут недолго. Поэтому куча разделена на зоны:
- Young Generation: Место для новых объектов. Делится на Eden (сюда объекты попадают сразу) и два пространства выживших — Survivor spaces (S1, S2). Сборка здесь называется Minor GC.
- Old (Tenured) Generation: Сюда перемещаются долгоживущие объекты, пережившие заданный порог циклов очистки в Young-зоне. Сборка здесь называется Major GC.
- Metaspace (взамен старого PermGen): Область памяти, где хранятся метаданные классов и методов. Она автоматически меняет размер.

## Основные типы сборщиков мусора в JVM
- Serial GC: Использует один поток, останавливает все приложение ("Stop The World"). Подходит для маленьких приложений (до 100 МБ).
- Parallel GC: Сборщик по умолчанию Java 8. Использует несколько потоков для Young-зоны. Нацелен на максимальную пропускную способность (например, для пакетной обработки данных).
- G1 (Garbage First) GC: Java 9 default. Разделяет кучу на множество равных регионов. Определяет, где больше всего мусора, и очищает эти регионы в первую очередь. 
Подходит для больших куч (от 4 ГБ) с требованиями к малому времени задержки. Чуть выше накладные расходы CPU.
- ZGC / Shenandoah: Современные ультранизкозадержечные сборщики, которые выполняют почти всю работу (включая перемещение объектов) параллельно с работой потоков приложения, снижая паузы до минимума (менее 10 мс). 
Выше потребление CPU, чуть ниже throughput по сравнению с Parallel/G1.
- Epsilon GC - вообще не собирает мусор — только выделяет память. Когда память заканчивается, выбрасывает OutOfMemoryError. Использование - тесты производительности, бенчмарки, сценарии с очень коротким жизненным циклом JVM.
